Explain the MVVM pattern — what are the responsibilities of Model, View, and ViewModel?

One-liner: MVVM separates UI rendering (View) from UI logic (ViewModel) from business data (Model). The ViewModel knows nothing about the View — it exposes only observable state and commands. This makes every layer independently testable.
Model
  • Plain domain entities and DTOs
  • Business rules and validation logic
  • Data access — repository calls
  • Completely unaware of the UI
  • No references to WPF namespaces
  • Fully unit-testable in isolation
View
  • XAML only — no business logic in code-behind
  • Binds to ViewModel properties
  • Triggers Commands on user interaction
  • DataContext set to a ViewModel instance
  • Code-behind limited to UI-only concerns
  • Should be replaceable without breaking logic
ViewModel
  • Implements INotifyPropertyChanged
  • Exposes ICommand properties for actions
  • Transforms Model data for display
  • Mediates between View and Model
  • Handles loading state, error messages
  • Fully testable — no WPF UI required
MVVM — Full layer structure for Rule Engine app 
// ── MODEL — pure domain, no WPF dependency ──────────────────────────────
public class Rule
{
    public int    Id          { get; init; }
    public string Name        { get; set; } = default!;
    public bool   IsActive    { get; set; }
    public int    Priority    { get; set; }

    public bool IsValid() =>
        !string.IsNullOrWhiteSpace(Name) && Priority > 0;
}

// ── VIEW MODEL — mediates, transforms, exposes observable state ──────────
public class RuleListViewModel : BaseViewModel
{
    private readonly IRuleService _ruleService;

    private ObservableCollection<Rule> _rules = [];
    public  ObservableCollection<Rule> Rules
    {
        get => _rules;
        set => SetProperty(ref _rules, value);
    }

    private bool _isLoading;
    public bool  IsLoading
    {
        get => _isLoading;
        set => SetProperty(ref _isLoading, value);
    }

    public ICommand LoadRulesCommand  { get; }
    public ICommand DeleteRuleCommand  { get; }

    public RuleListViewModel(IRuleService ruleService)
    {
        _ruleService      = ruleService;
        LoadRulesCommand  = new AsyncRelayCommand(LoadRulesAsync);
        DeleteRuleCommand = new RelayCommand<Rule>(DeleteRule, r => r?.IsActive == false);
    }

    private async Task LoadRulesAsync()
    {
        IsLoading = true;
        var data = await _ruleService.GetAllAsync();
        Rules     = new ObservableCollection<Rule>(data);
        IsLoading = false;
    }
}

// ── VIEW — XAML only, zero logic ─────────────────────────────────────────
// <ListView ItemsSource="{Binding Rules}" />
// <Button Command="{Binding LoadRulesCommand}" Content="Refresh" />
// <ProgressBar Visibility="{Binding IsLoading, Converter={...}}" />
Layer Knows About Does NOT Know About Testable Without UI?
Model Domain logic, data shapes WPF, ViewModel, View ✓ Yes — pure C#
ViewModel Model, services, commands View, XAML, UI controls ✓ Yes — mock services
View ViewModel (via DataContext) Model, service layer ✗ Needs WPF runtime
🎤 Interview Answer

"In the Rule Engine desktop application, we enforced strict MVVM — ViewModels had zero references to any WPF type. All ViewModels were registered in the DI container and injected with services. This meant every ViewModel was fully unit-testable with xUnit and Moq — no WPF test harness needed. The View was just XAML with bindings. A junior developer on the team initially put a MessageBox call inside the ViewModel — we refactored it to a dialog service interface so it remained testable."

How does data binding work in WPF? What is INotifyPropertyChanged?

Summary: WPF data binding creates a live connection between a UI control's property and a ViewModel property. INotifyPropertyChanged is the contract that tells the WPF binding engine "this property's value has changed — re-read it from me."
Binding Modes — Know Each One
  • OneWay: ViewModel → View only. Use for display-only labels and read-only fields.
  • TwoWay: ViewModel ↔ View. Use for TextBox, CheckBox — user input flows back to ViewModel.
  • OneWayToSource: View → ViewModel only. Rare — used for specific input capture scenarios.
  • OneTime: Reads once at binding initialization. Use for static data — most performant, zero overhead.
C# — BaseViewModel implementing INotifyPropertyChanged correctly 
// Base class used by ALL ViewModels in the project
public abstract class BaseViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    // CallerMemberName — compiler fills in the property name automatically
    // No magic strings: SetProperty(ref _name, value, "Name") ← old, fragile way
    protected void OnPropertyChanged(
        [CallerMemberName] string? propertyName = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));

    // SetProperty: only raises event if value actually changed — prevents redundant UI updates
    protected bool SetProperty<T>(ref T field, T value,
        [CallerMemberName] string? propertyName = null)
    {
        if (EqualityComparer<T>.Default.Equals(field, value)) return false;
        field = value;
        OnPropertyChanged(propertyName);
        return true;
    }
}

// ViewModel using the base class
public class RuleEditViewModel : BaseViewModel
{
    private string _ruleName = string.Empty;
    public string RuleName
    {
        get => _ruleName;
        set
        {
            if (SetProperty(ref _ruleName, value))
            {
                // Dependent properties that need to refresh when RuleName changes
                OnPropertyChanged(nameof(WindowTitle));
                (SaveCommand as RelayCommand)?.RaiseCanExecuteChanged();
            }
        }
    }

    public string WindowTitle => string.IsNullOrEmpty(RuleName)
        ? "New Rule"
        : $"Edit — {RuleName}";  // Computed property, driven by RuleName
}
XAML — Binding modes and ObservableCollection usage 
<!-- DataContext is set once — all child bindings inherit it -->
<Window DataContext="{Binding Source={StaticResource Locator},
                            Path=RuleEditViewModel}">

    <!-- TwoWay: user input flows back to ViewModel -->
    <TextBox Text="{Binding RuleName, Mode=TwoWay,
                           UpdateSourceTrigger=PropertyChanged}" />

    <!-- OneWay: display only, ViewModel drives the value -->
    <TextBlock Text="{Binding WindowTitle, Mode=OneWay}" />

    <!-- ObservableCollection: ListView auto-refreshes on Add/Remove -->
    <ListView ItemsSource="{Binding Rules}"
              SelectedItem="{Binding SelectedRule, Mode=TwoWay}" />

    <!-- IsLoading spinner — bound to bool with converter -->
    <ProgressBar IsIndeterminate="True"
                  Visibility="{Binding IsLoading,
                               Converter={StaticResource BoolToVisibilityConverter}}" />
</Window>
ObservableCollection vs List: Use ObservableCollection<T> for any collection bound to the UI. It implements INotifyCollectionChanged — the ListView automatically re-renders when items are added or removed. Replacing the entire list with List<T> requires raising PropertyChanged on the property itself, which is less efficient for large sets.

What is the Command pattern in WPF? How did you use it in the Rule Engine app?

Summary: The Command pattern decouples a UI action (button click) from the logic that handles it. In WPF, ICommand has two responsibilities — Execute (what happens) and CanExecute (whether the button is enabled). The View never calls business logic directly.
ICommand Contract — Three Members
  • Execute(object? parameter): Runs the action when the button is clicked.
  • CanExecute(object? parameter): Returns true/false — WPF automatically enables or disables the button. Zero code-behind needed.
  • CanExecuteChanged (event): Fires when the enabled/disabled state should be re-evaluated. Raise this when dependent state changes.
C# — RelayCommand implementation (no third-party library) 
// Generic RelayCommand — covers 95% of use cases without pulling in MVVM toolkits
public class RelayCommand<T> : ICommand
{
    private readonly Action<T?>    _execute;
    private readonly Func<T?, bool>? _canExecute;

    public RelayCommand(Action<T?> execute, Func<T?, bool>? canExecute = null)
    {
        _execute    = execute    ?? throw new ArgumentNullException(nameof(execute));
        _canExecute = canExecute;
    }

    public event EventHandler? CanExecuteChanged
    {
        add    => CommandManager.RequerySuggested += value;   // WPF auto-polls CanExecute
        remove => CommandManager.RequerySuggested -= value;
    }

    public bool CanExecute(object? parameter) =>
        _canExecute == null || _canExecute(parameter is T t ? t : default);

    public void Execute(object? parameter) =>
        _execute(parameter is T t ? t : default);

    // Call this manually when CanExecute depends on non-WPF state
    public void RaiseCanExecuteChanged() =>
        CommandManager.InvalidateRequerySuggested();
}

// Async variant — critical for loading/save operations (prevents UI freeze)
public class AsyncRelayCommand : ICommand
{
    private readonly Func<Task> _execute;
    private bool _isExecuting;

    public AsyncRelayCommand(Func<Task> execute) => _execute = execute;

    public event EventHandler? CanExecuteChanged
    {
        add    => CommandManager.RequerySuggested += value;
        remove => CommandManager.RequerySuggested -= value;
    }

    public bool CanExecute(object? _) => !_isExecuting;  // Disabled while running

    public async void Execute(object? _)
    {
        _isExecuting = true;
        CommandManager.InvalidateRequerySuggested();  // Disable button immediately
        try   { await _execute(); }
        finally
        {
            _isExecuting = false;
            CommandManager.InvalidateRequerySuggested(); // Re-enable after done
        }
    }
}
C# — Commands used in Rule Engine ViewModel 
public class RuleEditorViewModel : BaseViewModel
{
    private Rule? _selectedRule;
    public  Rule? SelectedRule
    {
        get => _selectedRule;
        set
        {
            SetProperty(ref _selectedRule, value);
            // CanExecute of these commands depends on SelectedRule
            (DeleteCommand as RelayCommand<Rule>)?.RaiseCanExecuteChanged();
            (ActivateCommand as RelayCommand<Rule>)?.RaiseCanExecuteChanged();
        }
    }

    public ICommand SaveCommand     { get; }
    public ICommand DeleteCommand   { get; }
    public ICommand ActivateCommand { get; }
    public ICommand ExportCommand   { get; }

    public RuleEditorViewModel(IRuleService ruleService)
    {
        // Save — only enabled when a rule is selected AND has a valid name
        SaveCommand = new AsyncRelayCommand(SaveRuleAsync);

        // Delete — only enabled when selected rule is inactive (business rule)
        DeleteCommand = new RelayCommand<Rule>(
            execute:    r => ruleService.DeleteAsync(r!.Id),
            canExecute: r => r != null && !r.IsActive   // Can't delete active rules
        );

        // Activate — only enabled for inactive rules
        ActivateCommand = new RelayCommand<Rule>(
            execute:    r => ruleService.ActivateAsync(r!.Id),
            canExecute: r => r != null && !r.IsActive
        );

        // Export — always enabled, no condition needed
        ExportCommand = new AsyncRelayCommand(ExportToExcelAsync);
    }
}

<Button Content="Save Rule"

<Button Content="Delete"
        Command="{Binding DeleteCommand}"
        CommandParameter="{Binding SelectedRule}" />

        <DataTemplate>
            <Button Content="Activate"

                               RelativeSource={RelativeSource AncestorType=ListView}}"

🎤 Interview Answer

"In the Rule Engine app we had 8 commands per screen — Save, Delete, Activate, Deactivate, Export, Import, Preview, and Reset. We built our own RelayCommand and AsyncRelayCommand base classes rather than pulling in a full MVVM toolkit, which kept our dependency footprint minimal. CanExecute logic enforced business rules visually — you couldn't delete an active rule because the Delete button was disabled by CanExecute, not by a runtime exception. This gave users clear affordance and removed a whole class of invalid-state bugs."

How did you manage thread safety in WPF when updating UI from background threads?

Core rule: WPF controls can only be read or written from the UI thread (the thread that created them). Touching a UI element from a background thread throws an InvalidOperationException. Always marshal UI updates back to the dispatcher thread.
Approach When to Use Modern?
Dispatcher.Invoke() Synchronous marshal — blocks caller until UI update completes Legacy — avoid in new code
Dispatcher.BeginInvoke() Fire-and-forget marshal — non-blocking but no await support Legacy — avoid in new code
async/await on UI thread Start async work, continuation automatically returns to UI thread ✓ Preferred approach
Progress<T> Report incremental progress from background task to UI ✓ Preferred for progress updates
SynchronizationContext Capture UI context for use inside library or non-async code ✓ Useful in framework code
C# — The wrong way vs the right way 
// ❌ WRONG — touches UI label from background thread — InvalidOperationException
Task.Run(() =>
{
    var data = _service.GetHeavyData();
    StatusLabel.Content = "Done";    // ← CRASH: wrong thread
    Rules.Add(data);                  // ← CRASH: ObservableCollection cross-thread
});

// ❌ LEGACY — Dispatcher.Invoke works but blocks the background thread
Task.Run(() =>
{
    var data = _service.GetHeavyData();
    Application.Current.Dispatcher.Invoke(() =>
    {
        StatusLabel.Content = "Done";  // Works, but blocks background thread until done
    });
});

// ✓ MODERN — async/await: background work on thread pool,
//   continuation resumes on UI thread automatically (no Dispatcher needed)
private async void OnLoadButtonClick(object sender, RoutedEventArgs e)
{
    IsLoading = true;                                    // UI thread ✓
    var data = await Task.Run(() => _service.GetHeavyData()); // Thread pool
    Rules     = new ObservableCollection<Rule>(data);    // UI thread ✓ (await returned here)
    IsLoading = false;                                   // UI thread ✓
}
C# — Progress<T> for incremental background reporting 
// Progress<T> captures the SynchronizationContext at construction time (UI thread)
// and automatically marshals ProgressChanged back to it — no Dispatcher needed
private async Task ImportRulesAsync(string filePath)
{
    var progress = new Progress<int>(percent =>
    {
        ImportProgress = percent;                   // Safe — runs on UI thread
        StatusMessage  = $"Importing... {percent}%";
    });

    var importedRules = await Task.Run(() =>
        _importService.ImportAsync(filePath, progress)  // Background work
    );

    Rules = new ObservableCollection<Rule>(importedRules); // UI thread after await
    StatusMessage = $"Imported {importedRules.Count} rules successfully.";
}

// The service calls progress.Report() from the background thread safely
public IEnumerable<Rule> ImportAsync(string path, IProgress<int> progress)
{
    var lines = File.ReadAllLines(path);
    for (int i = 0; i < lines.Length; i++)
    {
        // ... parse line ...
        progress.Report((int)((i + 1) / (double)lines.Length * 100));
    }
}
C# — ObservableCollection thread-safety for parallel updates 
// ObservableCollection is NOT thread-safe for Add/Remove from background threads.
// Solution A: Accumulate on background thread, assign new collection on UI thread
var results = await Task.Run(() => _service.GetAllAsync());  // List<T> on bg thread
Rules = new ObservableCollection<Rule>(results);            // Single assign on UI thread

// Solution B: Dispatcher-aware ObservableCollection for real-time additions
// (custom subclass used in the Rule Engine for live log streaming)
public class ThreadSafeObservableCollection<T> : ObservableCollection<T>
{
    protected override void OnCollectionChanged(NotifyCollectionChangedEventArgs e)
    {
        if (Application.Current?.Dispatcher.CheckAccess() == true)
            base.OnCollectionChanged(e);                       // Already on UI thread
        else
            Application.Current.Dispatcher.Invoke(() =>
                base.OnCollectionChanged(e));                  // Marshal to UI thread
    }
}
🎤 Interview Answer

"In the Rule Engine app, we had a rule validation engine that processed hundreds of rules in parallel on a background thread. Results streamed into the UI as they completed. We used a ThreadSafeObservableCollection that overrides OnCollectionChanged to check and marshal to the dispatcher. For the progress bar and status message, we used Progress<T> — it captures the UI SynchronizationContext at creation, so all Report() calls automatically land on the UI thread. We completely avoided Dispatcher.Invoke in ViewModel code — that would mean the ViewModel knows it's running in WPF, breaking testability."

Why did you replace Interop with Open XML? What were the key challenges?

Context: Microsoft.Office.Interop.Excel automates a running Excel process via COM. Open XML SDK reads and writes the raw .xlsx ZIP/XML format directly — no Office installation, no COM objects, no Excel process required.
❌ Interop — Why We Removed It
  • Requires Microsoft Office installed on every machine
  • Fails on server environments (no Office on Azure/IIS)
  • COM objects must be manually released — memory leaks if you forget
  • Excel process hangs silently on unhandled exceptions
  • Very slow — drives a real Excel UI in the background
  • Microsoft explicitly warns against Interop in server-side code
✓ Open XML — Why We Chose It
  • No Office dependency — works anywhere .NET runs
  • Safe in Azure App Services, IIS, Docker containers
  • No COM marshaling — no memory leak surface
  • 5–10× faster for large files (no Excel UI overhead)
  • Full control over XML structure and styling
  • NuGet package: DocumentFormat.OpenXml
C# — The Interop memory leak problem (why it breaks servers) 
// ❌ Classic Interop code — looks clean, leaks COM objects
var excel    = new Excel.Application();
var workbook = excel.Workbooks.Add();
var sheet    = (Excel.Worksheet)workbook.Sheets[1];

sheet.Cells[1, 1] = "RegistrationNumber";  // Works on dev machine, crashes on server

workbook.SaveAs(@"C:\report.xlsx");
workbook.Close();
excel.Quit();

// Problem: intermediate objects (Sheets, Cells, Range) are also COM objects.
// Each one needs Marshal.ReleaseComObject() — forgetting even one leaks an Excel process.
// On servers: Excel processes pile up, RAM fills, IIS crashes.

// The "two-dot rule": excel.Workbooks.Add() touches two COM objects in one line.
// You can't release the intermediate Workbooks reference.
// This is why Microsoft says: DO NOT use Interop in server-side or service code.
C# — Open XML SDK: generate styled .xlsx with headers and data rows 
using DocumentFormat.OpenXml;
using DocumentFormat.OpenXml.Packaging;
using DocumentFormat.OpenXml.Spreadsheet;

public class ExcelExportService : IExcelExportService
{
    public byte[] ExportRules(IEnumerable<Rule> rules)
    {
        using var stream = new MemoryStream();
        using (var document = SpreadsheetDocument.Create(stream,
            SpreadsheetDocumentType.Workbook))
        {
            var workbookPart  = document.AddWorkbookPart();
            workbookPart.Workbook = new Workbook();

            var worksheetPart = workbookPart.AddNewPart<WorksheetPart>();
            var sheetData     = new SheetData();
            worksheetPart.Worksheet = new Worksheet(sheetData);

            // Register the worksheet in the workbook
            workbookPart.Workbook.AppendChild(new Sheets()).AppendChild(new Sheet
            {
                Id      = workbookPart.GetIdOfPart(worksheetPart),
                SheetId = 1, Name = "Rules"
            });

            // Header row
            sheetData.AppendChild(BuildHeaderRow("Id", "Name", "Priority", "IsActive"));

            // Data rows
            foreach (var rule in rules)
                sheetData.AppendChild(BuildDataRow(
                    rule.Id.ToString(), rule.Name,
                    rule.Priority.ToString(), rule.IsActive.ToString()));

            workbookPart.Workbook.Save();
        }
        return stream.ToArray();
    }

    private static Row BuildHeaderRow(params string[] headers)
    {
        var row = new Row();
        foreach (var h in headers)
            row.AppendChild(new Cell
            {
                DataType  = CellValues.String,
                CellValue = new CellValue(h),
                StyleIndex = 1   // Bold style defined in stylesheet
            });
        return row;
    }

    private static Row BuildDataRow(params string[] values)
    {
        var row = new Row();
        foreach (var v in values)
            row.AppendChild(new Cell
            {
                DataType  = CellValues.String,
                CellValue = new CellValue(v)
            });
        return row;
    }
}
Key Challenges When Migrating from Interop to Open XML
  • Verbose API: Open XML mirrors raw OOXML XML elements — much more code than sheet.Cells[1,1] = "value". We built a thin wrapper (ExcelBuilder) to hide the verbosity from the rest of the codebase.
  • No formula evaluation: Open XML writes formulas as strings — it does not calculate them. If you write =SUM(A1:A10), the result cell shows 0 until Excel recalculates on open. We pre-calculated values server-side and wrote the computed result instead.
  • Shared Strings Table: String cell values in Open XML are stored in a separate SharedStringTable to reduce file size. Skipping it works but produces larger files and can break Excel compatibility for large exports.
  • Date serialization: Dates in Open XML are stored as numeric OA dates, not strings. You must apply a number format style (StyleIndex) to display them correctly in Excel. Easy to miss in testing if your test data uses short date ranges.
  • Styling complexity: Fonts, fills, borders, and number formats are each defined in separate stylesheet parts and referenced by index. The indirection is error-prone — we wrote a StylesheetBuilder helper that pre-registered all styles at workbook creation time.
Alternative — ClosedXML: For teams where Open XML verbosity is a blocker, ClosedXML is a higher-level wrapper over Open XML SDK that brings back the Interop-like ws.Cell("A1").Value = "Name" syntax — while still having no Office dependency. We evaluated it but chose raw Open XML for maximum control over file size and streaming in our export service.
🎤 Interview Answer

"We replaced Interop in the Rule Engine export feature after it started silently hanging on our Azure deployment — no Office on the server. The migration to Open XML took about a week. The biggest challenge was styling: I had initially ignored the SharedStringTable and StylesheetBuilder, which produced files that opened with warnings in Excel. Once I wrapped all style registration into a builder class that ran at workbook initialization, the output was clean. Export time for 10,000 rule records went from 18 seconds with Interop to 1.2 seconds with Open XML — because we eliminated the COM automation overhead entirely."
