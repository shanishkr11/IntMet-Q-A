What is the difference between Code First and Database First approaches?

One-liner: Code First = your C# classes drive the schema. Database First = an existing schema drives your C# classes. For any greenfield project, Code First is the standard choice.
✓ Code First — Preferred
  • Define domain models in C#
  • EF generates migrations & schema
  • Schema lives in version control
  • Clean Architecture friendly
  • Works with CI/CD pipelines
  • Full migration history tracked
Database First — Legacy Use
  • Schema already exists (legacy DBs)
  • EF scaffolds DbContext + models
  • DBAs own the schema directly
  • Difficult to evolve incrementally
  • Regenerating overwrites customizations
  • Harder to integrate with CI/CD
AspectCode FirstDatabase First
Source of truthC# modelsSQL schema
MigrationsTracked in code (version-controlled)Manual SQL scripts
Best forNew projects, Clean ArchitectureLegacy / DBA-managed databases
Evolving schemaIncremental, reversibleRisk of overwriting scaffolding
Team workflowDev-driven, PR-trackedRequires DB access to scaffold
Code First — Domain model + Fluent API configuration 
public class Trailer
{
                public int Id { get; set; }
                public string RegistrationNumber { get; set; } = default!;
                public TrailerStatus Status { get; set; }
                public ICollection<Trip> Trips { get; set; } = [];
}

// Fluent API config — keeps domain model clean (no data annotations)
public class TrailerConfiguration : IEntityTypeConfiguration<Trailer>
{
                public void Configure(EntityTypeBuilder<Trailer> builder)
    {
        builder.HasKey(t => t.Id);
        builder.Property(t => t.RegistrationNumber)
               .HasMaxLength(20)
               .IsRequired();
        builder.HasIndex(t => t.RegistrationNumber).IsUnique();
        builder.HasMany(t => t.Trips)
               .WithOne(tr => tr.Trailer)
               .HasForeignKey(tr => tr.TrailerId)
               .OnDelete(DeleteBehavior.Restrict);
    }
}
🎤 Interview Answer

"In all our greenfield projects — Trailer Management System, Rule Engine — we used Code First exclusively. The schema lives in the repository alongside the application code, so every change goes through a PR, is reviewed, and is tracked in Git history. Database First was only relevant when we integrated with a legacy Oracle database on one project — we scaffolded the models once and then hand-maintained them to avoid the regeneration problem."

How does Lazy Loading vs. Eager Loading work? When would you prefer each?

Summary: Eager loading fetches related data upfront in a single query using Include(). Lazy loading defers it until the navigation property is accessed — silently firing extra queries. In production APIs, default to eager loading.
StrategyHow It WorksQuery CountBest For
Eager Loading JOIN at query time via Include() 1 query API responses, reports, known relationships
Lazy Loading Proxy fires query on property access N+1 risk Desktop apps, rarely in web APIs
Explicit Loading Manual Entry().Collection().Load() Controlled N Conditional loading of large collections
Split Queries AsSplitQuery() — separate SELECTs Controlled Cartesian explosion on multiple Includes
Eager Loading — Preferred in API layer 
// Single JOIN query — predictable, fast, no hidden round-trips
var trailers = await _context.Trailers
    .Include(t => t.Trips)
        .ThenInclude(tr => tr.Driver)
    .Where(t => t.Status == TrailerStatus.Active)
    .AsNoTracking() // Read-only queries — skip change tracking overhead
    .ToListAsync();

// AsSplitQuery — avoids cartesian explosion when including multiple collections
var trailers = await _context.Trailers
    .Include(t => t.Trips)
    .Include(t => t.MaintenanceRecords) // 2 collections = cartesian risk
    .AsSplitQuery()                      // Fires 3 separate SELECTs instead
    .ToListAsync();
Lazy Loading — Enabled but dangerous in web APIs 
// Setup: Install Microsoft.EntityFrameworkCore.Proxies
services.AddDbContext<AppDbContext>(opt =>
    opt.UseSqlServer(connectionString)
       .UseLazyLoadingProxies()); // ⚠ Enable with caution

// Navigation properties must be virtual for proxy interception
public virtual ICollection<Trip> Trips { get; set; } = [];

// Problem: this fires a hidden SELECT for EVERY trailer's Trips
foreach (var trailer in trailers)
{
                var count = trailer.Trips.Count(); // ← silent DB round-trip here
}
Production rule: Disable lazy loading in Web API projects by not calling UseLazyLoadingProxies(). Make every data access explicit. Hidden queries are the #1 cause of performance regressions that only show up under load.
🎤 Interview Answer

"We enforced eager loading as a team standard in the Trailer Management System. Lazy loading was explicitly disabled — if a developer needed related data, they had to Include() it intentionally. This made query behavior predictable, reviewable in PRs, and profiled easily in Azure Application Insights. We used AsSplitQuery() in a few cases where including two large collections caused cartesian explosion on the result set."

How do you handle database migrations in a production environment?

Summary: Never run migrate from a developer machine against production. Generate SQL scripts, review them, and apply through a controlled pipeline with rollback capability.
Production Migration Workflow
  • 1
    Generate idempotent SQL script — dotnet ef migrations script --idempotent produces a script that checks which migrations are already applied before running. Safe to run multiple times.
  • 2
    Review the script — a DBA or senior dev reviews the generated SQL. Catches destructive operations: column drops, data-type changes, index rebuilds on large tables.
  • 3
    Run in CI/CD pipeline — apply via Azure DevOps release pipeline, not from a developer's machine. Ensures auditability and environment parity.
  • 4
    Take a DB snapshot before applying — on Azure SQL, enable Point-in-Time Restore. On-premise: full backup first. This is your rollback strategy.
  • 5
    Use backward-compatible migrations — add columns as nullable first, backfill data, then add NOT NULL constraints in a subsequent migration. Never drop a column in the same release the code stops using it.
Generate idempotent script — safe for production 
# Generate script between two specific migrations (safer for targeted releases)
dotnet ef migrations script 20240101_InitialCreate 20240815_AddBranchIdToTrailer \
  --idempotent \
  --output ./deploy/migrations/20240815_migration.sql \
  --project src/Infrastructure \
  --startup-project src/API
Program.cs — Auto-migrate on startup (staging only, never production) 
// ✓ Acceptable for staging / integration environments
// ✗ Never for production — no review, no rollback point
if (app.Environment.IsStaging())
{
                using var scope = app.Services.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await db.Database.MigrateAsync();
}
Backward-compatible migration pattern — safe column rename 
// WRONG — dropping and re-adding breaks running instances during deploy
migrationBuilder.DropColumn("OldName", "Trailers");
migrationBuilder.AddColumn<string>("NewName", "Trailers");

// CORRECT — expand/contract pattern across two releases
// Release 1: Add nullable new column, keep old
migrationBuilder.AddColumn<string>(
    name: "NewName", table: "Trailers", nullable: true);
migrationBuilder.Sql("UPDATE Trailers SET NewName = OldName"); // Backfill

// Release 2 (separate deploy): Remove old column after all code uses NewName
migrationBuilder.DropColumn("OldName", "Trailers");
Senior insight — Expand/Contract pattern: During a rolling deployment, both old and new application instances run simultaneously. A destructive schema change breaks the old instances before they shut down. Always expand (add) first, contract (remove) in a later release.

What is the N+1 query problem, and how did you resolve it?

Summary: N+1 happens when you load a list of N records, then fire one extra query per record to load related data — resulting in N+1 database round-trips instead of 1. It's invisible in development, catastrophic under load.
❌ N+1 Pattern — 101 queries for 100 trailers
SELECT * FROM Trailers← 1 query
SELECT * FROM Trips WHERE TrailerId = 1← per row
SELECT * FROM Trips WHERE TrailerId = 2← per row
... × 100 trailers = 101 queries total
✓ Fixed with Include() — 1 query with JOIN
SELECT t.*, tr.* FROM Trailers t LEFT JOIN Trips tr ON t.Id = tr.TrailerId
The N+1 problem — how it silently appears 
// ❌ Triggers N+1 — Trips loaded lazily inside the loop
var trailers = await _context.Trailers.ToListAsync(); // Query 1
foreach (var trailer in trailers)
{
                var tripCount = trailer.Trips.Count(); // ← Query 2..N+1
    Console.WriteLine($"Trailer {trailer.Id} has {tripCount} trips");
}
Fix 1 — Eager loading with Include() 
// ✓ Single JOIN query — all related data loaded upfront
var trailers = await _context.Trailers
    .Include(t => t.Trips)
    .AsNoTracking()
    .ToListAsync();

foreach (var trailer in trailers)
{
                var tripCount = trailer.Trips.Count(); // ← Already loaded, no DB hit
}
Fix 2 — Project into DTO to avoid loading full entities 
// ✓ Best for API responses — project only what you need
var result = await _context.Trailers
    .Where(t => t.Status == TrailerStatus.Active)
    .Select(t => new TrailerSummaryDto
    {
        Id = t.Id,
        Registration = t.RegistrationNumber,
        TripCount = t.Trips.Count(),          // ← Translated to SQL COUNT()
        LastTripDate = t.Trips
            .OrderByDescending(tr => tr.Date)
            .Select(tr => tr.Date)
            .FirstOrDefault()
    })
    .AsNoTracking()
    .ToListAsync();
Fix 3 — Detect N+1 with EF Core logging in development 
// Warn when EF fires multiple queries in a single request — catches N+1 early
services.AddDbContext<AppDbContext>(opt =>
{
    opt.UseSqlServer(connectionString);
                if (env.IsDevelopment())
    {
        opt.EnableSensitiveDataLogging();
        opt.LogTo(Console.WriteLine, LogLevel.Information);
        opt.EnableDetailedErrors();
    }
});
🎤 Real Project Example

"In the Trailer Management System, we had a report endpoint that loaded trailers with their full trip history. In dev it felt fast — 10 records. In production with 500 trailers it fired 501 queries and timed out. We diagnosed it with SQL Profiler and Azure Application Insights query tracking. The fix was a single projection query using Select() into a DTO — query count went from 501 to 1, and response time dropped from 8 seconds to 180ms."

When would you use Raw SQL / Stored Procedures over LINQ in EF Core?

Summary: LINQ is the default — readable, type-safe, refactorable. Drop to raw SQL or stored procedures only when LINQ can't express the query efficiently, or when the generated SQL is provably worse than hand-written SQL.
ScenarioUse LINQUse Raw SQL / SP
Standard CRUD operations ✓ Always —
Complex aggregations / window functions Sometimes — check generated SQL ✓ If LINQ output is inefficient
Reporting / bulk reads with CTEs ✗ Rarely expressive enough ✓ Raw SQL or view-backed query
Bulk INSERT / UPDATE / DELETE EF Core 7+ ExecuteUpdateAsync ✓ For very large batches
DBA-tuned queries with query hints ✗ Not supported in LINQ ✓ Stored procedures
Multi-step transactional logic Use with transactions ✓ Stored procedures
Raw SQL with FromSqlRaw — still maps to entities 
// Use when LINQ can't express the query (CTEs, window functions, etc.)
// EF Core still handles result mapping — you keep type safety on the output
var results = await _context.Trailers
    .FromSqlRaw("""
        SELECT t.*, 
               ROW_NUMBER() OVER (PARTITION BY t.BranchId ORDER BY t.CreatedAt DESC) AS RowNum
        FROM   Trailers t
        WHERE  t.Status = 'Active'
    """)
    .AsNoTracking()
    .ToListAsync();

// ⚠ Always use parameterized queries to prevent SQL injection
var branchId = 5;
var trailers = await _context.Trailers
    .FromSqlInterpolated($"SELECT * FROM Trailers WHERE BranchId = {branchId}")
    .ToListAsync(); // EF parameterizes the interpolated value — safe
Stored Procedure execution via EF Core 
// Executing a stored procedure that returns entities
var trailers = await _context.Trailers
    .FromSqlRaw("EXEC sp_GetActiveTrailersByBranch @BranchId",
                new SqlParameter("@BranchId", branchId))
    .AsNoTracking()
    .ToListAsync();

// For SPs that don't map to an entity — use a raw DTO projection
var report = await _context.Database
    .SqlQueryRaw<TrailerReportDto>(
                "EXEC sp_GetTrailerActivityReport @StartDate, @EndDate",
                new SqlParameter("@StartDate", startDate),
                new SqlParameter("@EndDate",   endDate))
    .ToListAsync(); // EF Core 7+ SqlQueryRaw supports non-entity types
EF Core 7+ — Bulk operations without loading entities 
// ✓ ExecuteUpdateAsync — no entity load, single UPDATE statement
await _context.Trailers
    .Where(t => t.LastInspectionDate < DateTime.UtcNow.AddYears(-1))
    .ExecuteUpdateAsync(s =>
        s.SetProperty(t => t.Status, TrailerStatus.RequiresInspection));

// ✓ ExecuteDeleteAsync — no entity load, single DELETE statement
await _context.AuditLogs
    .Where(a => a.CreatedAt < DateTime.UtcNow.AddYears(-7))
    .ExecuteDeleteAsync(); // Retention cleanup — never load 500k rows to delete them
Use LINQ when
  • Standard CRUD and filtering
  • Business logic benefits from type safety
  • Query needs to be composable / reusable
  • Unit testing the query logic matters
  • The generated SQL is clean (check with ToQueryString())
Use Raw SQL / SP when
  • Window functions, CTEs, PIVOT needed
  • Generated LINQ SQL is provably worse
  • DBA has a tuned query with query hints
  • Bulk data operations (>10k rows)
  • Multi-step transactional stored proc logic
Pro tip — inspect before you optimize: Run query.ToQueryString() in development to see the exact SQL EF generates. Many developers jump to raw SQL prematurely. Often, a well-structured LINQ query with Select() projection produces perfectly efficient SQL.
🎤 Interview Answer

"In the Rule Engine application, we had a complex report that ranked rules by execution frequency across multiple branches using ROW_NUMBER() window functions. LINQ couldn't express this cleanly, so we used FromSqlRaw() with a hand-written query while still mapping the results to typed DTOs via EF Core. For bulk archiving of audit logs — sometimes 300k+ rows — we used ExecuteDeleteAsync() in EF Core 7, which generates a single DELETE statement instead of loading every entity into memory."
