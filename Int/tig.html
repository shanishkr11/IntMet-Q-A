ASP.NET Core Middleware

01 / 12
Q1Walk me through the ASP.NET Core request pipeline.▶
Interviewer Can you walk me through the ASP.NET Core request pipeline?
You Sure! The ASP.NET Core pipeline is basically a chain of middleware components. Think of it like a series of layers — each layer can do something before passing the request to the next one, and then also do something on the way back out with the response.

There are three key methods to know: Use() is the most common — it lets you call the next middleware in the chain. Run() is a terminal — it short-circuits and never passes to anything after it. And Map() lets you branch the pipeline based on the URL path or a condition.

The ordering really matters. For example, UseAuthentication must always come before UseAuthorization — because authentication sets up who the user is, and authorization then decides what they're allowed to do. And I always put my exception handler outermost so it catches everything underneath it.
Likely follow-up: "What happens if you register middleware after Run()?" — Answer: It silently gets ignored. The compiler won't warn you — it's a silent bug.
Q2How would you write middleware to log all requests with a correlation ID?▶
Interviewer How would you write middleware to log all requests with a correlation ID?
You I'd implement the IMiddleware interface — that gives proper DI scoping compared to the convention-based approach.

The logic is: first check if the incoming request already has an X-Correlation-Id header — if yes, reuse it; if not, generate a new GUID. I stamp that ID on the response header too, so the caller can trace requests end-to-end. Then I open a logging scope with that correlation ID and log the incoming method and path, call next, and then log the response status code on the way out.

I register it as Transient in DI and wire it up with app.UseMiddleware. One thing I always mention in interviews — using IMiddleware over the lambda approach is the cleaner pattern because it supports scoped services properly.
Q3What's the difference between Use() and Run()?▶
Interviewer What's the difference between Use() and Run()?
You Use() receives a next delegate — so it can optionally pass control to the next middleware in the pipeline. It can do things both before and after calling next. Run() on the other hand is a terminal — it has no next parameter, it always ends the pipeline right there.

The tricky gotcha is: if you call Use() but forget to call await next(context) inside it, it behaves exactly like Run() — silently swallowing everything that comes after. That's a bug I always watch out for in code reviews.
Q4How does UseExceptionHandler differ from custom exception middleware?▶
Interviewer How does UseExceptionHandler differ from custom exception middleware?
You UseExceptionHandler is the built-in option — it catches unhandled exceptions and re-executes the pipeline to a specified error endpoint. It handles edge cases like when the response has already started streaming. It's safe for production out of the box.

Custom exception middleware gives you more control though. I personally prefer it for APIs because I can serialize structured JSON error responses, map domain-specific exceptions to appropriate HTTP status codes like 422 for validation errors, and attach correlation IDs — all without re-executing an error endpoint. I always place it first in the pipeline so it wraps everything else.
Q5Where in the pipeline should authentication middleware be placed, and why?▶
Interviewer Where in the pipeline should authentication middleware be placed, and why?
You UseAuthentication must come after UseRouting — because routing needs to resolve the path first — and before UseAuthorization. The reason is simple: authentication reads the JWT and sets HttpContext.User. Authorization then reads that user to decide what they're allowed to do. If you flip the order, the user is null when authorization runs and every request gets rejected as anonymous.

Also, for public static files, I put UseStaticFiles before authentication — no point in validating tokens for requests that are just fetching a CSS file.
💡 Tip: If they ask what happens after Run(), say it clearly — "Any middleware registered after Run() is unreachable and silently ignored. The compiler won't warn you."

JWT Authentication

02 / 12
Q1Why is JWT stateless and what problem does that cause?▶
Interviewer Why is JWT stateless and what problem does that cause?
You A JWT is self-contained — the server verifies it purely by checking the signature using a secret or key. Nothing is stored server-side, which makes it great for horizontal scaling since any server can validate any token without shared session state.

But the problem is: you can't revoke a valid JWT before it expires. If a token gets stolen, or a user logs out, the token is still technically valid until its expiry. The way I handle this is: keep access tokens short-lived — like 5 to 15 minutes — and use refresh token rotation for longer sessions. If I need hard revocation, I maintain a Redis blacklist keyed by the JWT's unique jti claim, with a TTL matching the token's remaining lifetime.
Likely follow-up: "What's the tradeoff of the Redis blacklist?" — Answer: One extra Redis lookup per request. That's the cost of adding revocation to a stateless system.
Q2How do you implement refresh token rotation?▶
Interviewer How do you implement refresh token rotation?
You Refresh token rotation means every time you use a refresh token, you get a brand new one and the old one is immediately invalidated. This limits the window of misuse if a token gets stolen.

The pattern I use: on login, issue a short-lived JWT — say 15 minutes — plus a long-lived refresh token, maybe 7 days, stored hashed in the database. When the client refreshes, I validate the hashed token, atomically revoke the old one, and issue a new JWT plus a new refresh token. If someone tries to use an already-consumed refresh token — that's reuse detection — I invalidate the entire token family and sign out all sessions for that user. That's the security-critical part most people miss.
Q3How would you revoke a JWT before expiry?▶
Interviewer How would you revoke a JWT before expiry?
You Since JWTs are stateless by design, revocation requires introducing some state. Two approaches I use in production.

The first is a Redis blacklist — on logout, I take the jti claim from the JWT, which is its unique identifier, and store it in Redis with a TTL equal to the token's remaining lifetime. On every authenticated request, my middleware checks Redis before proceeding. It's one extra lookup but very fast.

The second approach — and often cleaner — is combining short-lived access tokens with database-backed refresh tokens. If access tokens expire in 5 minutes, the revocation window is tiny anyway. I just revoke the refresh token in the DB to effectively log out the user permanently.
Q4What's the difference between authentication and authorization?▶
Interviewer What's the difference between authentication and authorization?
You Authentication answers "Who are you?" — it's the process of verifying identity. In ASP.NET Core, that's what sets HttpContext.User through JWT validation or cookie auth.

Authorization answers "What are you allowed to do?" — it checks permissions against the already-established identity. That's what the Authorize attribute and policies do.

The key thing is: authentication always runs first in the pipeline. Authorization can't make any meaningful decisions without a verified identity — that's why the ordering in middleware matters.
Q5How do you secure endpoints with [Authorize] and policies?▶
Interviewer How do you secure endpoints with Authorize and policies?
You I define policies in Program.cs using AddAuthorization. A policy can require a role, a specific claim, or even a custom assertion — for example, "user is Admin OR has the orders.write permission claim". Then I apply it to a controller action with the Authorize attribute, specifying the policy name.

For resource-based authorization — like "can this specific user edit this specific order" — I don't use attribute-based auth. Instead I inject IAuthorizationService and call AuthorizeAsync, passing the user, the resource, and the policy. That way the authorization decision has access to the actual resource data.
💡 Tip: If they push on token revocation, lead with "JWT is stateless by design — the Redis blacklist pattern using the jti claim is the production answer. The tradeoff is one extra Redis lookup per request."

Entity Framework Core

03 / 12
Q1How do you avoid the N+1 problem in EF Core?▶
Interviewer How do you avoid the N+1 problem in EF Core?
You The N+1 problem is when you load N entities and then make one extra query per entity to fetch related data — so if you have 100 orders, you end up with 101 database round trips. That kills performance.

I fix it two ways. For loading full entities, I use eager loading with Include and ThenInclude — that tells EF to join everything in a single query. But my preferred approach for read queries is projection using Select — you project into a DTO shape directly, EF generates a single optimized JOIN query, and you only fetch the columns you actually need. Projection also avoids over-fetching navigation properties you don't use.
Q2When would you use AsNoTracking() and why?▶
Interviewer When would you use AsNoTracking and why?
You By default, EF Core tracks every entity it loads through the ChangeTracker — it keeps snapshots for change detection, which has memory and CPU overhead.

For read-only queries where I'm just displaying data and not going to save changes, I always add AsNoTracking. It can make queries about 30% faster on large result sets and uses significantly less memory. The one rule is: never use it if you intend to modify and save the entity — EF won't track what changed and your updates won't persist.
Q3How do you handle concurrency conflicts in EF Core?▶
Interviewer How do you handle concurrency conflicts in EF Core?
You EF Core uses optimistic concurrency — no locking, but it detects if a row changed between when you read it and when you try to write it.

I add a rowversion column to the entity and configure it as IsRowVersion in the model. When EF generates an UPDATE, it includes the original rowversion in the WHERE clause. If the row was modified by someone else, zero rows are updated and EF throws a DbUpdateConcurrencyException.

I catch that, then decide the resolution strategy: client wins, store wins, or application-specific merge logic. In most cases, I surface it as a 409 Conflict to the client with a message like "This record was modified by another user, please refresh."
Q4How do you implement soft delete transparently using EF Core?▶
Interviewer How do you implement soft delete transparently using EF Core?
You I do this in two parts. First, I override SaveChangesAsync in the DbContext — when EF is about to delete an entity that extends my BaseEntity class, I intercept it, flip the state to Modified, and set IsDeleted to true along with a DeletedAt timestamp. So a hard delete becomes a soft delete transparently.

Second, I add a global query filter in OnModelCreating — something like HasQueryFilter with a condition that filters out IsDeleted records. This applies automatically to every query across the entire application without any developer having to remember to add a where clause. If I need to query deleted records for an admin feature, I use IgnoreQueryFilters to bypass the filter.
Likely follow-up: "Is this a pattern you've used in production?" — This is a senior differentiator. Confirm you have and mention the IgnoreQueryFilters escape hatch.
Q5How do you configure a value object (owned entity) in EF Core?▶
Interviewer How do you configure a value object in EF Core?
You In DDD, value objects have no identity — they're equal by their data. EF Core supports them as owned entities. I configure them with OwnsOne in the model builder, and by default EF maps them to the same table as the parent — no join required, which is efficient.

For example, a Customer entity with a ShippingAddress value object — I configure each address property with a specific column name like ShippingStreet, ShippingCity. The application just works with a strongly-typed Address record, completely unaware of how it's stored. If I want them in a separate table, I can use ToTable in the owned entity configuration.
💡 Tip: When asked about soft delete, mention both parts — the SaveChanges override AND the global query filter. Only mentioning one shows incomplete knowledge.

LINQ

04 / 12
Q1What's the difference between IQueryable and IEnumerable in a LINQ context?▶
Interviewer What's the difference between IQueryable and IEnumerable in LINQ?
You The simplest way I put it: IEnumerable works in memory — it's LINQ to Objects. If you filter an IEnumerable, all the data is already loaded and the filtering happens in C#.

IQueryable builds an expression tree — the query gets translated to SQL and executed on the database. So when you call Where on an IQueryable against an EF DbSet, EF generates a WHERE clause and only the matching rows come back over the wire.

The classic mistake is accidentally casting an IQueryable to IEnumerable too early — suddenly you're pulling the entire table into memory and filtering in C#. I always keep things as IQueryable when building up queries in repositories so callers can add further conditions without additional database round trips.
Q2When does deferred execution cause bugs?▶
Interviewer When does deferred execution cause bugs?
You LINQ queries don't actually run until you enumerate them — with ToList, foreach, First, and so on. This causes two common bugs I've seen.

First: returning an IQueryable from a method where the DbContext is disposed by the time the caller enumerates it. The query never ran — you get an ObjectDisposedException. Fix: always call ToListAsync inside the method, before the context goes out of scope.

Second: multiple enumeration. If you call Count() and then ToList() on the same IQueryable, you're hitting the database twice with the same query. Fix: materialize with ToList once and work with that in-memory list.
Q3Write a LINQ query to group orders by customer and get the total amount.▶
Interviewer Can you describe a LINQ query to group orders by customer and calculate totals?
You Sure. I'd write a GroupBy on the Orders DbSet, grouping by CustomerId and the Customer's name. Then I'd project into a DTO using Select — capturing the customer ID, name, the count of orders using g.Count(), and the total amount using g.Sum. Finally I'd order descending by total amount and call ToListAsync.

EF Core translates the whole thing into a single GROUP BY SQL query. I always verify complex groupings with ToQueryString or SQL logging to make sure EF isn't doing something unexpected like evaluating client-side.
Q4Why can't you use certain C# methods inside an EF Core LINQ query?▶
Interviewer Why can't you use certain C# methods inside an EF Core LINQ query?
You EF Core works by translating C# expression trees into SQL. It can only translate expressions it knows how to map to SQL constructs. Custom C# methods, things like string.Format, or complex business logic simply have no SQL equivalent — EF throws an InvalidOperationException at runtime.

The fix is to fetch the minimal data you need first — like just the Id and Name — and then apply the custom method on the in-memory result. AsEnumerable() is a deliberate switch to client-side evaluation, but I only use it after minimizing what comes back from the database.
Q5How would you debug a LINQ query that generates slow SQL?▶
Interviewer How would you debug a LINQ query that's generating slow SQL?
You Three steps. First, I capture the actual SQL EF is generating — either with query.ToQueryString(), or by enabling SQL logging via LogTo in the DbContext options during development.

Second, I run that SQL in SSMS with SET STATISTICS IO ON and look at the execution plan. I'm hunting for table scans on large tables, key lookups that suggest a missing covering index, or high logical reads that might mean I'm fetching too many columns.

Third, for EF-specific fixes: missing Include causing N+1, calling ToList too early and evaluating in memory, or complex predicates that prevent index use. Adding covering indexes and simplifying the LINQ shape are the most common fixes I end up making.
💡 Tip: IQueryable vs IEnumerable is almost always asked. Have a one-liner ready: "IQueryable builds an expression tree translated to SQL — IEnumerable works on in-memory data."

React Hooks

05 / 12
Q1What causes the stale closure problem in useEffect?▶
Interviewer What causes the stale closure problem in useEffect?
You A useEffect callback closes over variables from the render when it was created. If those variables change later but the effect doesn't re-run — because of an incorrect or empty dependency array — it keeps using the old, stale values.

Classic example: a setInterval inside useEffect with an empty deps array. The interval closes over the initial value of count and keeps logging that initial value forever, even as count updates.

Two fixes: add count to the dependency array so the effect re-runs on change, or use a ref — store the latest count in a ref inside a separate useEffect, and read from the ref inside the interval. The ref approach is preferred for intervals because it avoids recreating the interval on every render. The ESLint exhaustive-deps rule catches most of these at development time.
Q2When should you use useCallback vs useMemo?▶
Interviewer When should you use useCallback versus useMemo?
You useCallback memoizes a function reference — same function object across renders as long as dependencies haven't changed. I use it when passing callbacks to child components wrapped in React.memo, so the child doesn't re-render just because the parent re-rendered and created a new function reference.

useMemo memoizes a computed value — I use it for expensive calculations that I don't want to re-run on every render, like sorting a large list.

But I always caution — don't overuse either. Memoization itself has overhead. I only reach for them after profiling and measuring a real re-render problem, not as a default.
Q3How would you debounce an API call inside a React component?▶
Interviewer How would you debounce an API call inside a React component?
You I extract it into a custom hook — useDebounce — that takes a value and a delay. Inside, it uses useState and useEffect: when the value changes, it sets a setTimeout. The key is the cleanup function — it clears the previous timer if the value changes again before the delay fires. That's what creates the debouncing effect.

In the component, I get the debounced query value from the hook, then have a separate useEffect that fires the API call only when the debounced value changes. So the API only gets called after the user pauses typing for the specified delay — clean and reusable across any component that needs it.
Q4How do you share stateful logic across components?▶
Interviewer How do you share stateful logic across components in React?
You Custom hooks — functions that start with "use" and internally call React hooks. The important thing is that custom hooks share the logic, not the state. Each component that calls the hook gets its own independent state instance.

For example, a usePagination hook that takes total items and page size — it manages the current page, calculates total pages, and exposes next and prev functions. Any component can reuse it without duplicating logic.

If I need shared state — the same state across multiple components — I combine Context with a custom hook, or use a lightweight library like Zustand. For complex global state, Redux Toolkit.
Q5When should you use useReducer instead of useState?▶
Interviewer When should you use useReducer instead of useState?
You I reach for useReducer when the state has multiple sub-values that change together, when the next state depends on the previous state in complex ways, or when I need the transitions to be explicit and testable.

A form with multiple fields and an errors object is a good example — managing that with multiple useState calls gets messy. A reducer with SET_FIELD, SET_ERRORS, and RESET actions makes the state transitions clear and easy to unit test, because the reducer is just a pure function — no React rendering needed to test it.
💡 Tip: The stale closure and cleanup function in useEffect are senior React signals. Walk through a concrete interval example — it shows you really understand how closures and rendering interact.

Azure App Services

06 / 12
Q1How do deployment slots help with zero-downtime deployments?▶
Interviewer How do deployment slots help with zero-downtime deployments?
You Deployment slots are live separate environments within the same App Service. The standard pattern I use: deploy the new version to a staging slot, run smoke tests against the staging URL to confirm everything's working, and then swap staging with production. Azure reroutes traffic instantly — no downtime.

The rollback is equally instant — just swap back. I also make sure to mark environment-specific settings as slot settings, or "sticky" — so things like connection strings don't accidentally swap with the slot and point production at the staging database.
Q2How do you store secrets securely in App Service?▶
Interviewer How do you store secrets securely in App Service?
You Never plain text in App Settings and definitely never in source control. The production pattern I use is Key Vault references. Instead of a connection string value, the App Setting contains a reference like @Microsoft.KeyVault with the vault name and secret name. At runtime, App Service fetches the actual secret from Key Vault transparently — your code just reads Configuration["DbConnectionString"] as normal.

This works through Managed Identity — I enable System-assigned Managed Identity on the App Service and grant it the Key Vault Secrets User role on the vault. No credentials anywhere — Azure handles the authentication between the two services.
Likely follow-up: "What's the benefit over just putting it in App Settings?" — Answer: Secret rotation doesn't require redeployment, access is audited, and the secret never appears in the portal or source control.
Q3What's the difference between vertical and horizontal scaling?▶
Interviewer What's the difference between vertical and horizontal scaling in App Service?
You Vertical — or scale up — means moving to a bigger machine: more CPU, more RAM per instance. It's simple but has a ceiling and can require downtime during the resize.

Horizontal — or scale out — means adding more instances of the same size. That's what handles traffic spikes gracefully, and Azure can auto-scale based on CPU percentage, request queue length, or a schedule.

For stateless APIs I almost always prefer horizontal. The critical requirement though is that your app must actually be stateless — no in-memory sessions, no local filesystem state. I use Redis for distributed caching and Azure Blob Storage for file storage, so any instance can serve any request.
Q4How do you monitor App Service performance?▶
Interviewer How do you monitor App Service performance?
You My primary tool is Application Insights — it gives me request and response times, failure rates, dependency calls to databases and external APIs, and full distributed traces. I integrate it with a single NuGet package and one line in Program.cs.

Beyond that, the Azure portal shows CPU percentage, memory, and HTTP queue length. I always set up alerts on 5xx error rate and P95 response time so I'm notified before users start complaining. And during live incidents, Application Insights Live Metrics is brilliant — real-time stream of requests, failures, and server health.
Q5How do you configure health checks in App Service?▶
Interviewer How do you configure health checks in App Service?
You In Program.cs, I register health checks using AddHealthChecks and chain on SQL Server, Redis, and any custom checks I need — like an external API being reachable. I expose them on a /health endpoint using MapHealthChecks.

Then in the Azure portal, under the App Service's Health check section, I point it to that /health path. Azure will automatically remove instances that fail consecutive health checks from the load balancer and restart them. I set the threshold carefully — usually 2 or 3 consecutive failures — to avoid flapping on transient blips.
💡 Tip: Mentioning Key Vault references and Managed Identity together shows security maturity that most developers lack. It's a strong signal for senior roles.

Azure Functions

07 / 12
Q1When would you use Azure Functions over App Service?▶
Interviewer When would you use Azure Functions over App Service?
You I reach for Azure Functions for event-driven workloads — processing messages from Service Bus, reacting to blob uploads, handling Event Grid events. Also for infrequent or unpredictable traffic, because the Consumption plan only charges for actual execution time. And for scheduled jobs — TimerTrigger is a clean replacement for cron jobs.

I'd stick with App Service for long-running HTTP APIs with consistent traffic, WebSocket or SignalR connections that are stateful, or anywhere I need cold-start-free predictable performance. App Service is always on — Functions on Consumption can have cold start latency.
Q2How do you handle long-running operations with Durable Functions?▶
Interviewer How do you handle long-running operations with Durable Functions?
You Durable Functions add state and orchestration on top of regular Functions. The orchestrator coordinates a sequence of activity functions — each activity does a unit of work like validate an order, charge payment, send a confirmation.

The critical constraint everyone needs to know: the orchestrator must be completely deterministic. It replays from history on each execution, so you absolutely cannot put DateTime.Now, Guid.NewGuid, or any I/O directly in the orchestrator. Those go in activity functions. If you violate this, your orchestration produces different results on replay and things break in subtle, hard-to-debug ways.

Common patterns: sequential chaining, fan-out/fan-in with Task.WhenAll for parallel activities, and waiting for external events for human-in-the-loop workflows.
Q3What is the cold start problem and how do you mitigate it?▶
Interviewer What is the cold start problem and how do you mitigate it?
You On the Consumption plan, Functions scale to zero when idle. The first request after idle has to spin up a new instance — load the runtime, your app code, DI registrations. That can add anywhere from 1 to 10 seconds of latency.

Mitigations depend on how critical latency is. For production APIs, I use the Premium plan which keeps pre-warmed instances always running — cold start essentially disappears. For lighter workloads, I minimize startup time by keeping DI registrations lean, and I use WEBSITE_RUN_FROM_PACKAGE which runs from a zip file and starts faster than reading from the file system.
Q4How do you make an Azure Function idempotent?▶
Interviewer How do you make an Azure Function idempotent?
You Service Bus and queue triggers guarantee at-least-once delivery — the same message can arrive more than once, especially after failures or retries. So the function must be idempotent: processing the same message twice should produce the same result as processing it once.

My standard pattern: use the message's unique ID as an idempotency key. At the start of the function, check if that message ID already exists in a processed-messages table or Redis cache. If yes, return early — skip the work. If no, do the work, then record the ID. I also prefer upserts over inserts in any database operations, so running twice just overwrites with the same data rather than creating duplicates.
Q5How do you inject services into Azure Functions?▶
Interviewer How do you inject services into Azure Functions?
You In the isolated worker model — which is the preferred approach for .NET 8 — it's very similar to App Service. You have a Program.cs with a HostBuilder, and you call ConfigureServices exactly like you would in an ASP.NET Core app — AddDbContext, AddScoped, AddSingleton, whatever you need.

The function class then uses constructor injection just like a regular controller. I always use the isolated model now — it's cleaner, supports the latest .NET versions, and avoids the limitations of the older in-process model where you had to use the FunctionsStartup attribute.
💡 Tip: The orchestrator determinism constraint is the senior differentiator for Durable Functions. If you can explain replay-based execution and why non-deterministic code breaks it, that stands out.

Clean Architecture

08 / 12
Q1Why does Clean Architecture place Domain at the center?▶
Interviewer Why does Clean Architecture place Domain at the center?
You Because the Domain contains the core business logic — the things that make your application unique and valuable. It needs to be independent of everything else so it can evolve freely and be tested in isolation.

The dependency rule is: inner layers know nothing about outer layers. The Domain has no reference to EF Core, no HttpClient, no framework dependencies — just pure C# and .NET base class library types. This means I can run all my business logic tests without spinning up a database or HTTP server. And if I ever need to swap out the database from SQL Server to something else, the Domain doesn't change at all.
Q2Where does validation live — Domain or Application?▶
Interviewer Where does validation live in Clean Architecture — Domain or Application layer?
You Both — but for different concerns, and this distinction matters.

Domain validation enforces invariants — business rules that must always hold true. These live inside entity constructors or methods. For example, an Order entity's constructor throws a DomainException if the total is zero or negative. That rule can never be bypassed regardless of how the entity is created.

Application layer validation handles input and command correctness — required fields, valid formats, structural checks. That's where I use FluentValidation on command objects. It runs before the use case handler executes.

The order is: FluentValidation catches bad input first, then the handler runs and the entity enforces its own invariants. Both layers, different jobs.
Likely follow-up: "Is this something you've done in a real project?" — Be ready with a concrete example from your experience.
Q3How do you test Application layer without a database?▶
Interviewer How do you test the Application layer without a database?
You The Application layer declares interfaces — IOrderRepository, IEmailService — and depends on those abstractions. The Infrastructure layer implements them. In tests, I inject mocks instead.

So a test for CreateOrderHandler: I create mock implementations of IOrderRepository and IEmailService using Moq, pass them to the handler constructor, call Handle with a test command, and then verify on the mocks that the right methods were called. No database, no HTTP, no slow I/O — the test runs in milliseconds. That's the primary architectural benefit of this approach: fast, reliable, isolated unit tests for all business logic.
Q4How do you handle cross-cutting concerns like logging?▶
Interviewer How do you handle cross-cutting concerns like logging in Clean Architecture?
You I use MediatR pipeline behaviors. They wrap every command and query that goes through MediatR — like middleware but for the application layer.

I create a LoggingBehavior that implements IPipelineBehavior — it logs the request name before calling next, and logs completion after. I register it in DI and it automatically applies to every handler. Same pattern for validation, performance monitoring, and transactions. The handlers themselves stay clean — zero boilerplate for cross-cutting concerns in any individual handler.
Q5How does DI enforce the dependency rule?▶
Interviewer How does dependency injection enforce the dependency rule in Clean Architecture?
You The project reference graph is what enforces it at compile time. The Application project declares interfaces but has no project reference to Infrastructure — so it literally cannot import EF Core types. The Domain project references nothing external at all. Infrastructure references Domain and Application to implement their interfaces. And the API project — the outermost layer — references everything to wire up DI.

The DI container connects abstractions to implementations at runtime. The dependency rule is enforced before the code even runs, by the solution's project structure. You cannot accidentally create a forbidden dependency — the compiler stops you.
💡 Tip: "Where does validation live?" has a nuanced answer. Domain = invariants enforced in entities. Application = input validation on commands. Both layers — for different reasons — is the senior answer.

Domain-Driven Design

09 / 12
Q1What is an aggregate root and why should you only have one repository per aggregate?▶
Interviewer What is an aggregate root and why should you only have one repository per aggregate?
You An aggregate is a cluster of related domain objects treated as a single unit for consistency. The aggregate root is the only entry point — all external access goes through it, and it enforces invariants for everything inside.

Take an Order — it's the aggregate root. OrderItem and ShippingAddress are internal. You never update an OrderItem directly from outside; you call order.AddItem() so the Order can enforce its own rules — maybe there's a maximum of 20 items, or it needs to recalculate the total.

One repository per aggregate root because the repository persists the entire aggregate atomically. If you had separate repos for Order and OrderItem, you'd split the consistency boundary across two separate operations — and you could end up with partially saved aggregates.
Q2How do domain events decouple aggregates?▶
Interviewer How do domain events decouple aggregates?
You If aggregates directly reference each other, you get tight coupling. Domain events let an aggregate announce that something happened without knowing who cares or what they'll do about it.

Example: when an Order is completed, it raises an OrderCompletedEvent and adds it to an internal collection. It doesn't know anything about sending emails or releasing inventory reservations. After SaveChangesAsync succeeds, my infrastructure dispatches those events — an event handler in the Application layer sends the confirmation email and tells the inventory service to release the reservation.

Critically, I dispatch after SaveChanges — not before — so events only fire if the transaction actually committed. Otherwise you'd be sending confirmation emails for orders that failed to save.
Q3Difference between entity and value object?▶
Interviewer What's the difference between an entity and a value object in DDD?
You An entity has a unique identity — an ID. Two entities with identical data but different IDs are different objects. Entities are mutable over their lifetime — an order changes status, gets items added.

A value object has no identity. Two value objects with the same data are equal, full stop. They're also immutable — you don't mutate them, you replace them with new instances.

Classic examples of value objects: Money, Address, DateRange, Email address, geographic coordinates. A Money type with amount and currency — if you add two Money objects together, you get back a new Money instance, not a modification of the original. They're modeled as C# records now, which gives you value equality for free.
Q4What is an anti-corruption layer?▶
Interviewer What is an anti-corruption layer?
You When you integrate with an external system — a legacy API, a third-party payment provider, another bounded context — their model is usually very different from yours. Without protection, their concepts leak into your domain and corrupt it.

An Anti-Corruption Layer is a translation layer that maps the external model to your domain model in both directions. In practice it's an adapter class — it implements your domain interface, calls the external service using its model, and translates the response back to your domain types. Your domain never knows Stripe exists — it just works with your PaymentResult type. I use this pattern with every external integration I build.
Q5Can an Order directly reference a Product entity?▶
Interviewer Can an Order directly reference a Product entity?
You No — if Order and Product are in different aggregates or bounded contexts, you reference by ID only, never by object reference. Holding a direct reference would cascade-load an entire Product graph every time you load an Order, crossing aggregate boundaries.

In the OrderItem, I store a ProductId, a snapshot of the product name at order time, and a snapshot of the unit price at order time. That last part is actually critical from a business perspective — a customer's order history should reflect what they paid, not today's price if it changed. So the snapshot solves both the aggregate boundary problem and a real business requirement at the same time.
This is a trap question. The correct answer is "ID only + snapshot of relevant data." It shows you understand both aggregate design and real-world data consistency.

CQRS

10 / 12
Q1Why would you separate read and write models?▶
Interviewer Why would you separate read and write models in CQRS?
You Reads and writes have fundamentally different requirements. Writes need to enforce business rules and maintain consistency through a normalized domain model. Reads just need to be fast and serve the UI directly — they benefit from denormalized, pre-joined data.

Using one model for both creates tension — your normalized write model generates complex joins for every read, and your read-optimized structure doesn't cleanly enforce business rules. CQRS resolves this by letting reads hit a separate optimized read model — which could be a materialized view, a separate read database, or just direct SQL projections — while writes go through the domain model with all its invariants enforced.
Q2How does MediatR implement CQRS in .NET?▶
Interviewer How does MediatR implement CQRS in .NET?
You MediatR acts as an in-process message bus. Commands and queries are plain record or class objects. Handlers contain the logic and implement IRequestHandler.

A command like CreateOrderCommand implements IRequest of int — meaning it returns an order ID. The handler does the work and returns the ID. A query like GetOrderQuery implements IRequest of OrderDto. The controller just calls mediator.Send and doesn't know anything about which handler handles it — completely decoupled.

The beauty is that the controller has zero business logic. It receives the request, sends it to MediatR, and returns the result. All logic lives in focused, single-responsibility handler classes.
Q3What are pipeline behaviors and what are they used for?▶
Interviewer What are MediatR pipeline behaviors?
You Pipeline behaviors wrap every MediatR request and response — think of them as middleware for your application layer. They run in registration order and handle cross-cutting concerns without polluting individual handlers.

The classic stack I use: Logging goes first, then Validation — which runs FluentValidation validators and throws if the command is invalid, then a Transaction behavior for writes. Each behavior calls next to pass through to the next one, or throws to short-circuit. The handlers themselves have zero logging or validation code — completely clean.
Q4When would you NOT use CQRS?▶
Interviewer When would you not use CQRS?
You CQRS adds real complexity — more classes, more abstractions, more indirection. It's definitely not a default for every project.

I skip it for simple CRUD applications where the overhead outweighs the benefit. Small teams where the added indirection slows everyone down. Cases where read and write loads are similar and don't need separate optimization. Or when the domain is very thin — mostly data in, data out with minimal business logic.

My actual rule of thumb: I use CQRS when the read/write complexity or load profiles diverge significantly, or when I need to scale reads independently. For internal tools and simple domains, a service layer pattern is cleaner and faster to work with. CQRS is a deliberate tradeoff, not an architectural default.
Q5How do you implement validation as a cross-cutting concern with MediatR?▶
Interviewer How do you implement validation as a cross-cutting concern with MediatR?
You I use the ValidationBehavior pattern — a pipeline behavior that implements IPipelineBehavior and takes all registered IValidator instances for the request type through DI. Inside Handle, it runs all validators, collects any failures, and throws a ValidationException if there are any. Otherwise it calls next and the handler proceeds.

Registration is clean: I register MediatR for my assembly, then use AddValidatorsFromAssembly to auto-register all FluentValidation validators, then register the ValidationBehavior as a pipeline behavior.

In my global exception middleware, I catch ValidationException and return a 422 with the field-level errors. Zero validation boilerplate in any individual handler — the entire pipeline handles it once.
💡 Tip: The "when NOT to use CQRS" question rewards honest tradeoff thinking. "CQRS is a deliberate tradeoff, not a default" is the senior answer.

AI Integration

11 / 12
Q1How do you implement a RAG pipeline in .NET?▶
Interviewer How do you implement a RAG pipeline in .NET?
You RAG stands for Retrieval Augmented Generation — it grounds an LLM's responses in your own data to avoid hallucinations on domain-specific questions. There are six steps I always describe.

First, chunk — split your documents into roughly 500-token overlapping chunks so context isn't lost at boundaries. Second, embed — generate embedding vectors for each chunk using something like OpenAI's text-embedding-3-small. Third, store — persist those vectors in a vector database like Azure AI Search, Qdrant, or pgvector. Those three are the offline ingestion pipeline.

Then at query time: embed the user's question using the same model, search the vector DB for the top-K most similar chunks — that's the retrieval step. Inject those chunks as context into the LLM prompt. The model then answers based on that provided context. That's the full six-step cycle.
Likely follow-up: "What's the most important step?" — Chunking strategy. Bad chunking breaks everything downstream — too small loses context, too large wastes tokens and reduces precision.
Q2How do you handle token limits when sending large documents to an LLM?▶
Interviewer How do you handle token limits when sending large documents to an LLM?
You Never send the entire document — even though models like GPT-4o support 128K context, large contexts are slow, expensive, and actually reduce answer quality because the model has to process a lot of irrelevant content.

RAG is my preferred approach — I only send the relevant chunks, not the whole document. For cases where I need to summarize an entire large document, I use a sliding window map-reduce approach: chunk the document, summarize each chunk, then summarize the summaries.

I also always count tokens client-side before making the API call using the Microsoft.ML.Tokenizers package — that's tiktoken — so I can fail fast with a clear error rather than getting a cryptic truncation from the API.
Q3What is Semantic Kernel and how does it differ from calling the API directly?▶
Interviewer What is Semantic Kernel and how does it differ from calling the OpenAI API directly?
You Calling the API directly gives you full control — you construct prompts, make HTTP calls, parse responses. Simple and transparent, but you build everything yourself.

Semantic Kernel is Microsoft's SDK that adds higher-level abstractions. It gives you plugins — C# methods the AI can call through function calling. It has a planner that lets the AI autonomously chain plugins to achieve a goal. It has built-in memory abstractions for RAG. And crucially, it abstracts the AI provider — you can swap between OpenAI, Azure OpenAI, or other models through config without changing application code.

My rule: I use Semantic Kernel for agentic, multi-step flows where the AI needs to orchestrate tool calls. For simple one-shot completions, I just call the API directly — no need for the extra abstraction.
Q4How do you stream OpenAI responses to the client?▶
Interviewer How do you stream OpenAI responses to the client?
You I use Server-Sent Events from the API controller. On the controller endpoint, I set the Content-Type to text/event-stream and Cache-Control to no-cache. Then I use the streaming API on the OpenAI client — iterate over the streaming response chunks using await foreach — and for each chunk, write it to the response body in the SSE format: "data: " followed by the text and two newlines, then flush the response body.

On the React frontend, I connect with an EventSource — it automatically handles SSE reconnection — and in the onmessage handler I append each chunk to the displayed response. That gives users the typing effect they expect from AI interfaces.
Q5How would you implement semantic search over a document corpus?▶
Interviewer How would you implement semantic search over a document corpus?
You Two pipelines — offline ingestion and online search.

For ingestion: for each document, I chunk the text with an overlap — say 500 tokens with 50 token overlap — so context isn't lost at chunk boundaries. I generate an embedding vector for each chunk and upsert it into the vector database with a document ID reference.

For search: I embed the user's query with the same embedding model, then search the vector DB for the top-K chunks with the highest cosine similarity — I usually set a minimum similarity threshold around 0.75 to filter out weak matches.

On Azure, I use Azure AI Search with vector search enabled. It also supports hybrid search — combining keyword and semantic — which generally gives better recall than either approach alone.
💡 Tip: RAG is the most-asked AI pattern. Be able to fluently walk through all 6 steps — chunk → embed → store → embed query → retrieve top-K → inject into prompt — without hesitation.

System Design & Performance

12 / 12
Q1How would you add caching to an API without breaking consistency?▶
Interviewer How would you add caching to an API without breaking consistency?
You I use the cache-aside pattern — also called lazy loading. On a read, I check Redis first. If the value is there, return it. If not, fetch from the database, store it in Redis with a TTL, then return it. Nothing is cached until it's first requested, so the cache stays lean.

The critical part for consistency is cache invalidation. On any write operation, I immediately delete or update the corresponding cache entry. For complex scenarios with multiple related cache entries, I use event-driven invalidation — when a domain event fires on save, a handler clears the relevant keys. The TTL is the safety net — even if invalidation misses something, it corrects itself eventually.
Q2How do you diagnose a slow EF Core query in production?▶
Interviewer How do you diagnose a slow EF Core query in production?
You Three steps. First, find it — Application Insights shows me the slowest SQL dependency calls. Or I can query the SQL Server Query Store for historically slow queries.

Second, capture the actual SQL — either EF's ToQueryString in development, or by enabling LogTo in the DbContext options. I want the exact SQL, not an abstraction.

Third, analyze in SSMS with SET STATISTICS IO ON and look at the execution plan. I'm looking for: table scans on large tables which suggest a missing index; key lookups which suggest I need a covering index with INCLUDE columns; or large logical reads which might mean I'm projecting too many columns. Parameter sniffing is another one — if the plan is cached for a specific parameter value that skews the execution, I add OPTION OPTIMIZE FOR UNKNOWN.
Q3What causes thread pool starvation in ASP.NET Core and how do you fix it?▶
Interviewer What causes thread pool starvation in ASP.NET Core and how do you fix it?
You Thread pool starvation happens when all available threads are blocked — waiting for I/O synchronously — so new incoming requests queue up and the server stops responding under load.

The root cause is almost always blocking async code with .Result or .Wait(), or the sync-over-async anti-pattern — calling async code from a sync context using GetAwaiter().GetResult(). These block a thread for the entire duration of the I/O operation instead of returning it to the pool while waiting.

The fix is straightforward: always use async/await consistently all the way down. A thread returned to the pool during an await can serve other requests. Long-running CPU-bound work belongs in background services, not request threads. Application Insights shows thread pool exhaustion through the "requests in queue" metric — that's how I detect it in production.
Q4How do you implement retry and circuit breaker with Polly?▶
Interviewer How do you implement retry and circuit breaker with Polly?
You In .NET 8 with Polly v8, I configure resilience policies on HttpClient in Program.cs using AddResilienceHandler. I chain three policies in order: retry, circuit breaker, and timeout per attempt.

For retry, I configure 3 attempts with exponential backoff — so it waits 1 second, then 2, then 4. For circuit breaker, I set a failure ratio threshold — say if 50% of calls fail in a 30-second sampling window with at least 5 minimum calls, the circuit opens and fails fast for 60 seconds, giving the downstream service time to recover. Timeout prevents any single attempt from hanging indefinitely.

The circuit breaker is the important one for cascade failure prevention — without it, if a downstream service is down, all your threads pile up waiting, which then starves your entire application.
Q5Design a URL shortener — how do you scale it?▶
Interviewer Design a URL shortener and tell me how you'd scale it.
You I always start with requirements. Let's say 100 million URLs, a 10-to-1 read-to-write ratio, under 100 milliseconds redirect latency, global availability. That shapes every decision.

For the core design: shortcode generation using Base62 encoding on a unique ID — 7 characters gives you about 3.5 trillion possible URLs. Storage is simple — a table with shortcode, long URL, created at, and expires at. On redirect, look up shortcode, return a 301 or 302.

For scaling reads — which is where the 10-to-1 ratio matters — Redis cache for hot shortcodes with LRU eviction. The vast majority of redirects are for popular links, so this hits the cache almost every time. For 301 permanent redirects, a CDN caches at the edge — zero origin hits. Read replicas handle any database load that gets through.

For writes: partition by shortcode prefix, rate limit per IP using a Redis sliding window. Analytics go async — publish redirect events to Service Bus, process with an Azure Function, store in a time-series database. Keeps the redirect path blazing fast.
Key framing: Always state requirements first, then make tradeoffs explicit — "I chose Redis over in-memory because we'll have multiple instances." That's what separates strong system design answers.
💡 Tip: For any system design, lead with requirements, then make tradeoffs explicit. "I chose X because Y" demonstrates engineering judgment, not just pattern recitation.
