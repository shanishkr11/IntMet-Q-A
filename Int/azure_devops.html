How did you integrate Azure AD for authentication in the e-commerce app?

Summary: Azure AD integration has two sides — the backend validates the incoming Bearer token issued by Azure, and the frontend uses MSAL.js to acquire that token silently or interactively. You write almost zero auth logic yourself; Microsoft's identity platform handles token issuance, refresh, MFA, and SSO.
Integration Checklist — Azure Portal + Code
  • Step 1 — App Registration: Register two apps in Azure AD — one for the API (exposes scopes), one for the SPA/client (granted those scopes). The API registration defines what permissions exist; the client registration requests them.
  • Step 2 — Expose an API scope: In the API app registration, create a scope such as api://<client-id>/Trailers.Read. This is what the frontend requests in its token.
  • Step 3 — Backend middleware: Microsoft.Identity.Web validates the incoming token — issuer, audience, signature, expiry — with one line of configuration.
  • Step 4 — Frontend MSAL: @azure/msal-browser handles the login redirect, token acquisition, and silent refresh. You never touch a raw token in component code.
  • Step 5 — App Roles for RBAC: Define roles in the API app manifest. Users assigned to roles receive a roles claim in their token — no custom role table needed in your database.
C# — ASP.NET Core backend: Microsoft.Identity.Web setup 
// Program.cs — Microsoft.Identity.Web replaces manual JWT validation entirely
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));

// appsettings.json — no secret stored here; validation uses Azure's public keys
// {
//   "AzureAd": {
//     "Instance":  "https://login.microsoftonline.com/",
//     "TenantId":  "your-tenant-id",
//     "ClientId":  "your-api-client-id",
//     "Audience":  "api://your-api-client-id"
//   }
// }

// The library automatically:
// - Downloads Azure AD's public signing keys (JWKS endpoint)
// - Validates: issuer, audience, signature, expiry, token version
// - Populates HttpContext.User with all claims from the token

// Policy-based RBAC using App Roles defined in Azure AD manifest
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanManageProducts", policy =>
        policy.RequireRole("Product.Manager", "Admin"));

    options.AddPolicy("CanViewOrders", policy =>
        policy.RequireRole("Order.Viewer", "Admin"));
});
C# — Controller: reading Azure AD claims 
[ApiController]
[Route("api/products")]
[Authorize]
public class ProductsController : ControllerBase
{
    [HttpPost]
    [Authorize(Policy = "CanManageProducts")]
    public async Task<IActionResult> CreateProduct(
        [FromBody] CreateProductRequest request)
    {
        // Claims populated automatically by Microsoft.Identity.Web
        var userId       = User.FindFirstValue(ClaimTypes.NameIdentifier); // Azure OID
        var userEmail    = User.FindFirstValue("preferred_username");
        var displayName  = User.FindFirstValue("name");
        var tenantId     = User.FindFirstValue("tid");

        // Use OID as the stable user identifier — email can change, OID never does
        request.CreatedByUserId = userId!;
        var product = await _productService.CreateAsync(request);
        return CreatedAtAction(nameof(GetProduct), new { id = product.Id }, product);
    }
}
TypeScript — React frontend: MSAL configuration and token acquisition 
// lib/msalConfig.ts — configured once, used app-wide
import { PublicClientApplication, Configuration } from '@azure/msal-browser';

const msalConfig: Configuration = {
  auth: {
    clientId:    'your-spa-client-id',
    authority:   'https://login.microsoftonline.com/your-tenant-id',
    redirectUri: window.location.origin,
  },
  cache: { cacheLocation: 'sessionStorage' },  // sessionStorage — cleared on tab close
};

export const msalInstance = new PublicClientApplication(msalConfig);

// Scopes to request — matches the scope exposed in the API app registration
export const apiScopes = ['api://your-api-client-id/Trailers.Read'];

// lib/apiClient.ts — attach Azure AD token to every API request automatically
apiClient.interceptors.request.use(async (config) => {
  const accounts = msalInstance.getAllAccounts();
  if (accounts.length === 0) return config;

  try {
    // acquireTokenSilent: uses cached token or refreshes it — no login popup
    const result = await msalInstance.acquireTokenSilent({
      scopes:  apiScopes,
      account: accounts[0],
    });
    config.headers.Authorization = `Bearer ${result.accessToken}`;
  } catch {
    // Silent refresh failed (expired refresh token) — force interactive login
    await msalInstance.acquireTokenRedirect({ scopes: apiScopes });
  }
  return config;
});
Key design decision — OID vs email as user identifier: Always store the Azure AD Object ID (oid claim) as the user's primary key in your database, not the email address. Email can change (name changes, domain migrations). The oid is immutable for the lifetime of the account in that tenant.
🎤 Interview Answer

"In the e-commerce app we had two Azure AD app registrations — one for the API that exposed scopes like Products.Read and Orders.Manage, and one for the React SPA. The backend used Microsoft.Identity.Web which handled all token validation automatically by downloading Azure's public signing keys. We defined App Roles in the manifest for RBAC — Product.Manager, Order.Viewer — so role assignments lived in Azure AD, not in our database. The frontend used MSAL's acquireTokenSilent inside the Axios interceptor, so the user was never prompted unless their session genuinely expired."

What is your experience with Azure DevOps pipelines? Describe a CI/CD pipeline you set up or worked with.

Summary: We had a two-stage YAML pipeline — a CI build pipeline that ran on every pull request, and a CD release pipeline that deployed to Dev automatically and required a manual approval gate before Staging and Production.
PR / Push → CI Build → Unit Tests → Publish Artifact → Deploy Dev → Approval Gate → Deploy Staging → Deploy Prod
azure-pipelines.yml — Full CI build pipeline 
trigger:
  branches:
    include: [main, develop]
  paths:
    exclude: ['**/*.md', 'docs/**']  # Don't trigger on doc-only changes

pr:
  branches:
    include: [main, develop]       # Run CI on every PR — blocks merge if failed

variables:
  buildConfiguration: 'Release'
  dotnetVersion:      '8.0.x'
  projectPath:        'src/TrailerManagement.API'
  testProjectPath:    'tests/TrailerManagement.Tests'

pool:
  vmImage: 'ubuntu-latest'

stages:
  - stage: Build
    displayName: 'Build & Test'
    jobs:
      - job: BuildJob
        steps:

          - task: UseDotNet@2
            inputs:
              packageType: 'sdk'
              version:     '$(dotnetVersion)'

          - script: dotnet restore $(projectPath)
            displayName: 'Restore NuGet packages'

          - script: |
              dotnet build $(projectPath) \
                --configuration $(buildConfiguration) \
                --no-restore \
                /p:TreatWarningsAsErrors=true   # Fail build on any warning
            displayName: 'Build solution'

          - script: |
              dotnet test $(testProjectPath) \
                --configuration $(buildConfiguration) \
                --no-build \
                --collect:"XPlat Code Coverage" \
                --results-directory $(Agent.TempDirectory)/coverage \
                --logger "trx;LogFileName=test-results.trx"
            displayName: 'Run unit tests with coverage'

          - task: PublishTestResults@2
            inputs:
              testResultsFormat: 'VSTest'
              testResultsFiles: '**/*.trx'
            condition: always()  # Publish results even if tests failed

          - task: PublishCodeCoverageResults@1
            inputs:
              codeCoverageTool: 'Cobertura'
              summaryFileLocation: '$(Agent.TempDirectory)/coverage/**/coverage.cobertura.xml'

          - script: |
              dotnet publish $(projectPath) \
                --configuration $(buildConfiguration) \
                --output $(Build.ArtifactStagingDirectory)/app \
                --no-build
            displayName: 'Publish application'

          - task: PublishBuildArtifacts@1
            inputs:
              PathtoPublish: '$(Build.ArtifactStagingDirectory)'
              ArtifactName:  'drop'   # Named artifact picked up by CD stage
azure-pipelines.yml — CD release stages with approval gate 
  - stage: DeployDev
    displayName: 'Deploy to Dev'
    dependsOn: Build
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/develop'))
    variables:
      - group: 'dev-variable-group'   # Linked to Azure Key Vault — secrets injected at runtime
    jobs:
      - deployment: DeployToDevApp
        environment: 'dev'
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureRmWebAppDeployment@4
                  inputs:
                    azureSubscription: '$(AZURE_SERVICE_CONNECTION)'
                    appType:           'webApp'
                    WebAppName:        'trailer-mgmt-dev'
                    packageForLinux:   '$(Pipeline.Workspace)/drop/app/**/*.zip'

                - task: AzureAppServiceSettings@1
                  inputs:
                    azureSubscription: '$(AZURE_SERVICE_CONNECTION)'
                    appName:           'trailer-mgmt-dev'
                    appSettings: |    # Inject Key Vault secrets as App Settings
                      [
                        {"name": "ConnectionStrings__Default",
                         "value": "$(DB_CONNECTION_STRING)", "slotSetting": false},
                        {"name": "AzureAd__TenantId",
                         "value": "$(AZURE_TENANT_ID)",      "slotSetting": false}
                      ]

  - stage: DeployStaging
    displayName: 'Deploy to Staging'
    dependsOn: DeployDev
    condition: succeeded()
    jobs:
      - deployment: DeployToStaging
        environment: 'staging'   # ← Approval gate configured on this environment in Azure DevOps UI
        strategy:                 #   Pipeline pauses here and emails approvers
          runOnce:
            deploy:
              steps:
                - task: AzureRmWebAppDeployment@4
                  inputs:
                    azureSubscription: '$(AZURE_SERVICE_CONNECTION)'
                    WebAppName:        'trailer-mgmt-staging'
                    packageForLinux:   '$(Pipeline.Workspace)/drop/app/**/*.zip'
                    deployToSlotOrASE: true   # Deploy to staging slot first
                    ResourceGroupName: 'rg-trailer-staging'
                    SlotName:          'staging'

                - task: AzureAppServiceManage@0
                  displayName: 'Swap staging slot to production'
                  inputs:
                    Action:            'Swap Slots'  # Zero-downtime swap
                    WebAppName:        'trailer-mgmt-staging'
                    SourceSlot:        'staging'
Branch Strategy and Pipeline Rules We Enforced
  • Branch policies on main and develop: PRs required at least 1 reviewer approval and a passing CI build before merge was allowed. No direct pushes to protected branches.
  • Variable groups linked to Azure Key Vault: Connection strings, API keys, and tenant IDs were stored in Key Vault — the pipeline injected them at runtime. No secrets in YAML files or source control.
  • Slot swapping for zero-downtime: Deployed to the staging slot on the App Service, ran smoke tests, then swapped slots. The old production slot became the new staging slot, giving instant rollback capability.
  • Separate service connections per environment: Dev, Staging, and Production had distinct Azure service connections with least-privilege service principals — the Dev pipeline could not accidentally deploy to Production.
  • Test gate enforced with /p:TreatWarningsAsErrors=true: Any compiler warning failed the build. This caught nullable reference issues and deprecated API usage before they reached review.

🎤 Interview Answer

"In the Trailer Management System we had a single YAML pipeline file committed to the repo — infrastructure as code, versioned alongside the application. CI ran on every PR: restore, build with warnings-as-errors, unit tests with coverage, then publish a zip artifact. CD had three stages — Dev deployed automatically, Staging and Production required manual approval from a lead. Secrets never touched the YAML file; they came from Azure Key Vault through variable groups. We used slot swapping for production deployments, which gave us instant rollback by swapping slots back if the smoke tests failed post-deploy."

What is the difference between Azure AD and traditional JWT-based auth?

Critical nuance: Azure AD tokens are JWTs — the formats are not opposites. The real distinction is between a managed identity provider (Azure AD) and a self-issued JWT approach where your application is its own token authority.
Aspect Azure AD (Managed IdP) Self-issued JWT
Token issuer Microsoft's STS — globally trusted Your own application / auth server
Signing key management Microsoft rotates keys automatically You manage and rotate the secret yourself
MFA support Built-in — enforced via Conditional Access Must build or integrate separately
SSO Free — works across all Azure AD apps Must implement cross-app token sharing
Token refresh MSAL handles silently with refresh tokens You implement refresh token rotation logic
RBAC App Roles in manifest — roles claim in token You query DB and embed roles in token yourself
Token revocation Conditional Access can revoke immediately JWT is valid until expiry — no instant revocation
User directory Azure AD manages users, groups, devices Your own Users table
Setup complexity App registrations, scopes, tenant config Simpler initial setup for small apps
Best for Enterprise, B2B, Microsoft 365 integration Public APIs, B2C, non-Microsoft ecosystems
Self-issued JWT Flow
  • User POSTs credentials to your /auth/login
  • Your code validates password against DB
  • Your code signs a JWT with your secret key
  • Client stores token, sends in Authorization header
  • Your API validates the signature on every request
  • You implement refresh token table and rotation
  • You handle token revocation (blocklist in DB/Redis)
Azure AD Flow
  • User redirected to login.microsoftonline.com
  • Microsoft validates identity (+ MFA if configured)
  • Microsoft issues a signed JWT access token
  • MSAL stores token, silently refreshes before expiry
  • Your API validates signature using Azure's public keys
  • Refresh tokens managed by Microsoft — invisible to your code
  • Conditional Access revokes sessions instantly if needed
C# — What you own with self-issued JWT vs Azure AD 
// ── SELF-ISSUED JWT — you own the full auth stack ───────────────────────
// You write and maintain all of this:

// 1. Password hashing and validation
var isValid = _passwordHasher.VerifyHashedPassword(user, user.PasswordHash, request.Password);

// 2. Token generation — your secret key must be stored and rotated securely
var token = new JwtSecurityToken(
    issuer:    "https://your-api.com",     // You are the issuer
    audience:  "https://your-api.com",
    claims:    claims,
    expires:   DateTime.UtcNow.AddMinutes(15),
    signingCredentials: new SigningCredentials(
        new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey)),
        SecurityAlgorithms.HmacSha256)
);

// 3. Refresh token — stored in DB, rotated on use, revoked on logout
var refreshToken = new RefreshToken
{
    Token     = Convert.ToBase64String(RandomNumberGenerator.GetBytes(64)),
    UserId    = user.Id,
    ExpiresAt = DateTime.UtcNow.AddDays(7),
    IsRevoked = false
};
await _context.RefreshTokens.AddAsync(refreshToken);

// ── AZURE AD — Microsoft owns all of the above ──────────────────────────
// You write only this in Program.cs:

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));

// Password hashing     → Microsoft handles
// Token signing        → Microsoft's private key (you verify with their public key)
// Refresh tokens       → Microsoft manages, MSAL handles silently
// MFA                  → Conditional Access policy — zero code
// Token revocation     → Conditional Access — zero code
// Key rotation         → Automatic — zero code
When to Choose Which
  • Choose Azure AD when: Your users already have Microsoft 365 / work accounts. You need MFA, SSO, or Conditional Access without building it. You are building a B2B application for corporate clients. You are in a Microsoft-heavy ecosystem (Teams, SharePoint, Dynamics integration).
  • Choose Azure AD B2C when: You have external/consumer users who need social login (Google, Facebook) or local accounts with their own email — this is Azure AD's consumer variant.
  • Choose self-issued JWT when: You need full control over the auth flow. Your users are external consumers without Microsoft accounts. You are building a public API consumed by third-party developers. You are using a non-Microsoft cloud.
  • The worst choice: Mixing both without a clear reason — dual token validation adds complexity and confusion for no benefit.
Interview trap — "Azure AD doesn't use JWT": It does. Azure AD access tokens are signed JWTs — you can decode them at jwt.ms. The difference is the issuer (iss claim shows https://login.microsoftonline.com/<tenantId>/v2.0) and the signing keys — Azure's RSA public keys from https://login.microsoftonline.com/common/discovery/v2.0/keys. Your API validates the signature using those public keys, not a shared secret.
🎤 Interview Answer

"Both approaches produce JWTs — the real difference is who issues and manages them. With self-issued JWTs we own everything: password hashing, signing key storage and rotation, refresh token tables, and revocation. With Azure AD, Microsoft's STS issues the token and we only validate it using their public keys — which rotate automatically. In the e-commerce app, the client already used Microsoft 365 for email and Teams, so Azure AD was the obvious choice. Every employee already had an account, MFA was enforced via Conditional Access with zero code on our side, and SSO worked across all internal tools from day one."
