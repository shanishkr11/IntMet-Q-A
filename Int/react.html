How did you structure your React components in the Trailer Management System?

Core principle: Feature-based folder structure — not type-based. Group everything a feature needs (component, hook, service, types, tests) in one folder. This scales; a components/, hooks/, services/ flat split does not survive past 20 screens.
Folder structure — Trailer Management System

├── features/                    # One folder per domain feature
│   ├── trailers/
│   │   ├── components/

│   │   │   ├── TrailerCard.tsx       # Dumb — pure display, no side effects

✓ Smart Component — TrailerList
  • Owns useTrailers() hook call
  • Handles loading and error states
  • Passes clean data down as props
  • Contains pagination and filter logic
  • Connects to global state if needed
✓ Dumb Component — TrailerCard

// ── SMART — owns data and orchestrates children ──────────────────────────
export const TrailerList: React.FC = () => {
  const [selectedId, setSelectedId] = useState<number | null>(null);
  const { trailers, isLoading, error } = useTrailers(); // custom hook owns fetch

  if (isLoading) return <Skeleton rows={5} />;
  if (error)     return <ErrorMessage error={error} />;

  return (
    <div className="trailer-list">
      {trailers.map(t => (
        <TrailerCard
          key={t.id}
          trailer={t}
          isSelected={selectedId === t.id}
          onSelect={setSelectedId}
        />
      ))}
    </div>
  );
};
TypeScript — Custom hook encapsulating fetch logic 
// hooks/useTrailers.ts — all data concern lives here, not in the component
export function useTrailers(filters?: TrailerFilters) {
  return useQuery({
    queryKey: ['trailers', filters],         // Cache key — refetches if filters change
    queryFn:  () => trailerService.getAll(filters),
    staleTime: 30_000,                        // Cache fresh for 30s — prevents waterfalls
    select: (data) => data.sort(               // Transform on the way out
      (a, b) => a.registrationNumber.localeCompare(b.registrationNumber)
    ),
  });
}

// Component stays clean — no fetch logic, no try/catch, no loading booleans
const { data: trailers = [], isLoading, error, refetch } = useTrailers(filters);

"In the Trailer Management System, we used a strict feature-based structure. Each feature folder was a self-contained module — you could delete the trailers folder and nothing in trips or drivers would break. Smart components owned the data layer through custom hooks and TanStack Query; dumb components were pure functions wrapped in React.memo. We enforced this in code review — any component that both fetched data AND rendered UI was split. The payoff was that unit testing was trivial: dumb components needed no mocking whatsoever."

How do you manage state in a React app — local state vs. context vs. Redux?

Decision rule: The question is not which tool is best — it is what type of state you are dealing with. Server state, UI state, and global app state are fundamentally different problems that need different solutions.
State Type Tool Example Why
Local UI state useState Modal open, active tab, form field Scoped to one component — keep it local
Shared UI state useState + props / Context Selected trailer across siblings Lift state up or use context for deep trees
Server / async state TanStack Query Trailer list, driver data, reports Caching, refetch, background sync built-in
Global app state Redux Toolkit Auth user, permissions, notifications Predictable, DevTools, time-travel debug
URL state React Router search params Filters, pagination, active tab Shareable, bookmarkable, browser back works
TypeScript — Context: right use vs wrong use 
// ✓ CORRECT use — low-frequency, truly global theme/auth value
const AuthContext = createContext<AuthContextValue | null>(null);

export const AuthProvider: React.FC<{ children: React.ReactNode }> = ({ children }) => {
  const [user, setUser] = useState<User | null>(null);

  const value = useMemo(() => ({        // useMemo prevents context re-render on every parent render
    user,
    isAuthenticated: user !== null,
    login:  (credentials: Credentials) => { /* ... */ },
    logout: () => setUser(null),
  }), [user]);

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
};

// ❌ WRONG use — high-frequency updates in context cause full tree re-renders
// Every subscriber re-renders when ANY property changes, even unrelated ones
const TrailerListContext = createContext({ /* trailers, filters, pagination... */ });
// 50 components subscribed → each filter keystroke re-renders all 50. Use Redux or URL state instead.
TypeScript — Redux Toolkit slice for auth and notifications 
// features/auth/authSlice.ts — Redux Toolkit (RTK) removes all the old boilerplate
const authSlice = createSlice({
  name: 'auth',
  initialState: { user: null as User | null, isLoading: false },
  reducers: {
    logout: (state) => { state.user = null; },
  },
  extraReducers: (builder) => {
    builder
      .addCase(loginThunk.pending,   (state)         => { state.isLoading = true; })
      .addCase(loginThunk.fulfilled, (state, action) => {
        state.user      = action.payload;
        state.isLoading = false;
      })
      .addCase(loginThunk.rejected,  (state)         => { state.isLoading = false; });
  },
});

// Typed selector — co-locate with slice, not in component
export const selectCurrentUser =
  (state: RootState) => state.auth.user;

// Async thunk with createAsyncThunk — handles pending/fulfilled/rejected automatically
export const loginThunk = createAsyncThunk(
  'auth/login',
  async (credentials: Credentials, { rejectWithValue }) => {
    try   { return await authService.login(credentials); }
    catch (err) { return rejectWithValue('Invalid credentials'); }
  }
);
TypeScript — Server state with TanStack Query (replaces Redux for API data) 
// TanStack Query handles: loading, error, caching, background refetch, pagination
// This replaces the old pattern of: Redux slice + thunk + loading flag + error flag

export function useTrailerDetail(id: number) {
  return useQuery({
    queryKey: ['trailers', id],
    queryFn:  () => trailerService.getById(id),
    enabled:  id > 0,                   // Don't fetch if id is invalid
    retry:    2,                          // Retry failed requests twice
    staleTime: 60_000,
  });
}

// Mutations — handle create/update/delete with optimistic updates
export function useUpdateTrailer() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: trailerService.update,
    onSuccess: (updated) => {
      // Invalidate the list cache + update the detail cache directly
      queryClient.invalidateQueries({ queryKey: ['trailers'] });
      queryClient.setQueryData(['trailers', updated.id], updated);
    },
  });
}

How did you implement real-time tracking on the frontend? (SignalR / WebSocket / Polling?)

Summary: We used SignalR — it negotiates the best available transport (WebSocket → Server-Sent Events → Long Polling) automatically. The frontend gets real-time trailer GPS updates without managing raw WebSocket lifecycle code.
Approach Bi-directional Auto-Reconnect Best For
SignalR ✓ Yes ✓ Built-in ASP.NET backends — our choice
Raw WebSocket ✓ Yes ✗ Manual Non-.NET backends, full control needed
Server-Sent Events ✗ One-way only ✓ Native Server-push only, no client messages
Polling ✗ Simulated ✓ Simple Fallback only — wastes bandwidth
TypeScript — SignalR client singleton with reconnection 
// lib/signalrClient.ts — singleton connection, not recreated per component
import * as signalR from '@microsoft/signalr';

let connection: signalR.HubConnection | null = null;

export function getTrackingConnection(): signalR.HubConnection {
  if (!connection) {
    connection = new signalR.HubConnectionBuilder()
      .withUrl(`${import.meta.env.VITE_API_URL}/hubs/tracking`, {
        accessTokenFactory: () => authService.getToken() ?? '',
      })
      .withAutomaticReconnect([0, 2000, 5000, 10000, 30000]) // Exponential back-off
      .configureLogging(signalR.LogLevel.Warning)
      .build();

    // Global lifecycle hooks — log reconnect events for monitoring
    connection.onreconnecting(() => console.warn('SignalR: reconnecting...'));
    connection.onreconnected (() => console.info('SignalR: reconnected'));
    connection.onclose       (() => console.error('SignalR: connection closed'));
  }
  return connection;
}

export async function startConnection(): Promise<void> {
  const conn = getTrackingConnection();
  if (conn.state === signalR.HubConnectionState.Disconnected) {
    await conn.start();
  }
}
TypeScript — Custom hook encapsulating full SignalR lifecycle 
// hooks/useTrailerTracking.ts
interface TrailerPosition {
  trailerId:  number;
  latitude:   number;
  longitude:  number;
  speed:      number;
  updatedAt:  string;
}

export function useTrailerTracking(trailerIds: number[]) {
  const [positions, setPositions] = useState<Map<number, TrailerPosition>>(
    new Map()
  );
  const [isConnected, setIsConnected] = useState(false);

  useEffect(() => {
    if (trailerIds.length === 0) return;

    let isMounted = true;  // Guard against state updates on unmounted component

    const subscribe = async () => {
      const conn = getTrackingConnection();
      await startConnection();

      // Tell the server which trailers we want updates for
      await conn.invoke('SubscribeToTrailers', trailerIds);
      if (isMounted) setIsConnected(true);

      // Server pushes updates — handler called per position update
      conn.on('TrailerPositionUpdated', (position: TrailerPosition) => {
        if (!isMounted) return;
        setPositions(prev => new Map(prev).set(position.trailerId, position));
      });
    };

    subscribe().catch(console.error);

    return () => {                          // Cleanup on unmount / trailerIds change
      isMounted = false;
      const conn = getTrackingConnection();
      conn.off('TrailerPositionUpdated');   // Remove listener — prevent memory leak
      conn.invoke('UnsubscribeFromTrailers', trailerIds).catch(() => {});
    };
  }, [trailerIds.join(',')]);   // Stable dependency — re-subscribes if trailer set changes

  return { positions, isConnected };
}

// Usage in component — completely decoupled from SignalR internals
const { positions, isConnected } = useTrailerTracking([1, 2, 3]);
Common pitfall — duplicate event handlers: Calling connection.on('event', handler) inside a useEffect without connection.off() in the cleanup registers a new handler on every render without removing the old one. After 10 re-renders you have 10 handlers firing for every update. Always pair on() with off() in the cleanup function.
🎤 Interview Answer

"In the Trailer Management System we used SignalR. The backend had a TrackingHub that pushed GPS coordinates every 5 seconds per active trailer. On the frontend, I built a useTrailerTracking hook that managed the full connection lifecycle — connect, subscribe, receive updates, unsubscribe, disconnect. The Map component subscribed to position updates and called Leaflet's marker.setLatLng() directly rather than triggering React re-renders for every coordinate change, which kept the map smooth even with 50 trailers active simultaneously."

How do you handle API error handling in React consistently?

Summary: Consistent error handling has three layers — Axios interceptors catch and normalize HTTP errors globally, TanStack Query surfaces them as typed error state per query, and React Error Boundaries catch render-time crashes. No try/catch scattered across components.
API Call → Axios Interceptor → Normalize Error → TanStack Query → Component / Toast
TypeScript — Axios instance with global interceptor 
// lib/apiClient.ts — single Axios instance used everywhere
export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
  timeout: 15_000,
  headers: { 'Content-Type': 'application/json' },
});

// Request interceptor — attach auth token to every outgoing request
apiClient.interceptors.request.use((config) => {
  const token = authService.getToken();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// Response interceptor — normalize ALL errors before they reach the component
apiClient.interceptors.response.use(
  (response) => response,                          // 2xx — pass through unchanged
  async (error: AxiosError<ApiErrorResponse>) => {
    const status  = error.response?.status;
    const message = error.response?.data?.message ?? error.message;

    switch (status) {
      case 401:
        // Token expired — attempt refresh, retry once, else redirect to login
        try {
          await authService.refreshToken();
          return apiClient.request(error.config!);   // Retry original request
        } catch {
          authService.logout();
          window.location.href = '/login';
        }
        break;
      case 403:
        toast.error('You do not have permission to perform this action.');
        break;
      case 422:
        // Validation errors — let the calling query handle field-level display
        break;
      case 500:
        toast.error('Server error — our team has been notified.');
        break;
    }

    // Normalize to a typed AppError — components never inspect AxiosError directly
    return Promise.reject(new AppError(message, status ?? 0, error.response?.data));
  }
);
TypeScript — Typed AppError class + global QueryClient config 
// Typed error class — all components deal with this, not raw AxiosError
export class AppError extends Error {
  constructor(
    message: string,
    public readonly statusCode: number,
    public readonly details?: ValidationErrors
  ) {
    super(message);
    this.name = 'AppError';
  }

  get isValidationError() { return this.statusCode === 422; }
  get isNotFound()        { return this.statusCode === 404; }
}

// Global TanStack Query config — one retry for non-4xx, immediate fail for client errors
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: (failureCount, error) => {
        if (error instanceof AppError && error.statusCode < 500)
          return false;               // 4xx errors: don't retry — they won't change
        return failureCount < 2;      // 5xx / network: retry up to 2 times
      },
      throwOnError: false,           // Components handle error state, not Error Boundaries
    },
    mutations: {
      onError: (error) => {          // Global mutation error — show toast for unexpected errors
        if (error instanceof AppError && !error.isValidationError)
          toast.error(error.message);
      },
    },
  },
});
TypeScript — Handling validation errors inline + Error Boundary for crashes 
// Inline validation error handling in a mutation
const { mutate: saveTrailer, error } = useUpdateTrailer();

const handleSubmit = (data: TrailerFormData) => {
  saveTrailer(data, {
    onError: (err) => {
      if (err instanceof AppError && err.isValidationError) {
        // Map server validation errors to React Hook Form fields
        Object.entries(err.details ?? {}).forEach(([field, msg]) =>
          setError(field as keyof TrailerFormData, { message: msg })
        );
      }
    },
    onSuccess: () => toast.success('Trailer updated successfully'),
  });
};

// Error Boundary — catches render-time errors (not async errors)
// Placed at route level to prevent full page crash on one widget failure
export class RouteErrorBoundary extends React.Component<
  { children: React.ReactNode }, { hasError: boolean }
> {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(error: Error) { logger.error(error); }  // Send to monitoring
  render() {
    return this.state.hasError
      ? <FallbackScreen onReset={() => this.setState({ hasError: false })} />
      : this.props.children;
  }
}

Components only checked the typed error state from their query hook. This meant a junior dev adding a new feature automatically got consistent error handling, 401 refresh, and toast notifications without writing a single line of error code themselves."

What is the difference between useEffect and useLayoutEffect?

One-liner: Both run after a render — but useEffect runs asynchronously after the browser has painted. useLayoutEffect runs synchronously before the paint. Use useLayoutEffect only when you must read or mutate the DOM before the user sees anything.
React renders → DOM updated → useLayoutEffect → Browser paints → useEffect
Aspect useEffect useLayoutEffect
Timing After browser paint — async Before browser paint — synchronous
Blocks paint? No — non-blocking Yes — blocks until complete
Use for Fetch, subscriptions, timers — 95% of cases DOM measurement, scroll position, tooltips
SSR (Next.js)? ✓ Safe — runs on client only ⚠ Warning — no DOM on server
Performance risk None — deferred Blocks paint if slow — visual delay
TypeScript — useEffect for async work (correct 95% use case) 
// ✓ useEffect — fetch, subscriptions, event listeners, timers
// Runs AFTER paint — user sees the initial render first, then data loads in

function TrailerDetail({ id }: { id: number }) {
  const [trailer, setTrailer] = useState<Trailer | null>(null);

  useEffect(() => {
    let cancelled = false;   // Guard for React Strict Mode double-fire in dev

    trailerService.getById(id).then(data => {
      if (!cancelled) setTrailer(data);
    });

    return () => { cancelled = true; };   // Cleanup — ignore stale response
  }, [id]);   // Re-runs when id changes

  return trailer ? <TrailerCard trailer={trailer} /> : <Skeleton />;
}
TypeScript — useLayoutEffect for DOM measurement before paint 
// ✓ useLayoutEffect — read DOM dimensions, reposition elements before user sees them
// If you used useEffect here, the tooltip would flash at the wrong position then jump

function Tooltip({ targetRef, content }: TooltipProps) {
  const tooltipRef = useRef<HTMLDivElement>(null);
  const [position, setPosition] = useState({ top: 0, left: 0 });

  useLayoutEffect(() => {
    if (!targetRef.current || !tooltipRef.current) return;

    // Read DOM — getBoundingClientRect must run BEFORE paint to avoid flicker
    const targetRect  = targetRef.current.getBoundingClientRect();
    const tooltipRect = tooltipRef.current.getBoundingClientRect();

    setPosition({
      top:  targetRect.bottom + 8,
      left: targetRect.left + (targetRect.width / 2) - (tooltipRect.width / 2),
    });
  }, [targetRef]);  // Recalculate if target changes

  return (
    <div
      ref={tooltipRef}
      style={{ position: 'fixed', top: position.top, left: position.left }}
    >
      {content}
    </div>
  );
}

// Other valid useLayoutEffect use cases:
// - Restore scroll position when navigating back
// - Measure element height to drive animation start values
// - Synchronize a canvas size with its container dimensions
// - Any "measure then render" pattern that must not flash
TypeScript — SSR-safe useLayoutEffect for Next.js / SSR projects 
// useLayoutEffect throws a warning in SSR because there is no DOM on the server.
// Solution: swap to useEffect on the server, use useLayoutEffect on the client

import { useEffect, useLayoutEffect } from 'react';

// A drop-in safe alias — commonly named useIsomorphicLayoutEffect
export const useIsomorphicLayoutEffect =
  typeof window !== 'undefined'
    ? useLayoutEffect   // Client — has DOM, use layout effect
    : useEffect;        // Server — no DOM, use regular effect safely

// Usage — exactly the same API, no other changes needed
function Tooltip() {
  useIsomorphicLayoutEffect(() => {
    // DOM measurement code — works in both SSR and CSR
  }, []);
}
✓ Use useEffect when
  • Fetching data from an API
  • Setting up event listeners or subscriptions
  • Starting timers or intervals
  • Logging or analytics calls
  • Updating non-visual external state
  • Default choice — covers 95% of cases
⚠ Use useLayoutEffect when
  • Reading DOM dimensions (getBoundingClientRect)
  • Positioning a tooltip or popover
  • Restoring scroll position
  • Synchronizing canvas size to container
  • Any "measure, then render" that would flicker
  • SSR: use useIsomorphicLayoutEffect alias

"In the Trailer Management System we built a custom Tooltip component for the map — it appeared next to trailer markers and needed to be perfectly centered above them.
