ASP.NET Core Middleware

01 / 12
Request pipeline Use / Run / Map Short-circuiting IMiddleware Exception handling Correlation IDs
Q1 Walk me through the ASP.NET Core request pipeline. ▶
The ASP.NET Core pipeline is a chain of middleware components. Each component can execute logic before calling next() (inbound) and after (outbound). The pipeline is configured in Program.cs using the IApplicationBuilder (or WebApplication) extension methods.

Key methods:
  • Use() — adds middleware that can call the next component. Most common.
  • Run() — terminal middleware. Does not call next; short-circuits the pipeline.
  • Map() / MapWhen() — branches the pipeline based on path or condition.
Ordering matters critically. Example: UseAuthentication() must come before UseAuthorization(). Logging middleware should be first so it captures all requests. 
app.UseExceptionHandler("/error"); // outermost — catches all
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthentication();        // identity must be established
app.UseAuthorization();         // then permissions checked
app.MapControllers();
Q2 How would you write middleware to log all requests with a correlation ID? ▶ 
public class CorrelationMiddleware : IMiddleware
{
    private readonly ILogger<CorrelationMiddleware> _logger;
    public CorrelationMiddleware(ILogger<CorrelationMiddleware> logger)
        => _logger = logger;

    public async Task InvokeAsync(HttpContext ctx, RequestDelegate next)
    {
        var correlationId = ctx.Request.Headers["X-Correlation-Id"]
                            .FirstOrDefault() ?? Guid.NewGuid().ToString();

        ctx.Response.Headers["X-Correlation-Id"] = correlationId;

        using (_logger.BeginScope(new { CorrelationId = correlationId }))
        {
            _logger.LogInformation("→ {Method} {Path}", ctx.Request.Method, ctx.Request.Path);
            await next(ctx);
            _logger.LogInformation("← {StatusCode}", ctx.Response.StatusCode);
        }
    }
}
Register with builder.Services.AddTransient<CorrelationMiddleware>() and app.UseMiddleware<CorrelationMiddleware>(). Using IMiddleware (instead of convention-based) gives you proper DI scoping.
Q3 What's the difference between Use() and Run()? ▶
Use() receives a RequestDelegate next parameter and can call it to pass control to the next middleware. It enables both pre- and post-processing.

Run() is a terminal — it has no next parameter and always short-circuits the pipeline. Any middleware registered after Run() is unreachable.

A common gotcha: calling app.Use() without calling await next(context) behaves like Run() — it silently swallows the rest of the pipeline.
Q4 How does UseExceptionHandler differ from custom exception middleware? ▶
UseExceptionHandler is a built-in middleware that catches unhandled exceptions and re-executes the pipeline to a specified error endpoint. It's production-safe and handles edge cases like response already started.

Custom exception middleware gives you more control — you can serialize structured JSON error responses, map domain exceptions to HTTP status codes, and add correlation IDs without re-executing an error endpoint. 
public async Task InvokeAsync(HttpContext ctx, RequestDelegate next)
{
    try { await next(ctx); }
    catch (DomainException ex)
    {
        ctx.Response.StatusCode = 422;
        await ctx.Response.WriteAsJsonAsync(new { error = ex.Message });
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Unhandled exception");
        ctx.Response.StatusCode = 500;
        await ctx.Response.WriteAsJsonAsync(new { error = "Internal server error" });
    }
}
Best practice: Place custom exception middleware first in the pipeline (outermost wrapper).
Q5 Where in the pipeline should authentication middleware be placed, and why? ▶
UseAuthentication() must come after UseRouting() (so the route is resolved) but before UseAuthorization().

Reason: Authentication reads the token and sets HttpContext.User (ClaimsPrincipal). Authorization then reads HttpContext.User to make access decisions. If you flip them, the user identity is null when authorization runs — every request will be rejected as anonymous.

Static files (UseStaticFiles()) should come before auth if assets are public — no point authenticating file requests unnecessarily.
💡 A common trick question: what happens if you call Use() after Run()? The middleware is registered but never reached. The compiler won't warn you — this is a silent bug.

JWT Authentication

02 / 12
Header.Payload.Signature RS256 vs HS256 Refresh token rotation Claims-based identity Token revocation
Q1Why is JWT stateless and what problem does that cause?▶
A JWT is self-contained — the server verifies it by checking the signature using a secret/key. No session state is stored server-side. This makes JWTs horizontally scalable (any server can verify any token).

The problem: You can't revoke a valid JWT before its expiry. If a user's token is stolen or the user logs out, the token remains valid until exp. Solutions:
  • Keep access tokens short-lived (5–15 min)
  • Maintain a token blacklist in Redis — check on each request (costs one Redis lookup)
  • Use refresh token rotation — long-lived refresh tokens stored in DB can be invalidated
Q2How do you implement refresh token rotation?▶
Refresh token rotation means each time you use a refresh token, you get a new one and the old one is invalidated. This limits the window of misuse if a token is stolen.

Pattern:
  • On login: issue short-lived JWT (15 min) + long-lived refresh token (7 days), stored hashed in DB
  • On refresh: validate refresh token, issue new JWT + new refresh token, invalidate old one atomically
  • If old refresh token is used again (reuse detection) — invalidate the entire family (sign out all sessions)
public async Task<TokenPair> RefreshAsync(string refreshToken)
{
    var stored = await _db.RefreshTokens
        .FirstOrDefaultAsync(t => t.TokenHash == Hash(refreshToken) && !t.IsRevoked);

    if (stored is null) throw new SecurityException("Invalid token");

    stored.IsRevoked = true; // revoke old
    var newRefresh = GenerateRefreshToken();
    _db.RefreshTokens.Add(new RefreshToken { TokenHash = Hash(newRefresh), UserId = stored.UserId });
    await _db.SaveChangesAsync();

    return new TokenPair(GenerateJwt(stored.UserId), newRefresh);
}
Q3How would you revoke a JWT before expiry?▶
Since JWTs are stateless, revocation requires introducing state. Two approaches:

1. Redis blacklist: On logout, add the JWT's jti (unique ID claim) to Redis with TTL = remaining token lifetime. On each authenticated request, check Redis before proceeding. 
// On logout
await _redis.SetAsync($"revoked:{jti}", "1", tokenRemainingLifetime);

// In middleware/auth handler
if (await _redis.KeyExistsAsync($"revoked:{jti}"))
    return AuthenticateResult.Fail("Token revoked");
2. Short expiry + refresh tokens: If access tokens expire in 5 minutes, revocation problem is minimized. Revoke the refresh token in DB for effective logout.
Q4What's the difference between authentication and authorization?▶
Authentication = "Who are you?" — verifies identity. In ASP.NET Core, this sets HttpContext.User (ClaimsPrincipal) via JWT validation, cookie, etc.

Authorization = "What are you allowed to do?" — checks permissions. Done via [Authorize], policies, or roles against the established identity.

In the pipeline: authentication always runs first. Authorization cannot make decisions without a verified identity.
Q5How do you secure endpoints with [Authorize] and policies?▶ 
// Define policy
builder.Services.AddAuthorization(opt =>
{
    opt.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
    opt.AddPolicy("MinAge18", p => p.RequireClaim("age", "18+"));
    opt.AddPolicy("CanEditOrders", p =>
        p.RequireAssertion(ctx =>
            ctx.User.IsInRole("Admin") || ctx.User.HasClaim("permission", "orders.write")));
});

// Apply to endpoint
[Authorize(Policy = "CanEditOrders")]
[HttpPut("orders/{id}")]
public async Task<IActionResult> UpdateOrder(int id, ...) { ... }
For resource-based authorization (e.g. "can this user edit this specific order"), use IAuthorizationService.AuthorizeAsync(user, resource, policy) rather than attribute-based.
💡 Expect a follow-up on token revocation. JWT is stateless by design — the Redis blacklist pattern (jti claim + TTL) is the production answer. Know the tradeoff: one extra Redis lookup per request.

Entity Framework Core

03 / 12

Q1How do you avoid the N+1 problem in EF Core?▶
The N+1 problem occurs when you load N entities then run 1 additional query per entity to fetch related data — resulting in N+1 total database round trips.

Fix 1 — Eager loading with Include: 
var orders = await _db.Orders
    .Include(o => o.Customer)
    .Include(o => o.OrderItems)
        .ThenInclude(i => i.Product)
    .ToListAsync();
Fix 2 — Projection (preferred for read queries): 
var orders = await _db.Orders
    .Select(o => new OrderDto
    {
        Id = o.Id,
        CustomerName = o.Customer.Name,
        Total = o.OrderItems.Sum(i => i.Price * i.Quantity)
    }).ToListAsync();
Projection is better because EF generates a single JOIN query and only selects needed columns — no over-fetching.
Q2When would you use AsNoTracking() and why?▶
By default, EF Core tracks every entity it loads via the ChangeTracker — this has memory and CPU overhead since EF stores snapshots for change detection.

Use AsNoTracking() for read-only queries where you won't update the entities: 
var products = await _db.Products
    .AsNoTracking()
    .Where(p => p.IsActive)
    .ToListAsync();
Benefits: ~30% faster queries on large result sets, less memory usage. Never use it when you intend to modify and save the entity — EF won't know what changed.
Q3How do you handle concurrency conflicts in EF Core?▶
EF Core uses optimistic concurrency — no locks, but it detects if a row changed between read and write.

Setup: Add a [ConcurrencyToken] or rowversion column: 
public byte[] RowVersion { get; set; }
// In OnModelCreating:
entity.Property(e => e.RowVersion).IsRowVersion();
Handle the conflict: 
try
{
    await _db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var dbValues = await entry.GetDatabaseValuesAsync();
    // Option 1: client wins — keep user's changes
    // Option 2: store wins — reload from DB
    // Option 3: merge — application-specific logic
    throw new ConflictException("Record was modified by another user.");
}
Q4How do you implement soft delete transparently using EF Core?▶
Override SaveChangesAsync to intercept deletes, and use a global query filter to exclude soft-deleted records from all queries: 
// Entity base
public abstract class BaseEntity
{
    public bool IsDeleted { get; set; }
    public DateTime? DeletedAt { get; set; }
}

// DbContext
protected override void OnModelCreating(ModelBuilder mb)
{
    mb.Entity<Order>().HasQueryFilter(o => !o.IsDeleted);
}

public override Task<int> SaveChangesAsync(CancellationToken ct = default)
{
    foreach (var entry in ChangeTracker.Entries()
        .Where(e => e.State == EntityState.Deleted && e.Entity is BaseEntity))
    {
        entry.State = EntityState.Modified;
        ((BaseEntity)entry.Entity).IsDeleted = true;
        ((BaseEntity)entry.Entity).DeletedAt = DateTime.UtcNow;
    }
    return base.SaveChangesAsync(ct);
}
To query deleted records, use .IgnoreQueryFilters().
Q5How do you configure a value object (owned entity) in EF Core?▶
In DDD, value objects have no identity — they're equal by value. EF Core supports them as "owned entities": 
// Domain
public record Address(string Street, string City, string PostalCode);

// Entity
public class Customer
{
    public int Id { get; private set; }
    public Address ShippingAddress { get; private set; }
}

// Config
modelBuilder.Entity<Customer>().OwnsOne(c => c.ShippingAddress, addr =>
{
    addr.Property(a => a.Street).HasColumnName("ShippingStreet").HasMaxLength(200);
    addr.Property(a => a.City).HasColumnName("ShippingCity").HasMaxLength(100);
    addr.Property(a => a.PostalCode).HasColumnName("ShippingPostalCode");
});
Owned entities map to the same table by default (no join needed). Use ToTable() to store them in a separate table if preferred.
💡 Soft delete via QueryFilter + SaveChanges override is a classic senior question. Have this pattern memorized — it shows you understand EF internals beyond basic CRUD.

LINQ

04 / 12
Deferred execution IQueryable vs IEnumerable Expression trees GroupBy / SelectMany SQL translation pitfalls
Q1What's the difference between IQueryable and IEnumerable in a LINQ context?▶
IEnumerable<T> — operates in memory. LINQ to Objects. The entire collection is loaded, then filtered locally. Extension methods accept Func<T, bool>.

IQueryable<T> — builds an expression tree. The query is translated to SQL (or another query language) and executed on the data source. Extension methods accept Expression<Func<T, bool>>.

Critical pitfall: 
// BAD: loads ALL orders into memory, then filters in C#
IEnumerable<Order> orders = _db.Orders;
var result = orders.Where(o => o.Total > 1000).ToList();

// GOOD: generates WHERE clause in SQL
IQueryable<Order> orders = _db.Orders;
var result = orders.Where(o => o.Total > 1000).ToList();
Always return IQueryable from repositories when the caller may add further filters.
Q2When does deferred execution cause bugs?▶
LINQ queries don't execute until enumerated (ToList(), foreach, First(), etc.). This causes bugs when:

1. DbContext is disposed before query executes: 
IQueryable<Order> GetOrders() // BAD — context disposed after method returns
{
    using var db = new AppDbContext();
    return db.Orders.Where(o => o.IsActive); // query not executed yet!
}
2. Multiple enumeration: 
var query = _db.Orders.Where(o => o.Total > 100); // not executed
var count = query.Count();    // executes once
var list = query.ToList();    // executes again — 2 DB round trips!
Fix: call ToList() once and work with the materialized result.
Q3Write a LINQ query to group orders by customer and get the total amount.▶ 
var customerTotals = await _db.Orders
    .GroupBy(o => new { o.CustomerId, o.Customer.Name })
    .Select(g => new CustomerSummaryDto
    {
        CustomerId = g.Key.CustomerId,
        CustomerName = g.Key.Name,
        OrderCount = g.Count(),
        TotalAmount = g.Sum(o => o.Total)
    })
    .OrderByDescending(x => x.TotalAmount)
    .ToListAsync();
EF Core translates this to a single SQL GROUP BY query. Always verify the generated SQL with ToQueryString() or SQL logging for complex groupings.
Q4Why can't you use certain C# methods inside an EF Core LINQ query?▶
EF Core translates LINQ expression trees to SQL. It can only translate expressions it knows how to map. C# methods like string.Format(), custom extension methods, or complex business logic have no SQL equivalent — EF throws InvalidOperationException.

// FAILS — EF can't translate MyCustomHelper()
var result = _db.Products.Where(p => MyCustomHelper(p.Name)).ToList();

// FIX — evaluate in memory after fetching necessary data
var products = await _db.Products
    .Select(p => new { p.Id, p.Name }) // fetch only what's needed
    .ToListAsync();
var result = products.Where(p => MyCustomHelper(p.Name)).ToList();
.AsEnumerable() is a deliberate switch to client-side evaluation — use only after minimizing the data fetched.
Q5How would you debug a LINQ query that generates slow SQL?▶
Step 1: Capture the generated SQL: 
var sql = query.ToQueryString(); // EF Core 5+
Or enable SQL logging: optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information)

Step 2: Run the SQL in SSMS — check the execution plan. Look for Table Scans, Key Lookups, missing indexes.

Step 3: Common EF-specific fixes:
  • Missing .Include() causes N+1
  • Calling .ToList() too early forces client evaluation
  • Complex predicates may prevent index use — simplify or add computed columns
  • Add covering indexes for frequently filtered + projected columns
💡 IQueryable vs IEnumerable is asked in nearly every .NET interview. The one-liner answer: IQueryable builds an expression tree translated to SQL; IEnumerable operates on in-memory data.

React Hooks

05 / 12
Stale closure useCallback vs useMemo Custom hooks useRef React.memo useReducer
Q1What causes the stale closure problem in useEffect?▶
A useEffect callback closes over variables from the render it was created in. If those variables change but the effect doesn't re-run (wrong/missing dependencies), it uses old (stale) values. 
// BUG — stale closure: always logs initial count value
useEffect(() => {
    const id = setInterval(() => console.log(count), 1000);
    return () => clearInterval(id);
}, []); // empty deps — effect never re-runs

// FIX 1 — add count to deps (re-creates interval on every change)
useEffect(() => {
    const id = setInterval(() => console.log(count), 1000);
    return () => clearInterval(id);
}, [count]);

// FIX 2 — use functional updater + ref (preferred for intervals)
const countRef = useRef(count);
useEffect(() => { countRef.current = count; }, [count]);
useEffect(() => {
    const id = setInterval(() => console.log(countRef.current), 1000);
    return () => clearInterval(id);
}, []);
The ESLint rule exhaustive-deps catches most of these. Always include it in your project.
Q2When should you use useCallback vs useMemo?▶
useCallback(fn, deps) — memoizes a function reference. Use when passing callbacks to child components wrapped in React.memo — prevents unnecessary re-renders because the callback reference stays stable.

useMemo(() => value, deps) — memoizes a computed value. Use for expensive calculations that shouldn't re-run on every render.

// useCallback — stable function for memoized child
const handleDelete = useCallback((id: number) => {
    dispatch({ type: 'DELETE', id });
}, [dispatch]);

// useMemo — expensive computation
const sortedItems = useMemo(() =>
    [...items].sort((a, b) => a.price - b.price),
[items]);
Don't overuse either. The memoization itself has a cost. Profile first — only optimize when you measure a real re-render problem.
Q3How would you debounce an API call inside a React component?▶
Extract the logic into a custom hook: 
function useDebounce<T>(value: T, delay: number): T {
    const [debounced, setDebounced] = useState(value);
    useEffect(() => {
        const timer = setTimeout(() => setDebounced(value), delay);
        return () => clearTimeout(timer); // cleanup on value change
    }, [value, delay]);
    return debounced;
}

// Usage
function SearchBox() {
    const [query, setQuery] = useState('');
    const debouncedQuery = useDebounce(query, 400);

    useEffect(() => {
        if (debouncedQuery) fetchResults(debouncedQuery);
    }, [debouncedQuery]);
}
The cleanup function is the key — it clears the timer if the value changes before the delay fires, preventing unnecessary API calls.
Q4How do you share stateful logic across components?▶
Use custom hooks — a function starting with use that internally calls React hooks. Custom hooks give each component its own state (they're not singletons), but share the logic.

function usePagination(totalItems: number, pageSize: number) {
    const [page, setPage] = useState(1);
    const totalPages = Math.ceil(totalItems / pageSize);
    const next = () => setPage(p => Math.min(p + 1, totalPages));
    const prev = () => setPage(p => Math.max(p - 1, 1));
    return { page, totalPages, next, prev };
}

// Reusable in any component
const { page, next, prev } = usePagination(orders.length, 20);
For shared state (same state across multiple components), use Context + a custom hook, Zustand, or Redux.
Q5When should you use useReducer instead of useState?▶
Use useReducer when:
  • State has multiple sub-values that change together
  • Next state depends on previous state in complex ways
  • State transitions need to be explicit and testable
type FormState = { name: string; email: string; errors: Record<string, string> };
type Action = { type: 'SET_FIELD'; field: keyof FormState; value: string }
            | { type: 'SET_ERRORS'; errors: Record<string, string> }
            | { type: 'RESET' };

function formReducer(state: FormState, action: Action): FormState {
    switch (action.type) {
        case 'SET_FIELD': return { ...state, [action.field]: action.value };
        case 'SET_ERRORS': return { ...state, errors: action.errors };
        case 'RESET': return initialState;
    }
}

const [state, dispatch] = useReducer(formReducer, initialState);
The reducer is a pure function — easy to unit test without rendering.
💡 Stale closure and the cleanup function in useEffect are the two signals that separate senior React devs. Be ready to walk through a live example.

Azure App Services

06 / 12
Deployment slots Scale-up vs scale-out Key Vault references VNet integration Health checks
Q1How do deployment slots help with zero-downtime deployments?▶
Deployment slots are live environments within the same App Service. The standard pattern:
  1. Deploy new version to staging slot
  2. Run smoke tests against staging URL
  3. Swap staging ↔ production — Azure routes traffic to the new version instantly
  4. Old version is now in staging — quick rollback by swapping back
Slots have their own app settings. Mark settings as "slot settings" (sticky) to prevent them from swapping — e.g. connection strings that are environment-specific. Non-sticky settings (like app version) do swap with the slot.
Q2How do you store secrets securely in App Service?▶
Never store secrets in App Settings as plain text in source control. The production pattern:

Key Vault References — App Service fetches the secret from Key Vault at runtime using its Managed Identity: 
// App Setting value (not a plain secret — a reference):
@Microsoft.KeyVault(VaultName=mykeyvault;SecretName=DbConnectionString)

// Code reads it normally — transparent:
var connStr = Configuration["DbConnectionString"];
Enable System-assigned Managed Identity on the App Service, then grant it Key Vault Secrets User role on the vault. No credentials needed — Azure handles the auth.
Q3What's the difference between vertical and horizontal scaling?▶
Scale up (vertical) — move to a larger App Service Plan tier (more CPU/RAM per instance). Simple but has a ceiling and requires downtime during resize.

Scale out (horizontal) — add more instances of the same size. Handles traffic spikes without changing instance size. Can be manual or auto-scale based on CPU %, request queue, or schedule.

For stateless APIs, horizontal scaling is almost always preferred. The key requirement: your app must be stateless — no in-memory session, no local file system state. Use Redis for distributed caching and Azure Blob for file storage.
Q4How do you monitor App Service performance?▶
Built-in tools:
  • Application Insights — request/response times, failure rates, dependency calls, distributed traces. Integrate via NuGet + builder.Services.AddApplicationInsightsTelemetry()
  • Metrics — CPU %, memory, HTTP queue length in Azure Portal
  • Diagnose and solve problems — built-in detector for common issues (memory leaks, CPU spikes, crashes)
  • Log streaming — real-time stdout logs from the Kudu console
For production, set up alerts on 5xx error rate and P95 response time. Use Application Insights Live Metrics for real-time debugging during incidents.
Q5How do you configure health checks in App Service?▶ 
// Program.cs
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString)
    .AddRedis(redisConnStr)
    .AddCheck<ExternalApiHealthCheck>("external-api");

app.MapHealthChecks("/health", new HealthCheckOptions
{
    ResponseWriter = UIResponseWriter.WriteHealthCheckUIResponse
});
In Azure Portal → App Service → Health check: point to /health. Azure will automatically remove unhealthy instances from load balancing and restart them. Set the threshold (e.g. 2 consecutive failures) to avoid flapping.
💡 Key Vault references (@Microsoft.KeyVault(...)) are the production secret management pattern. Knowing this shows security maturity — most junior devs just paste secrets directly into App Settings.

Azure Functions

07 / 12
Trigger types Durable Functions Cold start Idempotency Dependency injection Output bindings
Q1When would you use Azure Functions over App Service?▶
Use Azure Functions when:
  • Event-driven workloads — process messages from Service Bus, Blob uploads, Event Grid events
  • Infrequent or unpredictable traffic — Consumption plan charges only for execution time
  • Short-lived tasks — image resizing, sending emails, data transformation
  • Scheduled jobs — TimerTrigger replaces cron jobs
Use App Service when:
  • Long-running HTTP APIs with consistent traffic
  • WebSocket or SignalR connections (stateful)
  • You need predictable cold-start-free performance
Q2How do you handle long-running operations with Durable Functions?▶
Durable Functions add state and orchestration on top of Azure Functions. The key constraint: the orchestrator must be deterministic — it replays from history, so never put non-deterministic code (DateTime.Now, Guid.NewGuid, I/O) directly in the orchestrator.

[FunctionName("ProcessOrder_Orchestrator")]
public static async Task RunOrchestrator(
    [OrchestrationTrigger] IDurableOrchestrationContext ctx)
{
    var orderId = ctx.GetInput<int>();
    await ctx.CallActivityAsync("ValidateOrder", orderId);
    await ctx.CallActivityAsync("ChargePayment", orderId);
    await ctx.CallActivityAsync("SendConfirmation", orderId);
}

[FunctionName("ProcessOrder_Start")]
public static async Task<string> Start(
    [HttpTrigger] HttpRequest req,
    [DurableClient] IDurableOrchestrationClient client)
{
    return await client.StartNewAsync("ProcessOrder_Orchestrator", orderId);
}
Patterns: chaining (sequential), fan-out/fan-in (parallel with Task.WhenAll), human interaction (wait for external event), eternal orchestrations.
Q3What is the cold start problem and how do you mitigate it?▶
On the Consumption plan, Azure Functions scale to zero when idle. The first request after idle must spin up a new instance — loading the runtime, app code, and dependencies. This "cold start" can add 1–10 seconds of latency.

Mitigations:
  • Premium plan — keeps pre-warmed instances always running (no cold start)
  • Dedicated (App Service) plan — always-on instances, no cold start
  • Minimize startup time — reduce DI registrations, avoid heavy initialization at startup
  • Use WEBSITE_RUN_FROM_PACKAGE=1 — runs from a zip package, faster startup than file system
  • Ping/warm-up endpoint with App Insights availability tests every few minutes
Q4How do you make an Azure Function idempotent?▶
Azure Functions (especially queue/Service Bus triggers) guarantee at-least-once delivery — the same message can be delivered more than once. Your function must be idempotent: processing the same message twice produces the same result.

Patterns:
  • Use a unique message ID as an idempotency key — check if already processed before doing work
  • Database upserts instead of inserts
  • Store processed message IDs in a cache/DB with TTL
public async Task Run([ServiceBusTrigger("orders")] OrderMessage msg)
{
    if (await _db.ProcessedMessages.AnyAsync(m => m.Id == msg.MessageId))
        return; // already handled — idempotent skip

    await ProcessOrder(msg);
    _db.ProcessedMessages.Add(new ProcessedMessage { Id = msg.MessageId });
    await _db.SaveChangesAsync();
}
Q5How do you inject services into Azure Functions?▶
Azure Functions v4 (.NET isolated) supports standard DI via Program.cs: 
var host = new HostBuilder()
    .ConfigureFunctionsWorkerDefaults()
    .ConfigureServices(services =>
    {
        services.AddDbContext<AppDbContext>(opt =>
            opt.UseSqlServer(Environment.GetEnvironmentVariable("SqlConn")));
        services.AddScoped<IOrderService, OrderService>();
        services.AddSingleton<IEmailService, SendGridEmailService>();
    })
    .Build();

// Function class — constructor injection
public class OrderFunction(IOrderService orderService)
{
    [Function("ProcessOrder")]
    public async Task Run([ServiceBusTrigger("orders")] OrderMessage msg)
        => await orderService.ProcessAsync(msg);
}
In-process functions (v3) use [assembly: FunctionsStartup] instead. The isolated model is preferred for .NET 8+.
💡 Durable Functions orchestrator constraint — deterministic execution only — is the senior differentiator. If you've used it, explaining replay-based execution shows real depth.

Clean Architecture

08 / 12
Domain → Application → Infrastructure → Presentation Dependency rule Use cases Domain purity Testability
Q1Why does Clean Architecture place Domain at the center?▶
The Domain layer contains the core business logic and rules — the things that make your application unique. It must be independent of infrastructure (database, HTTP, UI) so that:
  • Business rules can be tested without a database or web server
  • Infrastructure can be swapped (e.g. SQL → MongoDB) without changing business logic
  • The domain model can evolve independently of frameworks
The dependency rule: inner layers know nothing about outer layers. Domain has no reference to EF Core, HttpClient, or any framework — only C# primitives and .NET BCL types.
Q2Where does validation live — Domain or Application?▶
Both — but for different concerns:

Domain layer — validates invariants (business rules that must always hold). Enforced in entity constructors or methods: 
public class Order
{
    public Order(decimal total)
    {
        if (total <= 0) throw new DomainException("Order total must be positive.");
        Total = total;
    }
}
Application layer — validates input/commands (format, required fields, structural correctness). Use FluentValidation: 
public class CreateOrderCommandValidator : AbstractValidator<CreateOrderCommand>
{
    public CreateOrderCommandValidator()
    {
        RuleFor(x => x.CustomerId).NotEmpty();
        RuleFor(x => x.Items).NotEmpty().WithMessage("Order must have at least one item.");
    }
}
Application validation runs before the use case executes; domain validation runs when the entity is constructed.
Q3How do you test Application layer without a database?▶
Define interfaces in the Application layer (e.g. IOrderRepository, IEmailService). The Application layer depends on abstractions, not implementations. In tests, inject mocks: 
public class CreateOrderHandlerTests
{
    [Fact]
    public async Task Handle_ValidCommand_CreatesOrderAndSendsEmail()
    {
        var repoMock = new Mock<IOrderRepository>();
        var emailMock = new Mock<IEmailService>();
        var handler = new CreateOrderHandler(repoMock.Object, emailMock.Object);

        await handler.Handle(new CreateOrderCommand { CustomerId = 1, Total = 99.99m }, default);

        repoMock.Verify(r => r.AddAsync(It.IsAny<Order>()), Times.Once);
        emailMock.Verify(e => e.SendConfirmationAsync(1), Times.Once);
    }
}
No database, no HTTP — pure unit test. This is the primary architectural benefit of Clean Architecture.
Q4How do you handle cross-cutting concerns like logging?▶
Cross-cutting concerns (logging, validation, performance monitoring, transactions) belong in the Application layer but should not pollute use-case handlers. Use MediatR pipeline behaviors: 
public class LoggingBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
{
    private readonly ILogger<TRequest> _logger;
    public LoggingBehavior(ILogger<TRequest> logger) => _logger = logger;

    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        _logger.LogInformation("Handling {Request}", typeof(TRequest).Name);
        var response = await next();
        _logger.LogInformation("Handled {Request}", typeof(TRequest).Name);
        return response;
    }
}
Register: services.AddTransient(typeof(IPipelineBehavior<,>), typeof(LoggingBehavior<,>)). Order behaviors by registration order.
Q5How does DI enforce the dependency rule?▶
The Application layer declares interfaces: IOrderRepository, IEmailService. The Infrastructure layer implements them: EfOrderRepository : IOrderRepository.

The DI container (in Presentation/Infrastructure) wires them together at runtime. This means:
  • Application project has no project reference to Infrastructure
  • Domain project has no references to anything external
  • Infrastructure references Domain + Application (implements their interfaces)
  • Presentation (API) references everything to configure DI
The compile-time project reference graph enforces the dependency rule — you literally cannot reference a framework from the Domain because there's no NuGet package reference there.
💡 "Where does validation live" has a nuanced answer that trips up many candidates. Domain = invariants (always enforced in entities). Application = input validation (FluentValidation on commands). Both, but for different reasons.

Domain-Driven Design

09 / 12

Q1What is an aggregate root and why should you only have one repository per aggregate?▶
An aggregate is a cluster of domain objects treated as a single unit for data changes. The aggregate root is the sole entry point — all external access goes through it, and it enforces consistency of the entire cluster.

Example: Order is the aggregate root. OrderItem and ShippingAddress are internal. You never update an OrderItem directly — you call order.AddItem() so the Order can enforce its own invariants (e.g. max 20 items, total recalculation).

One repository per aggregate root because the repository persists the entire aggregate atomically. Having separate repos for Order and OrderItem would split the consistency boundary across two persistence operations.
Q2How do domain events decouple aggregates?▶
Aggregates should not directly reference each other — that creates tight coupling across consistency boundaries. Domain events allow side effects to happen without the aggregate knowing about them. 
// Order raises an event — doesn't know who handles it
public class Order : AggregateRoot
{
    public void Complete()
    {
        Status = OrderStatus.Completed;
        AddDomainEvent(new OrderCompletedEvent(Id, CustomerId));
    }
}

// Handler in Application layer — dispatched after SaveChanges
public class OrderCompletedHandler : INotificationHandler<OrderCompletedEvent>
{
    public async Task Handle(OrderCompletedEvent evt, CancellationToken ct)
    {
        await _emailService.SendConfirmationAsync(evt.CustomerId);
        await _inventoryService.ReleaseReservationAsync(evt.OrderId);
    }
}
Dispatch events after SaveChangesAsync() — not before — so events only fire if the transaction succeeds.
Q3Difference between entity and value object?▶
Entity — has a unique identity (Id). Two entities with the same data but different IDs are different objects. Mutable over time (an order changes status, gets items added).

Value object — has no identity. Two value objects with the same data are equal. Immutable — you replace them, not mutate them.

// Value object — no Id, equality by value, immutable
public record Money(decimal Amount, string Currency)
{
    public Money Add(Money other)
    {
        if (Currency != other.Currency) throw new InvalidOperationException();
        return new Money(Amount + other.Amount, Currency); // returns new instance
    }
}
Examples of value objects: Money, Address, DateRange, Email, Coordinates.
Q4What is an anti-corruption layer?▶
When integrating with an external system (legacy API, third-party service, different bounded context), its model may be very different from your domain model. An Anti-Corruption Layer (ACL) is a translation layer that maps the external model to your domain model — preventing the external system's concepts from "polluting" your domain.

// External payment API returns its own model
public class StripePaymentAdapter : IPaymentGateway
{
    public async Task<PaymentResult> ChargeAsync(Money amount, string cardToken)
    {
        // Translate domain model → Stripe model
        var charge = await _stripe.Charges.CreateAsync(new ChargeCreateOptions
        {
            Amount = (long)(amount.Amount * 100), // Stripe uses cents
            Currency = amount.Currency.ToLower(),
            Source = cardToken
        });

        // Translate Stripe response → domain model
        return new PaymentResult(charge.Id, charge.Status == "succeeded");
    }
}
Q5Can an Order directly reference a Product entity?▶
No — if Order and Product are in different aggregates or bounded contexts.

Aggregates reference each other by ID only, not by object reference. This enforces the consistency boundary — loading an Order should not cascade-load an entire Product graph. 
// WRONG — Order holds a reference to Product entity
public class OrderItem { public Product Product { get; set; } }

// CORRECT — Order holds Product's ID (and a snapshot of relevant data)
public class OrderItem
{
    public int ProductId { get; private set; }       // ID reference only
    public string ProductName { get; private set; }  // snapshot at order time
    public decimal UnitPrice { get; private set; }   // snapshot — price may change
    public int Quantity { get; private set; }
}
Snapshotting price/name at order time also solves the problem of product data changing after an order is placed.
💡 "Can Order reference Product directly?" is a trap question. The right answer is "ID only + snapshot of relevant data" — showing you understand both aggregate boundaries and real-world data consistency.

CQRS

10 / 12
Commands vs Queries MediatR Pipeline behaviors Read model optimization Event sourcing
Q1Why would you separate read and write models?▶
Read and write operations have fundamentally different requirements:
  • Writes — need to enforce business rules, maintain consistency, use normalized domain models
  • Reads — need to be fast, serve UI directly, can be denormalized/pre-joined
Using one model for both creates tension — the normalized write model generates complex joins for reads; the read-optimized model doesn't enforce business rules cleanly for writes.

CQRS solves this by letting reads hit a separate, denormalized read model (could be a different DB, materialized views, or simple projections) while writes enforce business rules through the domain model.
Q2How does MediatR implement CQRS in .NET?▶
MediatR acts as an in-process message bus. Commands and queries are message objects; handlers contain the logic. 
// Command (write — no return value or just an ID)
public record CreateOrderCommand(int CustomerId, List<OrderItemDto> Items)
    : IRequest<int>;

public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, int>
{
    public async Task<int> Handle(CreateOrderCommand cmd, CancellationToken ct)
    {
        var order = Order.Create(cmd.CustomerId, cmd.Items);
        await _repo.AddAsync(order);
        return order.Id;
    }
}

// Query (read — returns a DTO)
public record GetOrderQuery(int OrderId) : IRequest<OrderDto>;

// Controller — sends to MediatR, doesn't know the handler
[HttpPost("orders")]
public async Task<IActionResult> Create(CreateOrderCommand cmd)
    => Ok(await _mediator.Send(cmd));
Q3What are pipeline behaviors and what are they used for?▶
Pipeline behaviors wrap every MediatR request/response — like middleware but for the application layer. They run in registration order and are the standard way to add cross-cutting concerns: 
public class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : IRequest<TResponse>
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var failures = _validators
            .SelectMany(v => v.Validate(request).Errors)
            .Where(f => f != null).ToList();

        if (failures.Any())
            throw new ValidationException(failures);

        return await next();
    }
}
Common behaviors: Logging → Validation → Authorization → Transaction → (Handler) → Transaction commit.
Q4When would you NOT use CQRS?▶
CQRS adds complexity — more classes, more abstractions, more indirection. It's not always worth it.

Skip CQRS when:
  • Simple CRUD applications — the overhead outweighs the benefit
  • Small teams where the indirection slows development
  • Read and write loads are similar and don't need separate optimization
  • The domain has very little business logic — it's mostly data in, data out
A senior answer: "I use CQRS when the read/write complexity or load profiles diverge significantly, or when we need to scale reads independently. For internal tools and simple domains, I'll use a service layer pattern instead — CQRS is a tradeoff, not a default."
Q5How do you implement validation as a cross-cutting concern with MediatR?▶
Use the ValidationBehavior pattern (shown in Q3) with FluentValidation. Registration: 
// Register MediatR + validators + behavior
builder.Services.AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(Application).Assembly));
builder.Services.AddValidatorsFromAssembly(typeof(Application).Assembly);
builder.Services.AddTransient(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));

// Catch in global exception middleware
catch (ValidationException ex)
{
    ctx.Response.StatusCode = 422;
    await ctx.Response.WriteAsJsonAsync(new
    {
        errors = ex.Errors.Select(e => new { e.PropertyName, e.ErrorMessage })
    });
}
This means every command/query is automatically validated without adding any validation code to individual handlers — zero boilerplate per handler.
💡 Pipeline behaviors (IPipelineBehavior<,>) are the MediatR answer to cross-cutting concerns. Know the registration order — it matches the behavior pipeline order. Logging → Validation → Transaction is the classic stack.

Q1How do you implement a RAG pipeline in .NET?▶
RAG (Retrieval Augmented Generation) grounds LLM responses in your own data, avoiding hallucinations on domain-specific questions.

Pipeline steps:
  1. Chunk — split documents into ~500-token overlapping chunks
  2. Embed — generate embedding vectors for each chunk (OpenAI text-embedding-3-small)
  3. Store — persist vectors in a vector DB (Azure AI Search, Qdrant, pgvector)
  4. Query — embed the user's question, retrieve top-K similar chunks
  5. Augment — inject retrieved chunks into the LLM prompt as context
  6. Generate — LLM answers based on the provided context
var questionEmbedding = await _embeddings.GetEmbeddingAsync(userQuestion);
var relevantChunks = await _vectorDb.SearchAsync(questionEmbedding, topK: 5);
var context = string.Join("\n\n", relevantChunks.Select(c => c.Text));

var response = await _chat.CompleteAsync($"""
    Use only the context below to answer. If unsure, say so.
    Context: {context}
    Question: {userQuestion}
    """);
Q2How do you handle token limits when sending large documents to an LLM?▶
Never send the entire document — most models cap at 128K context, and large contexts are slow and expensive.

Strategies:
  • RAG (preferred) — retrieve only relevant chunks, not the whole document
  • Sliding window summarization — chunk document, summarize each chunk, then summarize the summaries (map-reduce)
  • Hierarchical chunking — chunk with overlap so sentences don't split mid-context
// Count tokens before sending (avoid truncation surprises)
var tokenizer = TiktokenTokenizer.CreateForModel("gpt-4o");
var tokenCount = tokenizer.CountTokens(promptText);
if (tokenCount > MAX_TOKENS)
    throw new InvalidOperationException($"Prompt too large: {tokenCount} tokens");
Use the Microsoft.ML.Tokenizers package (tiktoken) to count tokens client-side before making the API call.
Q3What is Semantic Kernel and how does it differ from calling the API directly?▶
Direct API call — you construct prompts manually, call OpenAI/Azure OpenAI endpoint, parse the response. Simple, full control, but you build everything yourself.

Semantic Kernel — Microsoft's SDK that provides higher-level abstractions:
  • Plugins — C# functions the AI can call (function calling / tool use)
  • Planner — AI autonomously chains plugins to achieve a goal
  • Memory — built-in vector store abstractions for RAG
  • Multiple AI providers — swap between OpenAI, Azure OpenAI, Gemini via config
var kernel = Kernel.CreateBuilder()
    .AddAzureOpenAIChatCompletion(deploymentName, endpoint, apiKey)
    .Build();

kernel.ImportPluginFromType<OrderPlugin>();
var result = await kernel.InvokePromptAsync(
    "What's the status of my latest order?",
    new KernelArguments { ["userId"] = userId });
Use Semantic Kernel for agentic/multi-step flows; raw API calls for simple completions.
Q4How do you stream OpenAI responses to the client?▶
Use Server-Sent Events (SSE) from the API controller and the streaming API on the OpenAI client: 
// API controller
[HttpGet("chat/stream")]
public async Task Stream(string prompt, CancellationToken ct)
{
    Response.Headers["Content-Type"] = "text/event-stream";
    Response.Headers["Cache-Control"] = "no-cache";

    await foreach (var chunk in _openAiClient
        .GetChatClient("gpt-4o")
        .CompleteChatStreamingAsync(prompt)
        .WithCancellation(ct))
    {
        var text = chunk.ContentUpdate.FirstOrDefault()?.Text ?? "";
        if (!string.IsNullOrEmpty(text))
            await Response.WriteAsync($"data: {text}\n\n");
        await Response.Body.FlushAsync(ct);
    }
}

// React client
const es = new EventSource('/api/chat/stream?prompt=Hello');
es.onmessage = (e) => setResponse(prev => prev + e.data);
Q5How would you implement semantic search over a document corpus?▶
Ingestion pipeline (offline): 
foreach (var doc in documents)
{
    var chunks = ChunkText(doc.Content, maxTokens: 500, overlap: 50);
    foreach (var chunk in chunks)
    {
        var embedding = await _embeddings.GetEmbeddingAsync(chunk);
        await _vectorDb.UpsertAsync(new DocumentChunk
        {
            Id = Guid.NewGuid(),
            DocumentId = doc.Id,
            Text = chunk,
            Vector = embedding

    }
}
Search pipeline (online): 
var queryVector = await _embeddings.GetEmbeddingAsync(userQuery);
var results = await _vectorDb.SearchAsync(queryVector,
    filter: $"documentId eq '{docId}'", // optional filter
    topK: 5,
    minScore: 0.75f); // cosine similarity threshold

Q1How would you add caching to an API without breaking consistency?▶
Choose the cache strategy based on consistency requirements:

Cache-aside (lazy loading): 
public async Task<ProductDto> GetProductAsync(int id)
{
    var key = $"product:{id}";
    var cached = await _redis.GetStringAsync(key);
    if (cached != null) return JsonSerializer.Deserialize<ProductDto>(cached);

    var product = await _db.Products.FindAsync(id);
    var dto = _mapper.Map<ProductDto>(product);
    await _redis.SetStringAsync(key, JsonSerializer.Serialize(dto),
        new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5) });
    return dto;
}
Cache invalidation: On write, delete or update the cache entry. For complex scenarios, use cache tags or event-driven invalidation (domain event → invalidate cache).
Q2How do you diagnose a slow EF Core query in production?▶
Step 1 — Find it: Application Insights → Performance → slowest dependencies (SQL). Or enable slow query logging in SQL Server (Query Store).

Step 2 — Capture SQL: 
// Development — log all SQL
optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information)
              .EnableSensitiveDataLogging();

// Capture query string in code
var sql = query.ToQueryString();
Step 3 — Analyze in SSMS: Run with SET STATISTICS IO ON. Check execution plan. Look for:
  • Table scans → add index on filtered columns
  • Key lookups → use covering index (INCLUDE columns)
  • Large logical reads → consider projecting fewer columns or splitting query
  • Parameter sniffing → add OPTION(OPTIMIZE FOR UNKNOWN)
Q3What causes thread pool starvation in ASP.NET Core and how do you fix it?▶
Thread pool starvation occurs when all available threads are blocked (e.g. waiting for I/O synchronously), so incoming requests queue up and the server stops responding.

Root cause: Blocking async code with .Result or .Wait(), or using Task.Run() excessively to offload to the thread pool.

// BAD — blocks a thread while waiting
var result = GetDataAsync().Result;

// GOOD — thread is returned to pool while awaiting I/O
var result = await GetDataAsync();
Also avoid:
  • Long-running sync operations on request threads (use background services)
  • Excessive Task.Run() for CPU-bound work on web threads
  • Sync-over-async anti-pattern (calling async code from sync context with .GetAwaiter().GetResult())
Use Application Insights to detect thread pool exhaustion via "Requests in queue" metric.
Q4How do you implement retry and circuit breaker with Polly?▶ 
// Program.cs — HttpClient with Polly policies
builder.Services.AddHttpClient<IPaymentService, PaymentService>()
    .AddResilienceHandler("payment-pipeline", builder =>
    {
        // Retry: 3 times with exponential backoff
        builder.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            Delay = TimeSpan.FromSeconds(1),
            BackoffType = DelayBackoffType.Exponential,
            ShouldHandle = args => args.Outcome.Exception is HttpRequestException
        });

        // Circuit breaker: open after 5 failures in 30 seconds
        builder.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            SamplingDuration = TimeSpan.FromSeconds(30),
            MinimumThroughput = 5,
            BreakDuration = TimeSpan.FromSeconds(60)
        });

        // Timeout per attempt
        builder.AddTimeout(TimeSpan.FromSeconds(10));
    });
Circuit breaker prevents cascading failures — once the circuit opens, calls fail fast without hitting the failing service, giving it time to recover.
Q5Design a URL shortener — how do you scale it?▶
Requirements first: ~100M URLs, 10:1 read:write ratio, <100ms redirect latency, global availability.

Core design:
  • Shortcode generation: Base62 encode a unique ID (counter from DB or distributed ID like Snowflake). 7 characters = 62^7 ≈ 3.5 trillion URLs
  • Storage: SQL Server or Azure Cosmos DB — simple schema: (shortCode, longUrl, createdAt, expiresAt)
  • Redirect: Read shortcode → lookup → 301/302 redirect
Scaling reads (10:1 ratio):
  • Redis cache — cache hot shortcodes (LRU policy). 99% of redirects served from cache
  • CDN — for 301 (permanent) redirects, CDN caches at edge — zero origin hits
  • Read replicas — scale DB reads horizontally
Scaling writes: Partition by shortcode prefix. Rate limit per IP/API key using Redis sliding window.

Analytics: Async — publish redirect events to Service Bus, process with Azure Function, store in time-series DB.
💡 For system design: always state requirements first, then make tradeoff decisions explicit. "I chose Redis over in-memory cache because we'll have multiple instances" shows the right thinking — not just what, but why.
