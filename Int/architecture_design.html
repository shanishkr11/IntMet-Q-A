01

How would you structure a Clean Architecture project in .NET Core?

The core rule: Source code dependencies must point inward only. The Domain layer knows nothing about Infrastructure or the API. Infrastructure knows nothing about the API. This makes the business core framework-agnostic, database-agnostic, and fully testable.
Domain Layer — innermost
  • Entities, value objects, enums
  • Domain events
  • Repository interfaces (ITrailerRepository)
  • Domain service interfaces
  • Business rule validation logic
  • Zero NuGet dependencies
Application Layer
  • Use cases — Commands & Queries (MediatR)
  • DTOs, request/response models
  • Validators (FluentValidation)
  • Application service interfaces
  • Mapping profiles (AutoMapper)
  • Depends on: Domain only
Infrastructure Layer
  • EF Core DbContext & Configurations
  • Repository implementations
  • External service clients (email, SMS)
  • File storage, caching (Redis)
  • Identity, Azure AD integration
  • Depends on: Domain & Application
Presentation Layer — outermost
  • API Controllers (thin — delegate to MediatR)
  • Middleware pipeline setup
  • DI container registration
  • Program.cs, appsettings
  • Swagger configuration
  • Depends on: All layers

C# — Domain entity with encapsulated business rule 
// Domain/Entities/Trailer.cs
// Business rules live here — NOT in a service, NOT in a controller
public class Trailer
{
    private readonly List<Trip> _trips = [];

    public int           Id                   { get; private set; }
    public RegistrationNumber Registration    { get; private set; } = default!;
    public TrailerStatus Status               { get; private set; }
    public IReadOnlyList<Trip> Trips          => _trips.AsReadOnly();

    private List<IDomainEvent> _domainEvents = [];
    public IReadOnlyList<IDomainEvent> DomainEvents => _domainEvents.AsReadOnly();

    // Business rule: only available trailers can start a trip
    public Trip StartTrip(int driverId)
    {
        if (Status != TrailerStatus.Available)
            throw new DomainException($"Trailer {Id} is not available — status is {Status}");

        Status = TrailerStatus.InUse;
        var trip = new Trip(Id, driverId, DateTime.UtcNow);
        _trips.Add(trip);
        _domainEvents.Add(new TripStartedDomainEvent(Id, driverId));
        return trip;
    }

    public void EndTrip(int tripId)
    {
        var trip = _trips.SingleOrDefault(t => t.Id == tripId)
            ?? throw new DomainException("Trip not found on this trailer");
        trip.Complete();
        Status = TrailerStatus.Available;
    }
}

// Controller has ONE job: translate HTTP → command/query → HTTP response
[ApiController]
[Route("api/trailers")]
[Authorize]
public class TrailersController(ISender sender) : ControllerBase
{
    [HttpGet]
    public async Task<ActionResult<PagedResult<TrailerDto>>> GetTrailers(
        [FromQuery] GetTrailersQuery query)
        => Ok(await sender.Send(query));

    [HttpPost]
    public async Task<ActionResult<TrailerDto>> CreateTrailer(
        [FromBody] CreateTrailerCommand command)
    {
        var trailer = await sender.Send(command);
        return CreatedAtAction(nameof(GetTrailerById), new { id = trailer.Id }, trailer);
    }

    [HttpPost("{id}/trips/start")]
    public async Task<ActionResult<TripDto>> StartTrip(
        int id, [FromBody] StartTripCommand command)
        => Ok(await sender.Send(command with { TrailerId = id }));
}
// No business logic. No try/catch. No DB calls. Pure HTTP translation.
🎤 Interview Answer

"In the Trailer Management System we had four projects in the solution: Domain, Application, Infrastructure, and API. The csproj references enforced the dependency rule at compile time — Domain referenced nothing, Application referenced only Domain, Infrastructure referenced Domain and Application, and API referenced everything. If someone in Infrastructure accidentally tried to reference API, the build would fail. Business rules like 'a trailer must be Available before starting a trip' lived in the domain entity method, not in any service. This meant we could test that rule with a plain xUnit test — no database, no HTTP, no mocks needed."

Explain SOLID principles with examples from your actual projects.

Key interview tip: Every SOLID principle should be anchored to a specific problem it solved in a real project. Generic textbook definitions are forgettable — concrete violation examples followed by the fix are memorable.
S — Single Responsibility Principle

A class should have only one reason to change. If a class needs to change for two different business reasons, it has two responsibilities.

Violation in the Rule Engine: Our original RuleService handled CRUD operations, evaluated rules against data, sent email notifications on violations, and wrote audit logs. A change to the notification template required touching the same class as a change to rule evaluation logic.
C# — SRP fix: split into focused classes 
// ❌ Before — one class, four responsibilities
public class RuleService {
    public Rule  GetRule(int id)         { ... } // CRUD
    public bool  EvaluateRule(Rule rule)   { ... } // Evaluation logic
    public void  SendViolationEmail(...)   { ... } // Notification
    public void  WriteAuditLog(...)        { ... } // Audit
}

// ✓ After — each class has one job, one reason to change
public class RuleRepository     { /* CRUD only */ }
public class RuleEvaluator      { /* Evaluation logic only */ }
public class NotificationService { /* Sending alerts only */ }
public class AuditLogger        { /* Audit trail only */ }

// MediatR handler orchestrates them — no single class owns everything
public class EvaluateRuleCommandHandler(IRuleRepository repo,
    IRuleEvaluator evaluator, INotificationService notifier, IAuditLogger audit)
    : IRequestHandler<EvaluateRuleCommand, EvaluationResult>
{
    public async Task<EvaluationResult> Handle(EvaluateRuleCommand req, CancellationToken ct)
    {
        var rule   = await repo.GetByIdAsync(req.RuleId, ct);
        var result = evaluator.Evaluate(rule, req.Data);
        if (result.HasViolation) await notifier.SendViolationAlertAsync(rule, result);
        await audit.LogAsync(rule.Id, result);
        return result;
    }
}
O — Open/Closed Principle

Classes should be open for extension but closed for modification. Add new behavior by adding new code — not by editing existing, tested code.

C# — OCP: Strategy pattern for extensible rule evaluation 
// ❌ Violates OCP — adding a new rule type means editing this switch
public bool Evaluate(Rule rule, decimal value) => rule.Type switch
{
    "GreaterThan" => value > rule.Threshold,
    "LessThan"    => value < rule.Threshold,
    "Between"     => value >= rule.Min && value <= rule.Max,
    // Every new type requires editing this class — breaks OCP
    _ => throw new NotSupportedException(rule.Type)
};

// ✓ Satisfies OCP — add a new rule type by adding a new class, nothing changes
public interface IRuleEvaluationStrategy
{
    string RuleType  { get; }
    bool Evaluate(Rule rule, decimal value);
}

public class GreaterThanStrategy : IRuleEvaluationStrategy {
    public string RuleType => "GreaterThan";
    public bool   Evaluate(Rule r, decimal v) => v > r.Threshold;
}

public class BetweenStrategy : IRuleEvaluationStrategy {
    public string RuleType => "Between";
    public bool   Evaluate(Rule r, decimal v) => v >= r.Min && v <= r.Max;
}

// Evaluator resolves the correct strategy via DI — no switch needed
public class RuleEvaluator(IEnumerable<IRuleEvaluationStrategy> strategies)
{
    private readonly Dictionary<string, IRuleEvaluationStrategy> _map =
        strategies.ToDictionary(s => s.RuleType);

    public bool Evaluate(Rule rule, decimal value) =>
        _map.TryGetValue(rule.Type, out var strategy)
            ? strategy.Evaluate(rule, value)
            : throw new NotSupportedException(rule.Type);
}

03

How do you decide when to use a service layer vs. putting logic in the controller?

Hard rule: A controller is an HTTP adapter — it speaks HTTP in, and HTTP out. The moment logic inside a controller could be needed by another controller, a background job, a test, or a different transport (gRPC, CLI), it must move to a service or handler.
✓ Belongs in the Controller
  • Route definition and HTTP verb
  • Reading from query string, body, headers
  • Returning correct HTTP status codes
  • Calling ModelState.IsValid
  • Authorization attribute placement
  • Swagger documentation attributes
✗ Must NOT be in the Controller
  • Any business rule or decision
  • Database queries or EF Core calls
  • Cross-entity orchestration
  • Transaction management
  • Sending emails, notifications
  • Anything you would want to unit test
C# — Fat controller anti-pattern vs Clean Architecture controller 
// ❌ FAT CONTROLLER — untestable, violates SRP, cannot be reused
[HttpPost("start-trip")]
public async Task<IActionResult> StartTrip([FromBody] StartTripRequest request)
{
    var trailer = await _context.Trailers.FindAsync(request.TrailerId);
    if (trailer == null)        return NotFound();
    if (!trailer.IsAvailable)   return BadRequest("Trailer not available");

    trailer.Status = "InUse";
    var trip = new Trip { TrailerId = trailer.Id, DriverId = request.DriverId };
    _context.Trips.Add(trip);
    await _context.SaveChangesAsync();

    await _emailService.SendTripStartedEmailAsync(trailer, trip);
    await _auditService.LogAsync("TripStarted", trailer.Id);
    return Ok(trip);
    // Testing this requires mocking: DbContext, EmailService, AuditService — painful
}

// ✓ THIN CONTROLLER — HTTP translation only, all logic in the handler
[HttpPost("{id}/trips/start")]
public async Task<ActionResult<TripDto>> StartTrip(
    int id, [FromBody] StartTripCommand command, ISender sender)
    => Ok(await sender.Send(command with { TrailerId = id }));
// Testing the business rule: xUnit test → create handler → inject mocks → assert.
// No HTTP, no controller, no integration test needed for the logic.
The Decision Framework — Where does logic belong?
  • Domain layer: Invariants that must always be true regardless of how the operation is triggered — "a trailer must be Available to start a trip." Enforced in entity methods.
  • Application layer (Handler/Service): Use-case orchestration — fetch the aggregate, call the domain method, persist, dispatch events, send notifications. Testable with mocks.
  • Infrastructure layer: Technology-specific logic — how SQL Server stores the data, how Azure Blob stores the file. Not business logic.
  • Controller: HTTP concerns only. The test: "Would this logic matter if I called this use case from a background job?" If yes, move it out of the controller.
The other anti-pattern — anemic service: Moving all code from the controller into a giant TrailerService without proper layering just shifts the problem. If the service calls the repository, applies business rules, sends emails, and handles transactions all in one method, it is a fat controller in disguise. The application handler should orchestrate; the domain entity should enforce rules.
🎤 Interview Answer

"My test is simple: could this logic be needed from a background job, a different API endpoint, or a CLI tool? If yes, it does not belong in the controller. In the Trailer Management System, trip start logic was originally in the controller — 60 lines including DB access, status checks, email dispatch, and audit logging. A new requirement asked us to start trips automatically from a scheduler. We would have had to duplicate that controller code into a background service. Instead we extracted it into a MediatR command handler that both the controller and the scheduler could send. The controller dropped to one line."

C# — Repository + Unit of Work: coordinated persistence 
// Repository: abstracts data access — handlers depend on interface, not EF Core
// Problem it solved: switching from EF Core to Dapper for read queries
// without touching any application layer code
public interface ITrailerRepository
{
    Task<Trailer?>       GetByIdAsync(int id, CancellationToken ct);
    Task<List<Trailer>>  GetByBranchAsync(int branchId, CancellationToken ct);
    void                 Add(Trailer trailer);
    void                 Remove(Trailer trailer);
}

// Unit of Work: multiple repositories share one DbContext transaction
// Problem it solved: StartTrip needed to update Trailer + insert Trip atomically
public interface IUnitOfWork
{
    ITrailerRepository  Trailers  { get; }
    ITripRepository     Trips     { get; }
    IDriverRepository   Drivers   { get; }
    Task<int>            CommitAsync(CancellationToken ct);
}

// Handler uses UoW — one commit, one transaction, atomic
public class StartTripCommandHandler(IUnitOfWork uow)
    : IRequestHandler<StartTripCommand, TripDto>
{
    public async Task<TripDto> Handle(StartTripCommand req, CancellationToken ct)
    {
        var trailer = await uow.Trailers.GetByIdAsync(req.TrailerId, ct)
            ?? throw new NotFoundException(nameof(Trailer), req.TrailerId);

        var trip = trailer.StartTrip(req.DriverId);   // Domain method — throws if invalid
        uow.Trips.Add(trip);
        await uow.CommitAsync(ct);                     // Single SaveChanges — atomic
        return trip.ToDto();
    }
}
C# — Decorator pattern: transparent caching layer 
// Problem: GetActiveTrailers() was called 40 times per second on the dashboard
// Solution: Cache decorator wraps the real repository — callers never know
// Added zero code to handlers, zero code to the real repository
public class CachedTrailerRepository(ITrailerRepository inner, IMemoryCache cache)
    : ITrailerRepository
{
    private const string ActiveKey = "trailers:active";

    public async Task<List<Trailer>> GetActiveAsync(CancellationToken ct)
    {
        if (cache.TryGetValue(ActiveKey, out List<Trailer>? cached))
            return cached!;

        var trailers = await inner.GetActiveAsync(ct);   // Call real repository
        cache.Set(ActiveKey, trailers, TimeSpan.FromSeconds(30));
        return trailers;
    }

    // Write methods — invalidate cache then delegate to inner
    public void Add(Trailer t) { cache.Remove(ActiveKey); inner.Add(t); }
    public void Remove(Trailer t) { cache.Remove(ActiveKey); inner.Remove(t); }
}

// DI registration — swap in the decorator without touching any handler
services.AddScoped<EfTrailerRepository>();
services.AddScoped<ITrailerRepository>(sp =>
    new CachedTrailerRepository(
        sp.GetRequiredService<EfTrailerRepository>(),
        sp.GetRequiredService<IMemoryCache>()));
C# — MediatR Pipeline Behaviour (Decorator variant): cross-cutting concerns 
// Problem: every handler needed validation, logging, and performance monitoring
// Solution: MediatR pipeline behaviours — applied automatically to ALL handlers

// Validation behaviour — runs FluentValidation before any handler executes
public class ValidationBehaviour<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : IRequest<TResponse>
{
    public async Task<TResponse> Handle(TRequest request,
        RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var context = new ValidationContext<TRequest>(request);
        var failures = validators
            .Select(v => v.Validate(context))
            .SelectMany(r => r.Errors)
            .Where(f => f != null)
            .ToList();

        if (failures.Count > 0)
            throw new ValidationException(failures);

        return await next();   // Call the actual handler
    }
}

// Performance behaviour — logs a warning if any handler is slow
public class PerformanceBehaviour<TRequest, TResponse>(
    ILogger<PerformanceBehaviour<TRequest, TResponse>> logger)
    : IPipelineBehavior<TRequest, TResponse>
{
    public async Task<TResponse> Handle(TRequest request,
        RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var sw       = Stopwatch.StartNew();
        var response = await next();
        sw.Stop();

        if (sw.ElapsedMilliseconds > 500)
            logger.LogWarning("Slow request: {Request} took {Elapsed}ms",
                typeof(TRequest).Name, sw.ElapsedMilliseconds);

        return response;
    }
}

How do you approach structured logging? What tools did you use (Serilog, NLog)?

Structured vs plain text logging: Plain text logs are for humans to read in a terminal. Structured logs are machine-readable records where properties are first-class fields — queryable, filterable, and alertable in tools like Seq, Application Insights, and Elasticsearch.
❌ Plain Text — Unqueryable

"Trip started for trailer AB1234 by driver 42 at 2024-08-15 09:30:00"

  • Cannot filter by TrailerId in production
  • Cannot alert when TripCount exceeds threshold
  • Cannot correlate across microservices
  • Regex parsing is fragile and slow
✓ Structured — Queryable

{ "EventType": "TripStarted", "TrailerId": 5, "DriverId": 42, "CorrelationId": "abc-123", "Elapsed": 142 }

  • Filter: TrailerId = 5 AND Level = Error
  • Alert: Elapsed > 500ms
  • Correlate: CorrelationId = "abc-123" across all services
  • Aggregate: average elapsed time per endpoint

C# — Request logging middleware + correlation ID propagation 
// Attach CorrelationId to every request — ties together all logs for one HTTP call
public class CorrelationIdMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var correlationId = context.Request.Headers["X-Correlation-ID"]
            .FirstOrDefault() ?? Guid.NewGuid().ToString("N");

        context.Response.Headers["X-Correlation-ID"] = correlationId;

        using (LogContext.PushProperty("CorrelationId", correlationId))
        {
            await next(context);
        }
    }
}

// Serilog request logging — replaces verbose default ASP.NET Core request logs
// Produces one clean structured log per request with status, path, elapsed time
app.UseSerilogRequestLogging(options =>
{
    options.EnrichDiagnosticContext = (diagnosticContext, httpContext) =>
    {
        diagnosticContext.Set("UserId",      httpContext.User.GetUserId());
        diagnosticContext.Set("UserAgent",   httpContext.Request.Headers.UserAgent);
        diagnosticContext.Set("RequestHost", httpContext.Request.Host.Value);
    };
    options.MessageTemplate =
        "HTTP {RequestMethod} {RequestPath} responded {StatusCode} in {Elapsed:0.0000}ms";
});
Log Level Strategy — What to log at which level
  • Verbose / Trace: Fine-grained internal state — SQL query text, loop iterations. Dev only, never production.
  • Debug: Diagnostic information for troubleshooting a specific issue. Off in production by default, toggleable via appsettings without redeploy.
  • Information: Normal business operations — trip started, user logged in, report generated. High-value events that should always be logged.
  • Warning: Unexpected but handled situations — retry attempted, fallback activated, slow query threshold exceeded. Something to monitor.
  • Error: Operation failed, exception caught and handled. Requires investigation. Alert triggers here.
  • Fatal / Critical: Application cannot continue — database unreachable, unhandled exception in startup. PagerDuty-level alert.
appsettings.json log level control — no redeployment needed: Configure minimum levels per namespace in appsettings. Azure App Configuration or Azure Key Vault can update these at runtime, enabling you to temporarily enable Debug-level logging for a specific namespace in production to diagnose an issue, then revert — without restarting the application.

"We used Serilog in both the Trailer Management System and the Rule Engine. The biggest win was correlation IDs — every HTTP request got a CorrelationId either from the incoming header or generated fresh, pushed into Serilog's LogContext, and added to the response header. When a client reported 'the dashboard was slow at 9:15 AM', we searched Application Insights for that time range, grouped by CorrelationId, and saw exactly which 3 queries in one request were taking 3 seconds each. Without structured logging that would have taken hours. We also used Serilog's request logging middleware instead of the default ASP.NET Core logs — it produced one clean JSON record per request instead of 4 noisy text lines, which cut our Application Insights bill by 30%."
