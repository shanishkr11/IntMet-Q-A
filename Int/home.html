01

.NET Framework vs .NET Core — What's the difference and when to choose?

One-liner: Framework is Windows-only, legacy. Core is cross-platform, modern, and the future. For any new project — always choose .NET Core.
Aspect .NET Framework .NET Core / .NET 5+
Platform Windows only Cross-platform
Performance Lower Significantly higher (Kestrel, Span<T>)
Deployment GAC / IIS bound Self-contained, Docker-friendly
Open Source No Yes
Future Support Maintenance only Active development
🎤 How to say it in an interview

"In my projects, I've worked on both. We had a legacy monolith on .NET Framework 4.8 — tightly coupled to IIS and Windows services. When we started greenfield projects like the Trailer Management System, we chose .NET Core because we needed containerized deployment on Linux-based Azure App Services, better performance under load, and access to the modern middleware pipeline. Migration from Framework to Core is also something I've guided — the biggest pain points are HttpContext changes, removed APIs, and third-party library compatibility."

Decision Rule
  • Choose .NET Framework: Maintaining legacy systems, heavy WCF usage, or COM interop required.
  • Choose .NET Core: Anything new. Period.

How does the Middleware Pipeline work in ASP.NET Core?

Summary: Middleware is a chain of delegates — each one can short-circuit or pass control to the next via next(). Every middleware runs twice: once on request, once on response.
Request → ExceptionHandler → Authentication → Authorization → RateLimiting → Endpoint
Response ← ExceptionHandler ← Authentication ← Authorization ← RateLimiting ← Endpoint
Program.cs — Order matters critically 
// Order is NOT optional — a classic mistake junior devs make
app.UseExceptionHandler("/error");   // Must be first to catch all
app.UseHttpsRedirection();
app.UseAuthentication();             // Who are you?
app.UseAuthorization();              // What can you do?
app.UseRateLimiting();               // Custom middleware
app.MapControllers();
RequestLoggingMiddleware.cs — Real project example 
public class RequestLoggingMiddleware
{
                    private readonly RequestDelegate _next;
                    private readonly ILogger<RequestLoggingMiddleware> _logger;

                    public RequestLoggingMiddleware(RequestDelegate next,
                    ILogger<RequestLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

                    public async Task InvokeAsync(HttpContext context)
    {
                    var stopwatch = Stopwatch.StartNew();

        _logger.LogInformation("Incoming: {Method} {Path}",
            context.Request.Method, context.Request.Path);

                    await _next(context); // Pass to next middleware

        stopwatch.Stop();
        _logger.LogInformation("Completed: {StatusCode} in {ElapsedMs}ms",
            context.Response.StatusCode, stopwatch.ElapsedMilliseconds);
    }
}

// Extension method — clean registration pattern
public static class MiddlewareExtensions
{
                    public static IApplicationBuilder UseRequestLogging(
                    this IApplicationBuilder app)
        => app.UseMiddleware<RequestLoggingMiddleware>();
}
Key Interview Point: UseAuthentication() must always come before UseAuthorization() — this ordering mistake is one of the most common junior errors.

How did you implement JWT Authentication in the Trailer Management System?

Summary: JWT is a self-contained, stateless token with three parts: Header, Payload (Claims), Signature. No database lookup needed per request.
Key Components
  • Issuer (iss): Who created the token — your auth server (e.g., https://trailerapi.domain.com)
  • Audience (aud): Who the token is intended for — your consuming API
  • Claims: Business data embedded in payload — userId, role, branchId
  • Expiry (exp): Short-lived (15–60 min) + Refresh Token for renewal
  • ClockSkew: Set to TimeSpan.Zero — removes the default 5-minute drift allowance
JwtTokenService.cs — Token generation 
public class JwtTokenService : IJwtTokenService
{
                    private readonly JwtSettings _settings;

                    public string GenerateToken(ApplicationUser user, IList<string> roles)
    {
                    var claims = new List<Claim>
        {
                    new(JwtRegisteredClaimNames.Sub, user.Id),
                    new(JwtRegisteredClaimNames.Email, user.Email),
                    new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
                    new("branchId", user.BranchId.ToString()), // Custom business claim
        };

                    // Embed roles as claims
        claims.AddRange(roles.Select(r => new Claim(ClaimTypes.Role, r)));

                    var key = new SymmetricSecurityKey(
                    Encoding.UTF8.GetBytes(_settings.SecretKey));
                    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

                    var token = new JwtSecurityToken(
            issuer: _settings.Issuer,
            audience: _settings.Audience,
            claims: claims,
            expires: DateTime.UtcNow.AddMinutes(_settings.ExpiryMinutes),
            signingCredentials: creds
        );

                    return new JwtSecurityTokenHandler().WriteToken(token);
    }
}
Program.cs — JWT registration 
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = jwtSettings.Issuer,
            ValidAudience = jwtSettings.Audience,
            IssuerSigningKey = new SymmetricSecurityKey(
                    Encoding.UTF8.GetBytes(jwtSettings.SecretKey)),
            ClockSkew = TimeSpan.Zero // Don't allow 5-min default drift
        };
    });

Authentication vs Authorization — How did you handle RBAC in the Rule Engine?

Authentication

"Who are you?" — Verifies identity via JWT, cookies, API keys, etc. Runs first in the pipeline.

Authorization

"What can you do?" — Enforces permissions after identity is confirmed. Role-based, policy-based, or claim-based.

Policy-based RBAC — Rule Engine Application 
// Roles: Admin, RuleManager, Viewer
// Policy-based is more maintainable than [Authorize(Roles="...")] strings
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanManageRules", policy =>
        policy.RequireRole("Admin", "RuleManager"));

    options.AddPolicy("CanViewReports", policy =>
        policy.RequireAuthenticatedUser()
              .RequireClaim("branchId")); // Must have branch assignment
});

// Controller usage
[Authorize(Policy = "CanManageRules")]
[HttpPost("rules")]
public async Task<IActionResult> CreateRule([FromBody] CreateRuleRequest request)
{ ... }
Custom Authorization Handler — Fine-grained branch access control 
public class BranchAccessRequirement : IAuthorizationRequirement { }

public class BranchAccessHandler
    : AuthorizationHandler<BranchAccessRequirement>
{
                    protected override Task HandleRequirementAsync(
                    AuthorizationHandlerContext context,
                    BranchAccessRequirement requirement)
    {
                    var branchClaim = context.User.FindFirst("branchId");
                    if (branchClaim != null)
            context.Succeed(requirement);

                    return Task.CompletedTask;
    }
}
Why policy-based over role strings? Role strings hardcoded in attributes are brittle. Policies are testable, centrally defined, and business-meaningful — changing a policy definition in one place updates all endpoints automatically.

Global Exception Handling — Middleware vs. Filters

Rule of thumb: Use middleware for global/unhandled exceptions. Use filters only for controller-scoped, action-level overrides.
Aspect Middleware Exception Filter
Scope Entire pipeline Controllers/Actions only
Catches routing errors ✓ Yes ✗ No
Access to HttpContext Full access Yes
Best for Global handler (preferred) Domain-specific overrides
GlobalExceptionMiddleware.cs 
public class GlobalExceptionMiddleware
{
                    private readonly RequestDelegate _next;
                    private readonly ILogger<GlobalExceptionMiddleware> _logger;

                    public GlobalExceptionMiddleware(RequestDelegate next,
                    ILogger<GlobalExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

                    public async Task InvokeAsync(HttpContext context)
    {
                    try
        {
                    await _next(context);
        }
                    catch (Exception ex)
        {
            _logger.LogError(ex, "Unhandled exception for {Path}",
                context.Request.Path);
                    await HandleExceptionAsync(context, ex);
        }
    }

                    private static async Task HandleExceptionAsync(
                    HttpContext context, Exception ex)
    {
                    var (statusCode, message) = ex switch
        {
                    NotFoundException e    => (404, e.Message),
                    ValidationException e  => (400, e.Message),
                    UnauthorizedAccessException => (401, "Unauthorized"),
            _                      => (500, "An unexpected error occurred")
        };

        context.Response.ContentType = "application/json";
        context.Response.StatusCode = statusCode;

                    var response = new {
            error = message,
            traceId = context.TraceIdentifier
        };
                    await context.Response.WriteAsJsonAsync(response);
    }
}
Why custom middleware over built-in UseExceptionHandler? Full control over response shape, logging correlation IDs, and mapping domain exceptions to HTTP status codes cleanly — without redirecting to an error controller.

IActionResult vs ActionResult<T> — What's the difference?

Prefer ActionResult<T> — it's type-safe and enables automatic Swagger/OpenAPI schema generation. No need for [ProducesResponseType] decoration for the success case.
❌ IActionResult — Avoid
// No compile-time type info
// Swagger can't infer response schema
[HttpGet("{id}")]
public IActionResult GetTrailer(int id)
{
                            var trailer = _service.GetById(id);
                            if (trailer == null) return NotFound();
                            return Ok(trailer); // Swagger doesn't know type
}
✓ ActionResult<T> — Preferred
// Type-safe, Swagger schema auto-generated
// Implicit cast from T → 200 OK
[HttpGet("{id}")]
public async Task<ActionResult<TrailerDto>> GetTrailer(int id)
{
                            var trailer = await _service.GetByIdAsync(id);
                            if (trailer == null) return NotFound();
                            return trailer; // Implicit Ok(trailer)
}
Key Benefits of ActionResult<T>
  • Return T directly — it implicitly wraps in 200 OK
  • Swagger generates the correct $ref schema for TrailerDto automatically
  • Compile-time safety — the compiler knows the return type
  • Use IActionResult only when one action legitimately returns multiple different types — rare in practice

How do you version your APIs? What strategies have you used?

Summary: We used URL segment versioning as primary, with header versioning awareness. Both are supported simultaneously via ApiVersionReader.Combine().
Strategy Example Pros Cons
URL Segment /api/v1/trailers Explicit, cacheable, easy to test URL changes
Query String ?api-version=1.0 Backward compatible Clutters URLs
Header api-version: 1.0 Clean URLs Harder to test in browser
Program.cs — Versioning registration 
// Install: Microsoft.AspNetCore.Mvc.Versioning
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true; // Adds api-supported-versions header
    options.ApiVersionReader = ApiVersionReader.Combine(
                    new UrlSegmentApiVersionReader(),
                    new HeaderApiVersionReader("api-version") // Support both
    );
});
Controllers — V1 and V2 side by side 
[ApiController]
[Route("api/v{version:apiVersion}/trailers")]
[ApiVersion("1.0")]
public class TrailersV1Controller : ControllerBase { ... }

[ApiController]
[Route("api/v{version:apiVersion}/trailers")]
[ApiVersion("2.0")]
[ApiVersion("1.0", Deprecated = true)]
public class TrailersV2Controller : ControllerBase
{
                    // V2 adds pagination, new filter fields, richer response schema
}
🎤 Real Decision Rationale

"We chose URL segment versioning on the Trailer Management System because the API was consumed by a React frontend and a mobile app. URL-based versions are explicit in logs, easy to route in API Gateway (Azure APIM), and require zero client header configuration. We deprecated V1 with a 6-month sunset period, using the Deprecated attribute and a response header warning."

Senior tip: Always deprecate — never delete immediately. Use [ApiVersion("1.0", Deprecated = true)] and communicate the sunset date in response headers so consumers have time to migrate.
