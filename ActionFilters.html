02 — Middleware vs filters

The most important distinction. Middleware operates on raw HttpContext — it has no knowledge of controllers, actions, or model binding. Filters live inside the MVC endpoint and have full action-aware context.

Middleware

Sees only HttpContext. Applies to all requests, including static files. Ideal for global concerns like CORS, compression, rate-limiting. Has no concept of action metadata.

Filters

Operate inside the MVC endpoint. Have access to ActionDescriptor, ModelState, and ActionArguments. Only run for controller actions — not for static files or other middleware-handled requests.

03 — Execution (wrapping model)

Filters don't run sequentially — they wrap each other. Each filter gets a before and after hook, forming a Russian-doll nesting pattern.

Filter execution order — entering and exiting
→ AuthorizationFilter.OnAuthorization()
  → ResourceFilter.OnResourceExecuting()
      [Model Binding]
    → ActionFilter.OnActionExecuting()
        [Action Method executes]
    ← ActionFilter.OnActionExecuted()
    ← ExceptionFilter ← only if exception was thrown
  ← ResourceFilter.OnResourceExecuted()
  → ResultFilter.OnResultExecuting()
      [IActionResult.ExecuteResultAsync()]
  ← ResultFilter.OnResultExecuted()
04 — Short-circuiting

Any filter can stop the pipeline by assigning context.Result without calling next(). Already-executed filters still run their OnXxxExecuted hooks on the way out.

AuthorizationFilter.cs
C#
public class RequireApiKeyFilter : IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationFilterContext context)
    {
        var hasKey = context.HttpContext.Request.Headers
            .TryGetValue("X-Api-Key", out var key);

        if (!hasKey || key != "expected-secret")
        {
            // Short-circuit — action method never runs
            context.Result = new UnauthorizedObjectResult(new
            {
                error = "Invalid or missing API key"
            });
        }
    }
}
ActionFilter.cs
C#
public class ValidateModelFilter : IActionFilter
{
    // Runs before the action — model is already bound
    public void OnActionExecuting(ActionExecutingContext context)
    {
        if (!context.ModelState.IsValid)
        {
            context.Result = new UnprocessableEntityObjectResult(
                context.ModelState
            );
        }
    }

    // Runs after the action — can inspect the result
    public void OnActionExecuted(ActionExecutedContext context)
    {
        // e.g. log execution time, enrich the result
    }
}
05 — When to use filter vs middleware
Use case Filter Middleware
Needs ModelState or action arguments ✓ Filter ✗ No access
Needs ActionDescriptor / route data ✓ Filter ~ Partial
Applies to all requests (incl. static files) ✗ MVC only ✓ Middleware
Response caching at the action level ✓ Resource filter ✗ No action context
Global exception handling (incl. middleware errors) ✗ Action scope only ✓ Middleware
Logging / timing around the action only ✓ Action filter ✗ Too broad
Response header manipulation ✓ Result filter ✓ Middleware
06 — Exception filter scope
⚠
Exception filters do NOT catch everything

Exception filters only handle exceptions thrown within the action method or action filters. They do not catch exceptions from middleware, result filters, or IActionResult.ExecuteResultAsync(). Use UseExceptionHandler() middleware as the global safety net.

07 — Filter scope and execution order

Filters can be registered at three levels. Global wraps controller, which wraps action-scoped. Within the same scope, use IOrderedFilter.Order (lower = outer).
