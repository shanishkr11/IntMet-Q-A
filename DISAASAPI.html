Service Lifetimes with E-Commerce Examples
DI-01 Explain the three DI lifetimes with real e-commerce service examples and the captive dependency problem. Senior
✦ Answer

In an e-commerce platform, choosing the wrong lifetime causes either data leaks between requests (Singleton used wrongly) or performance waste (Transient for heavy services).

C# · Program.cs
// ─── SINGLETON: one instance for app lifetime ───────────────────────────────
// ✅ Use for: stateless, thread-safe, expensive-to-create services
builder.Services.AddSingleton<ICurrencyConverter, ExchangeRateCurrencyConverter>();
builder.Services.AddSingleton<IProductCatalogCache, InMemoryProductCatalogCache>();
builder.Services.AddSingleton<IPricingEngine, RuleBasedPricingEngine>();

// ─── SCOPED: one instance per HTTP request ──────────────────────────────────
// ✅ Use for: DbContext, repositories, cart/order services, unit of work
builder.Services.AddScoped<ECommerceDbContext>();
builder.Services.AddScoped<IShoppingCartService, ShoppingCartService>();
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<IUnitOfWork, EfUnitOfWork>();

// ─── TRANSIENT: new instance every injection ────────────────────────────────
// ✅ Use for: lightweight, stateless, short-lived operations
builder.Services.AddTransient<IOrderEmailService, SmtpOrderEmailService>();
builder.Services.AddTransient<IInvoiceGenerator, PdfInvoiceGenerator>();
builder.Services.AddTransient<IStockNotifier, LowStockNotifier>();

Captive Dependency — the most common senior mistake:

C# · Captive Dependency Bug
// ❌ BUG: Singleton holds a reference to Scoped service
//    ShoppingCartService is Scoped (per-request),
//    but ProductRecommendationEngine is Singleton.
//    Result: same ShoppingCartService instance shared across ALL requests!
public class ProductRecommendationEngine  // Singleton
{
    private readonly IShoppingCartService _cart; // Scoped — CAPTURED FOREVER
    public ProductRecommendationEngine(IShoppingCartService cart) => _cart = cart;
}

// ✅ FIX 1: Inject IServiceScopeFactory and resolve per-use
public class ProductRecommendationEngine
{
    private readonly IServiceScopeFactory _scopeFactory;
    public ProductRecommendationEngine(IServiceScopeFactory scopeFactory)
        => _scopeFactory = scopeFactory;

    public async Task<IEnumerable<Product>> GetRecommendationsAsync(string userId)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var cart = scope.ServiceProvider.GetRequiredService<IShoppingCartService>();
        return await cart.GetRecommendationsAsync(userId);
    }
}

// ✅ FIX 2: Make both Singleton (if service can be stateless)
// ✅ FIX 3: ASP.NET Core validates scope violations in Development:
builder.Services.Configure<ServiceProviderOptions>(o =>
{
    o.ValidateScopes = true;   // catch captive deps at startup
    o.ValidateOnBuild = true;  // fail fast — don't wait for first request
});

Payment Gateway — Factory & Strategy with DI
DI-03 How would you design a pluggable payment gateway system (Stripe, PayPal, COD) using DI and the Strategy pattern? Senior / Arch
✦ Answer

This combines DI + Strategy + Factory patterns. New payment methods are added by implementing one interface and registering — zero changes to existing code (Open/Closed).

C# · Domain Contracts
// Domain contracts (Application layer)
public interface IPaymentGateway
{
    string ProviderKey { get; }   // "stripe" | "paypal" | "cod"
    Task<PaymentResult> ChargeAsync(PaymentRequest request, CancellationToken ct);
    Task<RefundResult>  RefundAsync(string transactionId, decimal amount, CancellationToken ct);
}

public record PaymentRequest(decimal Amount, string Currency, string CustomerId, string OrderId);
public record PaymentResult(bool Success, string TransactionId, string? Error);

// Concrete implementations (Infrastructure layer)
public class StripePaymentGateway : IPaymentGateway
{
    public string ProviderKey => "stripe";
    private readonly StripeOptions _opts;
    public StripePaymentGateway(IOptions<StripeOptions> opts) => _opts = opts.Value;

    public async Task<PaymentResult> ChargeAsync(PaymentRequest req, CancellationToken ct)
    {
        // Stripe SDK call here
        var charge = await new ChargeService().CreateAsync(new ChargeCreateOptions
        {
            Amount   = (long)(req.Amount * 100),
            Currency = req.Currency,
            Customer = req.CustomerId,
        }, cancellationToken: ct);
        return new PaymentResult(charge.Status == "succeeded", charge.Id, null);
    }
    public async Task<RefundResult> RefundAsync(string txId, decimal amt, CancellationToken ct) { /*...*/ }
}

public class PayPalPaymentGateway : IPaymentGateway  { public string ProviderKey => "paypal"; /*...*/ }
public class CashOnDeliveryGateway : IPaymentGateway { public string ProviderKey => "cod";    /*...*/ }
C# · Factory & Registration
// Factory resolves correct gateway at runtime
public interface IPaymentGatewayFactory
{
    IPaymentGateway GetGateway(string providerKey);
}

public class PaymentGatewayFactory : IPaymentGatewayFactory
{
    private readonly IReadOnlyDictionary<string, IPaymentGateway> _gateways;

    public PaymentGatewayFactory(IEnumerable<IPaymentGateway> gateways)
        => _gateways = gateways.ToDictionary(g => g.ProviderKey);

    public IPaymentGateway GetGateway(string providerKey)
        => _gateways.TryGetValue(providerKey, out var gw)
            ? gw
            : throw new NotSupportedException($"Payment provider '{providerKey}' not registered.");
}

// Registration — add a new gateway = one line. Zero other changes.
builder.Services.AddScoped<IPaymentGateway, StripePaymentGateway>();
builder.Services.AddScoped<IPaymentGateway, PayPalPaymentGateway>();
builder.Services.AddScoped<IPaymentGateway, CashOnDeliveryGateway>();
builder.Services.AddScoped<IPaymentGatewayFactory, PaymentGatewayFactory>();

// OrderService consumes the factory
public class OrderPaymentService
{
    private readonly IPaymentGatewayFactory _factory;
    public OrderPaymentService(IPaymentGatewayFactory factory) => _factory = factory;

    public async Task<PaymentResult> ProcessAsync(Order order, CancellationToken ct)
    {
        var gateway = _factory.GetGateway(order.PaymentProvider); // "stripe"/"paypal"/"cod"
        return await gateway.ChargeAsync(new PaymentRequest(
            order.Total, "USD", order.CustomerId, order.Id.ToString()), ct);
    }
}
Decorator Pattern & DI Testing
DI-04 How do you layer caching on a ProductRepository using Decorator without touching the original class? How do you unit test DI-wired services? Senior
✦ Answer
C# · Decorator — Caching Product Repository
public interface IProductRepository
{
    Task<Product?> GetByIdAsync(Guid productId, CancellationToken ct);
    Task<IReadOnlyList<Product>> GetByCategoryAsync(string category, CancellationToken ct);
}

// Base EF implementation
public class EfProductRepository : IProductRepository
{
    private readonly ECommerceDbContext _ctx;
    public EfProductRepository(ECommerceDbContext ctx) => _ctx = ctx;

    public Task<Product?> GetByIdAsync(Guid id, CancellationToken ct)
        => _ctx.Products.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id, ct);

    public Task<IReadOnlyList<Product>> GetByCategoryAsync(string cat, CancellationToken ct)
        => _ctx.Products.Where(p => p.Category == cat).AsNoTracking()
               .ToListAsync(ct).ContinueWith(t => (IReadOnlyList<Product>)t.Result);
}

// Decorator adds Redis caching — EfProductRepository is UNTOUCHED
public class CachedProductRepository : IProductRepository
{
    private readonly IProductRepository    _inner;
    private readonly IDistributedCache       _cache;
    private readonly ILogger<CachedProductRepository> _logger;
    private static readonly TimeSpan _ttl = TimeSpan.FromMinutes(10);

    public CachedProductRepository(
        IProductRepository inner,
        IDistributedCache cache,
        ILogger<CachedProductRepository> logger)
        => (_inner, _cache, _logger) = (inner, cache, logger);

    public async Task<Product?> GetByIdAsync(Guid id, CancellationToken ct)
    {
        var key  = $"product:{id}";
        var json = await _cache.GetStringAsync(key, ct);

        if (json is not null)
            return JsonSerializer.Deserialize<Product>(json);

        var product = await _inner.GetByIdAsync(id, ct);
        if (product is not null)
            await _cache.SetStringAsync(key, JsonSerializer.Serialize(product),
                new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = _ttl }, ct);

        return product;
    }

    public Task<IReadOnlyList<Product>> GetByCategoryAsync(string cat, CancellationToken ct)
        => _inner.GetByCategoryAsync(cat, ct); // delegate — category lists cached at API layer
}

// Registration — ONE line wraps EF with cache (Scrutor library)
// Install: dotnet add package Scrutor
builder.Services.AddScoped<IProductRepository, EfProductRepository>();
builder.Services.Decorate<IProductRepository, CachedProductRepository>();

S — Single Responsibility Principle
SRP How does SRP apply to order processing in an e-commerce API? Show the before/after split. Senior
✦ Answer

SRP means each class has exactly one reason to change. An "OrderService" that validates, persists, emails, and generates invoices has four reasons to change.

C# · ❌ Before — God Class
// ❌ OrderService has 5+ responsibilities — every business change touches this class
public class OrderService
{
    public async Task PlaceOrderAsync(CreateOrderDto dto)
    {
        // 1. Validates the order (validation logic)
        if (dto.Items.Count == 0) throw new Exception("No items");

        // 2. Applies discounts (pricing logic)
        var total = dto.Items.Sum(i => i.Price * i.Qty) * 0.9m;

        // 3. Saves to DB (persistence logic)
        _ctx.Orders.Add(new Order { Total = total });
        await _ctx.SaveChangesAsync();

        // 4. Sends confirmation email (communication logic)
        await _smtp.SendAsync(dto.CustomerEmail, "Order confirmed");

        // 5. Generates invoice PDF (document logic)
        var pdf = GenerateInvoice(total);
    }
}
C# · ✅ After — Each Class Has One Job
// Each class has ONE reason to change
public class OrderValidator          // changes only when validation rules change
{
    public ValidationResult Validate(CreateOrderDto dto)
    {
        var errors = new List<string>();
        if (!dto.Items.Any())             errors.Add("Cart is empty");
        if (dto.ShippingAddress is null)  errors.Add("Shipping address required");
        return new ValidationResult(errors);
    }
}

public class OrderPricingCalculator  // changes only when pricing/discount rules change
{

    public OrderPricingCalculator(IDiscountStrategy discount) => _discount = discount;
    public PricingSummary Calculate(IEnumerable<OrderItem> items) =>
        _discount.Apply(items.Sum(i => i.UnitPrice * i.Quantity));
}

public class OrderRepository        // changes only when persistence layer changes
{
    private readonly ECommerceDbContext _ctx;
    public async Task<Order> SaveAsync(Order order, CancellationToken ct)
    {
        _ctx.Orders.Add(order);
        await _ctx.SaveChangesAsync(ct);
        return order;
    }
}

public class OrderEmailNotifier     // changes only when email templates/SMTP changes
{
    public Task SendConfirmationAsync(Order o, CancellationToken ct) => /*...*/;
}

public class InvoiceGenerator       // changes only when invoice format changes
{
    public Task<byte[]> GeneratePdfAsync(Order order, CancellationToken ct) => /*...*/;
}

// Orchestrator (Application Use Case) — only reason to change: business flow changes
public class PlaceOrderCommandHandler : IRequestHandler<PlaceOrderCommand, OrderDto>

O — Open/Closed Principle
OCP How do you add new discount types (seasonal, loyalty, coupon) without modifying existing code? Senior
✦ Answer

OCP: open for extension, closed for modification. Use the Strategy pattern. Each new discount = one new class. Zero changes to OrderPricingCalculator or any existing code.

C# · Discount Strategy with Pipeline
// Contract — never changes
public interface IDiscountStrategy
{
    int Priority { get; }   // lower = applied first
    bool IsApplicable(Cart cart);
    decimal Apply(decimal subtotal, Cart cart);
}

// Strategy 1: Loyalty discount (10% for Gold/Platinum members)
public class LoyaltyDiscountStrategy : IDiscountStrategy
{
    public int Priority => 1;
    public bool IsApplicable(Cart cart) => cart.CustomerTier is Tier.Gold or Tier.Platinum;
    public decimal Apply(decimal subtotal, Cart cart)
        => subtotal * (cart.CustomerTier == Tier.Platinum ? 0.85m : 0.90m);
}

// Strategy 2: Seasonal discount (20% sale events)
public class SeasonalDiscountStrategy : IDiscountStrategy
{
    private readonly ISeasonalSaleService _sale;
    public int Priority => 2;
    public bool IsApplicable(Cart cart) => _sale.IsActiveSale();
    public decimal Apply(decimal subtotal, Cart cart) => subtotal * _sale.DiscountFactor;
}

// Strategy 3: Coupon code discount
public class CouponDiscountStrategy : IDiscountStrategy
{
    private readonly ICouponRepository _coupons;
    public int Priority => 3;
    public bool IsApplicable(Cart cart) => !string.IsNullOrEmpty(cart.CouponCode);
    public decimal Apply(decimal subtotal, Cart cart)
    {
        var coupon = _coupons.GetValid(cart.CouponCode);
        return coupon?.Type == CouponType.Percentage
            ? subtotal * (1 - coupon.Value / 100)
            : Math.Max(0, subtotal - (coupon?.Value ?? 0));
    }
}

// Pipeline applies all applicable strategies in priority order
public class DiscountPipeline
{
    private readonly IEnumerable<IDiscountStrategy> _strategies;
    public DiscountPipeline(IEnumerable<IDiscountStrategy> strategies) => _strategies = strategies;

    public decimal Calculate(decimal subtotal, Cart cart)
        => _strategies
            .Where(s => s.IsApplicable(cart))
            .OrderBy(s => s.Priority)
            .Aggregate(subtotal, (price, strategy) => strategy.Apply(price, cart));
}

// Registration — add BulkDiscount in future = just this line
builder.Services.AddScoped<IDiscountStrategy, LoyaltyDiscountStrategy>();
builder.Services.AddScoped<IDiscountStrategy, SeasonalDiscountStrategy>();
builder.Services.AddScoped<IDiscountStrategy, CouponDiscountStrategy>();
builder.Services.AddScoped<DiscountPipeline>(); // DI injects all IDiscountStrategy instances
L — Liskov Substitution Principle
LSP How do you ensure Stripe, PayPal and COD are truly interchangeable without breaking LSP? What's an LSP violation in e-commerce? Senior
✦ Answer

LSP: any implementation should be substitutable for its base type without altering program correctness. Violations occur when a subtype throws where the base doesn't, ignores parameters, or changes the semantics of a method.

C# · LSP Violation vs Correct Design
// ❌ LSP VIOLATION — COD gateway throws on Refund (not in base contract)
public class CashOnDeliveryGateway : IPaymentGateway
{
    public Task<RefundResult> RefundAsync(string txId, decimal amt, CancellationToken ct)
        => throw new NotSupportedException("COD does not support refunds!");
        // Consumer code breaks when this gateway is injected
}

// ✅ FIX 1: Segregate refundable capability into separate interface
public interface IPaymentGateway
{
    string ProviderKey { get; }
    Task<PaymentResult> ChargeAsync(PaymentRequest req, CancellationToken ct);
}

public interface IRefundablePaymentGateway : IPaymentGateway   // ISP + LSP
{
    Task<RefundResult> RefundAsync(string transactionId, decimal amount, CancellationToken ct);
}

// Stripe and PayPal implement the full contract
public class StripePaymentGateway : IRefundablePaymentGateway
{
    public string ProviderKey => "stripe";
    public Task<PaymentResult> ChargeAsync(PaymentRequest req, CancellationToken ct) => /*...*/;
    public Task<RefundResult>  RefundAsync(string txId, decimal amt, CancellationToken ct) => /*...*/;
}

// COD only implements the base — no refund capability, no violation
public class CashOnDeliveryGateway : IPaymentGateway
{
    public string ProviderKey => "cod";
    public Task<PaymentResult> ChargeAsync(PaymentRequest req, CancellationToken ct)
        => Task.FromResult(new PaymentResult(true, $"COD-{req.OrderId}", null));
        // No exception — always succeeds as per COD semantics
}

// Refund service safely checks capability at runtime
public class RefundService
{
    public async Task<RefundResult> IssueRefundAsync(Order order, CancellationToken ct)
    {
        var gateway = _factory.GetGateway(order.PaymentProvider);
        if (gateway is not IRefundablePaymentGateway refundable)
            return RefundResult.NotSupported("Manual refund required for this payment method");

        return await refundable.RefundAsync(order.TransactionId, order.Total, ct);
    }
}

D — Dependency Inversion Principle
DIP Show the complete DIP flow in an e-commerce checkout — from controller to database — with Clean Architecture layers. Senior / Arch
✦ Answer

DIP: high-level modules (business logic) should not depend on low-level modules (database, email). Both depend on abstractions. The Application layer defines interfaces; Infrastructure implements them.

┌─────────────────────────────────────────────────────────────────┐
│  PRESENTATION                                                    │
│  CheckoutController  ──►  PlaceOrderCommand (MediatR)           │
└────────────────────────────┬────────────────────────────────────┘
                             │  depends on
┌────────────────────────────▼────────────────────────────────────┐
│  APPLICATION  (owns the interfaces — dependency flows IN)        │
│  PlaceOrderCommandHandler                                        │
│  ├── IOrderRepository     (interface defined HERE)              │
│  ├── IPaymentGateway      (interface defined HERE)              │
│  └── IOrderEmailService   (interface defined HERE)              │
└────────────────────────────┬────────────────────────────────────┘
                             │  implemented by
┌────────────────────────────▼────────────────────────────────────┐
│  INFRASTRUCTURE  (depends on Application, not the other way)    │
│  EfOrderRepository  implements  IOrderRepository                │
│  StripeGateway      implements  IPaymentGateway                 │
│  SmtpEmailService   implements  IOrderEmailService              │
└─────────────────────────────────────────────────────────────────┘
  Rule: Application project has ZERO reference to Infrastructure
C# · Full Checkout Flow with DIP
// ── APPLICATION LAYER ─────────────────────────────────────────────────────

public interface IOrderRepository
{

    Task<Order?> GetByIdAsync(Guid id, CancellationToken ct);
}

public interface IEmailService   { Task SendOrderConfirmationAsync(Order o, CancellationToken ct); }

// Use case — 100% unit-testable, no DB/network
public class PlaceOrderCommandHandler : IRequestHandler<PlaceOrderCommand, Guid>
{

public class ValidationBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;

    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var ctx = new ValidationContext<TRequest>(request);
        var failures = _validators
            .Select(v => v.Validate(ctx))
            .SelectMany(r => r.Errors)
            .Where(f => f != null).ToList();

        if (failures.Count != 0) throw new ValidationException(failures);
        return await next();
    }
}

public class LoggingBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
{

    {
        _logger.LogInformation("Handling {Name}: {@Request}", typeof(TRequest).Name, request);
        var sw = Stopwatch.StartNew();
        var result = await next();
        _logger.LogInformation("Handled {Name} in {Elapsed}ms", typeof(TRequest).Name, sw.ElapsedMilliseconds());
        return result;
    }
}

    {

        query = query.Where(o => o.CreatedAt < cursorOrder!.CreatedAt
                              || (o.CreatedAt == cursorOrder.CreatedAt && o.Id > cursor.Value));

        .Select(o => new OrderDto(o.Id, o.Total, o.Status, o.CreatedAt))

    return new CursorPage<OrderDto>(pageItems, nextCursor, hasMore);

        }
    }

State Machine — What the Compiler Generates
ASYNC-01 What does the compiler actually generate when you write async/await? Explain the state machine, MoveNext, and how continuations work. Senior / Principal
✦ Answer

The compiler transforms every async method into a struct implementing IAsyncStateMachine. Each await point becomes a state number. MoveNext() is the actual method body — it's called once per state transition.

  Your code:
  async Task<Order> GetOrderAsync(int id) {
      var order  = await _repo.GetByIdAsync(id);   // state 0 → 1
      var items  = await _items.GetAsync(order.Id); // state 1 → 2
      return order;                                 // state 2 = done
  }

  What compiler generates (simplified):
  struct GetOrderAsyncStateMachine : IAsyncStateMachine {
      int _state = -1;   // -1 = not started
      Order _order;
      TaskAwaiter<Order> _awaiter0;
      TaskAwaiter<List<Item>> _awaiter1;

      void MoveNext() {
          switch (_state) {
              case -1:  // first call
                  _awaiter0 = _repo.GetByIdAsync(id).GetAwaiter();
                  if (!_awaiter0.IsCompleted) {
                      _state = 0;
                      _awaiter0.OnCompleted(MoveNext); // register continuation
                      return;                          // ← THREAD RELEASED HERE
                  }
                  goto case 0;

              case 0:   // resumed after GetByIdAsync completed
                  _order = _awaiter0.GetResult();
                  _awaiter1 = _items.GetAsync(_order.Id).GetAwaiter();
                  if (!_awaiter1.IsCompleted) {
                      _state = 1;
                      _awaiter1.OnCompleted(MoveNext);
                      return;                          // ← THREAD RELEASED AGAIN
                  }
                  goto case 1;

              case 1:   // resumed after GetAsync completed
                  _awaiter1.GetResult();
                  _tcs.SetResult(_order);              // ← Task completes
          }
      }
  }
C# · What Actually Happens at Runtime
// ─── THREAD FLOW ──────────────────────────────────────────────────────────
// Thread A (HTTP request thread) calls GetOrderAsync:
//   1. MoveNext() called — state = -1
//   2. _repo.GetByIdAsync starts IO (network/SQL)
//   3. If NOT complete → registers MoveNext as continuation
//   4. Thread A is RELEASED back to the thread pool  ← key insight
//
// Thread B (any thread pool thread) when IO completes:
//   5. Continuation (MoveNext) is scheduled on thread pool
//   6. MoveNext resumes at state 0 — reads result
//   7. Continues to next await or finishes
//
// KEY: No thread is BLOCKED waiting. Thread A is free to serve other requests.
// This is why async makes servers scale — fewer threads needed.


// You can inspect the state machine yourself:
var method = typeof(OrderService).GetMethod("GetOrderAsync")!;

// IsCompleted = true → MoveNext continues synchronously, NO allocation!
public async Task<Product?> GetCachedProductAsync(Guid id, CancellationToken ct)

SynchronizationContext, Thread Pool & ConfigureAwait
ASYNC-02 What is SynchronizationContext? How does ConfigureAwait(false) affect it, and when does it cause deadlocks? Senior / Principal
✦ Answer
  SynchronizationContext flow:

  UI Thread / ASP.NET Classic:
  ┌──────────────────────────────────────────────────────┐
  │ SynchronizationContext.Current = WinFormsSyncContext  │
  │   await Task.Delay(100)                              │
  │   → continuation MUST run back on this thread        │
  │   → if thread is BLOCKED (.Result / .Wait()),        │
  │     continuation can NEVER run → ∞ DEADLOCK          │
  └──────────────────────────────────────────────────────┘

  ASP.NET Core:
  ┌──────────────────────────────────────────────────────┐
  │ SynchronizationContext.Current = null                 │
  │   → continuations scheduled on ThreadPool directly   │
  │   → .Result still dangerous (wastes thread), but     │
  │     no deadlock from SyncContext specifically         │
  └──────────────────────────────────────────────────────┘

  ConfigureAwait(false):
  ┌──────────────────────────────────────────────────────┐
  │ Tells awaiter: don't capture SynchronizationContext  │
  │ Continuation runs on any available ThreadPool thread  │
  │ → Lower overhead (no context switch)                  │
  │ → Safe in library code — required for reusable libs   │
  └──────────────────────────────────────────────────────┘

C# · ValueTask — When and Why
// ─── Task vs ValueTask ────────────────────────────────────────────────────
// Task = class (heap allocation) — even for completed/sync operations
// ValueTask = struct — ZERO allocation when result is synchronous

// ✅ Use ValueTask when: result is frequently available synchronously
public ValueTask<Product?> GetProductAsync(Guid id, CancellationToken ct)
{
    // Fast path: in-memory cache hit (99% of requests in hot catalog)
    if (_memCache.TryGetValue(id, out Product? cached))
        return ValueTask.FromResult(cached); // ZERO heap allocation

    // Slow path: DB query (allocates, but infrequent)
    return new ValueTask<Product?>(_repo.GetByIdAsync(id, ct));
}

C# · Parallel Async Patterns
// ─── Task.WhenAll: run multiple tasks concurrently ────────────────────────
// Checkout needs: user profile + cart + pricing — fetch in parallel
public async Task<CheckoutViewModel> BuildCheckoutPageAsync(string userId, CancellationToken ct)
{
    // Start ALL tasks — don't await between them (sequential would be 3x slower)
    var userTask    = _userService.GetProfileAsync(userId, ct);
    var cartTask    = _cartService.GetCartAsync(userId, ct);
    var pricingTask = _pricingEngine.GetRulesAsync(ct);

    // Await all concurrently — total time ≈ max(individual times)
    await Task.WhenAll(userTask, cartTask, pricingTask);

    return new CheckoutViewModel(
        await userTask, await cartTask, await pricingTask
    );
}

// ─── Task.WhenAny: first result wins (timeout pattern) ────────────────────
public async Task<ShippingRate?> GetFastestQuoteAsync(Order order, CancellationToken ct)
{
    using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);

    var fedex = _fedex.GetRateAsync(order, cts.Token);
    var dhl   = _dhl.GetRateAsync(order, cts.Token);
    var local = _local.GetRateAsync(order, cts.Token);

    var first = await Task.WhenAny(fedex, dhl, local);
    cts.Cancel(); // cancel the others
    return await first;
}
